## 決めたこと

1. 章題は「第4章 並べ替えを、比較とメモリから考える」。ファイルは `04-sort.md`。
2. 読了記録は `TRUNCATE reading_records;` で空にしてから、序章の大きい方と同じ式（book_count 1,000,000、2,000 万件、4 週間）で作り直す。以降の章はこの状態を使い、第7章で序章のランキングを再現できる。生成は約 13 秒。
3. 題材の SQL は `SELECT * FROM reading_records WHERE finished_at >= ... AND finished_at < ... ORDER BY finished_at DESC`。期間を 1 時間、1 日、1 週間と広げて件数を変える。
4. 「並べ替えの時間」は、Sort の `actual time` の最初の値（並べ終えて 1 行目を返せた時刻）から子の Seq Scan の全体時間を引いた差と定義する。第1章の A..B の定義を受け、公式文書の「初期処理の推定コスト」の説明を引用する。「おおよそ」と書く。
5. 計算量は O(n log n) を導入する。「n 件を並べるには、n 件それぞれについて log n 回くらい比べる」「件数が 100 倍なら仕事は 100 倍より少し多い」。第2章の O(n)、第3章の O(log n) と表で対比する。quicksort と external merge は Sort Method の名前として紹介するだけで、アルゴリズムの手順は説明しない。
6. 外部ソートは「work_mem に収まる分ずつ並べて一時ファイルに書き、あとで合流する」と説明し、`Buffers` の `temp read` と `temp written` を読む。work_mem の公式引用。
7. work_mem を 1GB にした実験は「速くならなかった」事実を表で示し、理由は追わないと明記する。「メモリを増やせば速くなる、とは限らない」だけを持ち帰る。SET は接続だけに効き、RESET で戻す手順を書く。
8. `shared hit` と `read` は、845MB の表が shared_buffers 128MB に収まらないので毎回 `read` が出る、で回収する。shared_buffers の公式引用。OS のキャッシュのことは控えめに一文。
9. 章末の「目録は並び順を持っている」は books の `ORDER BY id LIMIT 20` と `ORDER BY title LIMIT 20`（Index Scan、Sort なし）だけ示し、読了記録の finished_at に目録がないことを次章の引きにする。
10. 用語: 並べ替え（ソート）、外部ソート、一時ファイル、合流（マージ）、work_mem、shared_buffers、O(n log n)（オーダー エヌ ログ エヌ）。「ヒープ」は出さない。
11. 図は Mermaid 1 枚（外部ソートの模型: 500 万件 → 64MB 分ずつ並べる → 一時ファイル → 合流 → 並んだ結果）。

## 章の構成

### はじめに
第3章で検索は速くなった。次は並べる。読了記録が序章の規模になり、新しい順に並べる一覧を題材にする。この章で手に入れるのは、並べ替えの仕事量の見方と、メモリに収まらないときに何が起きるかの観察。3 段落前後。序章と同じ :::message。

### 読了記録が2,000万件になった
物語。友人たちの利用が広がり、読了記録は序章の「利用が広がった状態」の 2,000 万件に届く。実験では 2 万件の記録を空にして、序章と同じ式で 2,000 万件を作り直す（TRUNCATE、INSERT、ANALYZE。約 13 秒）。845MB、108,109 ページ。二人は「読み終えた本を新しい順に並べる一覧」を作ることにする。会話 3 行前後。

### 件数が増えると、並べ替えの仕事はどう増えるか
予想。1 時間分（約 3 万件）、1 日分（約 71 万件）、1 週間分（約 500 万件）を新しい順に並べる。件数が増えると並べ替えの時間はどう増えるか。選択肢: 件数に比例 / 比例より少し多い / 件数の 2 乗くらい。あわせて「500 万件を全部メモリで並べられるか」も問う。答えは示さない。

### 並べ替えの時間だけを取り出す
1 時間分の EXPLAIN ANALYZE（1 回目）を転記。Sort が Seq Scan の上に積まれている（第2章の Limit と同じ形）。Sort の actual time の最初の値は、並べ終えて 1 行目を返せた時刻。子の Seq Scan の全体時間との差が並べ替えの時間（おおよそ）。公式引用（初期処理コスト）。`Sort Method: quicksort Memory: 1699kB` を「メモリの中で並べた。使ったメモリ 1.7MB」と読む。

### 件数を増やして測る
1 日分、1 週間分の出力（1 回目）を転記。表: 期間 / 件数 / Sort Method / 使ったメモリまたはディスク / 並べ替えの時間 / 全体。倍率の読み方（独立レビュー後に訂正）: 1 時間分の並べ替えは 5 ms 前後で、690 ms 前後の全体からの差として取り出しているため誤差が大きく、倍率の比較には向かない（1 時間→1 日は 24 倍で 16〜27 倍とブレる）。O(n log n) の主張は 1 日→1 週間（件数 7.0 倍）を主軸にする。実測は 7.9〜10.1 倍で、外部ソートへの切り替えを含む。O(n log n) の見込みは 7 × (log 5,000,000 ÷ log 714,284) ≒ 8.0 倍。メモリに収まる条件（work_mem 1GB の節の実測、並べ替えの時間 793 / 919 ms）では 6.7〜8.7 倍。ここで O(n log n) を導入。第2章の O(n)、第3章の O(log n) と表で対比。

### メモリに収まらないときに何が起きるか
1 週間分の Sort Method external merge Disk 127216kB と Buffers の temp read / written を読む。work_mem の公式引用（64MB に設定してある）。外部ソートの説明（収まる分ずつ並べて一時ファイルへ、あとで合流）。Mermaid の模型図。SET work_mem = '1GB' で同じ SQL を実行すると quicksort Memory 352858kB になるが、全体の時間は速くならなかった（表: 64MB と 1GB、3 回と 2 回）。理由はこの本では追わない。RESET work_mem。

### 読んだページの hit と read
1 時間分でも 1 週間分でも Buffers は hit 約 16,200、read 約 91,850 で、合計は表の 108,109 ページ。shared_buffers の公式引用（128MB）。845MB は収まらないので、毎回大半を外から読む。ただし 0.85 秒で読めているので OS のメモリから来ていると考えられる、と控えめに。第2章の約束の回収と、「時間よりページ数で数える」方針の再確認。

### 目録は並び順を持っている
books の `ORDER BY id LIMIT 20` と `ORDER BY title LIMIT 20` の出力。Sort ノードがなく、Index Scan だけで 20 冊が順に出る。目録は作ったときから並んでいる。読了記録の finished_at には目録がないので、いまは毎回並べている。

### この章で持ち帰ること
- 並べ替えの仕事は件数に比例より少し多く増える（O(n log n)）。O(n) と O(log n) との違い
- work_mem に収まらなければ一時ファイルに書いて合流する。メモリを増やせば速くなるとは限らない
- 大きな表は shared_buffers に収まらず、毎回 read が出る。ページ数で数える方針は変わらない
- 目録は並び順を持っていて、並べ替えの仕事を消せることがある

### 次の章へ
一覧の画面は新しい順に 20 件しか出さない。500 万件を全部並べる必要があるのか。LIMIT 20 を付けると Sort Method に別の名前が出る（名前は出さない）。第5章で確かめる。
