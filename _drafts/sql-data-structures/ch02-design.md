- `_drafts/sql-data-structures/experiments/README.md` に第2章の計測条件を追記

## 決めたこと

1. 章題は「第2章 本が増えると、探す仕事はどれだけ増えるか」。ファイル名は `02-linear-search.md`。
2. 読者の DB の本を 1,000 冊から 10 万冊、100 万冊へ増やす。この章を終えると `books` は 100 万冊になり、以降の章もそのまま使う。読了記録は増やさない（「並べる」の章で 2,000 万件にする）。
3. データを増やす前に、実験用の設定を序章の実測条件に揃える。`ALTER DATABASE reading_log SET max_parallel_workers_per_gather = 0;`、`SET jit = off;`、`SET work_mem = '64MB';` の 3 つ。設定後は `\q` で抜けて再接続し、`SHOW` で確認する。理由は「100 万冊では PostgreSQL が自動で作業を手分けする並列読みに切り替わり、計画の形が変わる。この本では一人分の仕事量を見たいので止める。実験用の設定で本番向けではない。並列は発展で扱う」。
4. 仕事量は時間ではなくページ数で数える。`EXPLAIN ANALYZE` の `Buffers: shared hit=N` をこの章で読み始める。PostgreSQL 18 では ANALYZE を付けると BUFFERS が既定で有効なので、コマンドは第1章と同じ `EXPLAIN ANALYZE` のまま。17 以前は `EXPLAIN (ANALYZE, BUFFERS)` と明示する、と一言添える。
5. 「見つかったところで止まれるか」の実験は 10 万冊の段階で行う。100 万冊では表が大きくなり、PostgreSQL が直前の読み位置から読み始める工夫（synchronize_seqscans）で開始位置が変わるため。この現象は 100 万冊の節の `:::details` に発展として置き、公式文書を引用する。
6. 「ヒープ」という言葉はこの章では出さない。表を「ページの集まり」と呼ぶ。
7. 図は Mermaid 1 枚（Seq Scan がページを先頭から順に読む模型）。数値の比較は表で示す。

## 章の構成

見出しはトピック直接型。区切り記号と補足括弧を付けない。

### はじめに

第1章で題名検索は 1,000 冊全部を見ていた。本が増えたら仕事はどう増えるか。この章では本を 100 倍、1,000 倍に増やして測り、仕事量を時間ではなくページ数で数える見方を手に入れる、という位置づけを 3 段落前後で。序章と同じ `:::message`。

### 本が増える前に、探す仕事の増え方を知りたい

物語。友人たちが自分の本を登録し、読みたい本も探せるように書誌データをまとめて取り込む計画が出る。いまは 1,000 冊で速いが、10 万冊、100 万冊になったら題名検索はどうなるか。二人は増やす前に手元で確かめることにする。会話 3 行前後。読了記録が 2,000 万件あることに触れてよいが、ランキングの答えは出さない。

### 実験用の設定を序章に揃える

`ALTER DATABASE` の 3 行、`\q` と再接続、`SHOW` 3 つ。理由を 2〜3 文で。並列は発展で扱うと予告。

### 本が100倍になったら、捨てる行数と時間はどう変わるか

予想。1,000 冊で捨てた行は 999、時間は 0.041 ms だった。10 万冊にしたら、捨てる行数と時間はそれぞれどうなるか。選択肢は「変わらない」「100 倍くらい」「100 倍よりずっと大きい」。二人の会話 3 行前後。ここではページの話をまだ出さない。

### 本を10万冊に増やして測る

`INSERT ... generate_series(1001, 100000)`、`ANALYZE books`、`count(*)`、`EXPLAIN ANALYZE`（1 回目の出力を転記）。捨てた行 99,999、時間約 3.2 ms。予想の答え合わせ。

続けて `Buffers: shared hit=736` を読む。第1章で読み飛ばした行。ページとは「8 キロバイトの箱」で、表はこの箱の集まりとして保存されている（公式引用）。`pg_class` の `relpages` が 8 から 736 になったことを示し、1 ページに約 136 冊入っていると計算で示す。`shared hit` はメモリにあったページ、`read` はディスクから読んだページ。合計が読んだページ数で、仕事量として数える。時間は環境と回ごとにブレるが、ページ数は同じ操作なら同じ値になる、と 3 回分の時間と一緒に示す。BUFFERS の公式引用。

### 見つかったところで止まれるか

第1章の予想の選択肢「見つかったところで止まる」を確かめる。`LIMIT 1` を付けると 1 行見つかったところで止まれる。先頭近く、真ん中、末尾近くの 3 冊で `Buffers` と `Rows Removed by Filter` を比べる（10 万冊、出力 3 つを転記）。位置で仕事が変わり、最悪は全部。`LIMIT` なしなら同じ題名の本が他にもあるかもしれないので最後まで見る（比較用の出力を転記）。「探し物がどこにあるかで仕事が変わる。最悪の場合は全部」を、計算量の考え方の入り口として置く。

### 100万冊でも測る

`INSERT ... generate_series(100001, 1000000)`（数秒かかる）、`ANALYZE`、`count(*)`、`EXPLAIN`（cost も比例して増えることを一言）、`EXPLAIN ANALYZE`（1 回目を転記）。3 段の表で冊数、読んだページ、捨てた行、時間を並べる。冊数が 10 倍でページも 10 倍。ここで計算量を導入する。「本の数を n としたとき、仕事が n に比例して増える探し方を O(n) と書く。n が 1,000 倍なら仕事も 1,000 倍」。言葉は噛み砕き、記号の読み方（オーダー エヌ）を添える。

`:::details 100万冊で LIMIT 1 を試すと` に発展の注記。大きな表では PostgreSQL が直前の読み位置から読み始めることがあり、`LIMIT 1` の結果が先頭からの位置どおりにならない。公式引用（synchronize_seqscans）。この本では 10 万冊で試した理由もここに書く。

### 表はページの集まりとして並んでいる

Seq Scan の模型図。Mermaid `flowchart TB` で、ページ 0、ページ 1、…、ページ 735 を縦に並べ、各ページの 136 行に `Filter` を当てながら次へ進む流れ。ノード数は 4〜5 に絞る（ページ 0、ページ 1、途中の省略、ページ 735、結果）。図の直前に目的、直後に読み取れること。実測ではなく模型だと明記。

### この章で持ち帰ること

- 全部を見る探し方の仕事は、本の数に比例して増える（O(n)）
- 仕事量は時間ではなくページ数で数える。時間はブレるがページ数は再現する
- 探し物の位置で仕事は変わるが、最悪は全部
- `LIMIT` がなければ、条件に合う行が他にもあるかもしれないので最後まで見る

### 次の章へ

番号検索は 100 万冊でも 7 ページと 4 ページだった（出力 1 つを転記してよい）。1,000 倍に増えたのに、読むページはほとんど増えていない。なぜかは第3章で、主キーのインデックスの中身（木構造）を見て確かめる。
