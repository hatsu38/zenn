## コントローラーの通読メモ（T3 の結果と合わせて裁定する。T3 には渡していない）

1. 物語の整合。「本の詳細画面で使っている SQL」が題名検索になっているが、詳細画面なら番号で引くのが自然。題名の完全一致は「本を探す検索機能」の SQL として置き直し、番号検索を詳細画面の SQL にすると、序章の表（本を探す検索機能）ともつながる。
2. 操作性。`EXPLAIN SELECT ...` と `EXPLAIN ANALYZE SELECT ...` のコマンド自体が本文にない。出力の直前に読者が打つ SQL を ```sql で置く（番号検索の EXPLAIN ANALYZE も同様）。
3. 技術的な正確さ。「インデックスを 1 回調べただけ」は、インデックスで場所を調べてから表の 1 行を読む、が正しい。図と本文を直す。
4. 図。フローチャートは Zenn の Mermaid で枝の中が横並びになる。案 B（縦一列を 2 枚）に差し替え、`Rows Removed by Filter: 999` を節点にしない。設計メモの「1 枚」を「2 枚」に変更する（コントローラー判断）。
5. 文体。序章はインライン code の前後に半角スペースを置く（「`SELECT` でデータ」）。初稿はスペースなし（「`EXPLAIN`という機能」）。序章に揃える。
6. 冒頭。「件数を数えただけでは」は序章の内容（時間を測った）と合わない。「時間を測っただけでは」に直す。
7. 見出し「予想する。題名で1冊探すとき、PostgreSQL は何冊調べるか」の句点区切りは、見出しに二要素を詰める形に近い。「題名で1冊探すとき、PostgreSQL は何冊調べるか」に絞る。
8. 「あなたなら、どちらだと予想しますか」は 3 択なので「どれ」。
9. 「3回分の記録は、番号で探す場合と合わせてこの章の終わりに置きます」だが、:::details は番号検索の節末にある。表現を合わせる。
10. 「ノード」の初出に言い換えがない（中 2 基準）。「ノード（実行計画の中の処理の単位）」など。
11. EXPLAIN ANALYZE 節で、公式の「実際にその問い合わせを実行し」の引用が答え合わせの後に来る。EXPLAIN ANALYZE を導入した直後に移すと流れが素直。
12. ER 図に PK 表記がない。序章時代の試作では `PK` を付けていた。FK を付けない判断とは別なので、`bigint id PK` にしてよい。
