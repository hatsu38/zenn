# 第6章で引用候補にする PostgreSQL 18 日本語文書の文（2026-09-21 取得、原文どおり）

## 50.5 プランナ/オプティマイザ（結合の 3 つの戦略）  https://www.postgresql.jp/document/18/html/planner-optimizer.html

> ネステッドループ結合：左側のリレーションの中で見つけられた行ごとに右側のリレーションが1回スキャンされます。この戦略は実装が簡単ですが、時間がかかる場合があります。（とは言っても右側のリレーションがインデックススキャンによってスキャン可能であればよい戦略になります。右側のインデックススキャンのキーとして左側のリレーションの現在の行の値を使用することができます。）

> ハッシュ結合：右側のリレーションがハッシュキーとして結合属性を用いて初めにスキャンされ、ハッシュテーブルに読み込まれます。次に左側のリレーションがスキャンされ、見つかったそれぞれの行に相応しい値が、右側のリレーションの行を探し出すためのハッシュキーとして使われます。

## 14.1.1 EXPLAINの基本（結合）  https://www.postgresql.jp/document/18/html/using-explain.html

> ネステッドループ結合ノードは、外部の子から得られた行毎に、その２番目または「内部の」子を一回実行します。現在の外部の行からの列の値は内部スキャンに組み込まれます。

> ここでプランナはハッシュ結合の使用を選択しました。片方のテーブルの行がメモリ内のハッシュテーブルに格納され、もう片方のテーブルがスキャンされた後、各行に対して一致するかどうかハッシュテーブルを探索します。

> マージ結合は、結合キーでソートされる入力データを必要とします。この例では、各入力がインデックススキャンを使用して正しい順序で行にアクセスすることでソートされますが、シーケンシャルスキャンとソートも使用できます。

## 14.1.2 EXPLAIN ANALYZE（loops）  https://www.postgresql.jp/document/18/html/using-explain.html

> 例えば、上述のネステッドループの計画では、内部インデックススキャンは外部の行ごとに一度行われます。このような場合、loops値はそのノードを実行する総回数を報告し、表示される実際の時間と行数は1実行当たりの平均です。

## 19.7.1 プランナメソッド設定  https://www.postgresql.jp/document/18/html/runtime-config-query.html

> 問い合わせプランナがハッシュ結合計画型を選択することを有効もしくは無効にします。デフォルトはonです。

> 問い合わせプランナがマージ結合計画型を選択することを有効もしくは無効にします。デフォルトはonです。

## 19.4.1 メモリ（work_mem とハッシュ）  https://www.postgresql.jp/document/18/html/runtime-config-resource.html

> ハッシュテーブルはハッシュ結合、ハッシュに基づいた集約、メモ化（memoize）ノードおよびIN副問い合わせのハッシュに基づいた処理で使用されます。

> 一般的に、ハッシュに基づく操作はソートに基づく操作よりも利用可能なメモリに敏感です。ハッシュテーブルのメモリ制限は、work_memにhash_mem_multiplierを乗算することで計算されます。

## 補足（引用ではなく、執筆時の確認事項）

- PostgreSQL 18 では Nested Loop の内側に Memoize（同じキーの結果を覚えておく仕組み）が挟まることがある。本文では「同じ本を二度引かないための覚え書き。この本では読み飛ばす」と一言で済ませ、公式引用（メモ化ノード）に触れる程度にする。
- ハッシュ表の説明は「値から置き場所（バケット）を直接計算する箱。並んでいなくても 1 回で見つかる」。Buckets、Batches、Memory Usage を Hash ノードの行で読む。Batches が 2 以上なら一時ファイルに分けている。
- 「1 時間分でもハッシュ表を作る 0.2 秒がかかる」を「前処理と繰り返しのトレードオフ」の実測として使う。プランナがその場面で Nested Loop を選ばなかった理由の分析はしない。
- GROUP BY の HashAggregate もハッシュ表を使う（本ごとに数える箱）。第7章のランキングの部品として名前だけ結ぶ。
