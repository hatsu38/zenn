こんにちは、hatsu です。

PostgreSQL の `EXPLAIN` について書いているとき、検証用のデータ作りで詰まりました。
`random()` で 100 万行を作ると、実行するたびに中身が変わります。
記事に `rows=45` と書いても、読者の手元では違う数字が出ます。

しかも `random()` で一様に散らすと、データがのんべんだらりと平坦になります。
現実のデータには偏りがあり、その偏りこそがプランナの挙動を左右します。

そこで「何度実行しても同じ」と「現実的な偏りがある」を両立させる作り方を考えました。
やってみると、`md5()` と累積和だけで済みました。

## TL;DR

- `random()` は再現できない。`setseed()` でも「何行目に何が来るか」が実行順に依存する
- `md5(id)` から疑似乱数を作れば、行ごとに独立して値が決まる。実行順に一切左右されない
- 割合どおりの振り分けは、0 から 1 の数直線を割合の長さに区切るだけでよい
- 重みつきの振り分け（人口比など）は、累積和で区間を作って範囲 JOIN すれば書ける
- カラム間の相関を意図的に作り込むと、プランナが行数を読み違える様子を再現できる（見積もり 4 行に対して実測 46 行）

作ったサンプル環境はこちらです。

https://github.com/hatsu38/zenn-explain-sandbox

## random() では手元と同じ数字が出ない

一番素直な書き方はこれです。

```sql
INSERT INTO people (id, blood_type)
SELECT i,
       (ARRAY['A','O','B','AB'])[1 + floor(random() * 4)::int]
FROM generate_series(1, 1000000) AS i;
```

これには問題が二つあります。

一つ目は再現性です。
実行するたびに中身が変わるので、記事に載せた `EXPLAIN` の数字を読者が確かめられません。

二つ目は分布です。
`random() * 4` は四つの血液型を 25% ずつに散らします。
しかし日本人の血液型は A が約 38%、O が約 31%、B が約 22%、AB が約 9% です[^blood]。
一様分布にしてしまうと、プランナが「どの値が何件あるか」を頼りに判断する場面を再現できません。

[^blood]: 日本赤十字社が公開している献血者の血液型分布による概数。

再現性については `setseed()` という手があります。

```sql
SELECT setseed(0.42);
```

乱数列は固定できますが、これは「乱数を何番目に引いたか」で値が決まる仕組みです。
クエリを書き換えて行の処理順が変わったり、並列実行が挟まったりすると、同じ行に別の値が入ります。
検証用データの生成としては、もう少し強い保証が欲しいところです。

## md5 から決定的な疑似乱数を作る

`md5()` は入力が 1 文字違えば結果が大きく変わり、同じ入力なら必ず同じ結果を返します。
この性質を使えば、行の `id` から「乱数のように見えて完全に決まっている数」を作れます。

```sql
CREATE OR REPLACE FUNCTION det_rand(n bigint, tag text)
RETURNS double precision
LANGUAGE sql
IMMUTABLE
PARALLEL SAFE
AS $$
    SELECT (('x' || substr(md5(n::text || ':' || tag), 1, 7))::bit(28)::int)
           / 268435456.0
$$;
```

やっていることは三段階です。

1. `md5()` でハッシュ値（16 進数 32 桁）を得る
2. 先頭 7 桁だけを取り出し、`bit(28)` 経由で整数にする
3. 28 ビットの最大値で割って 0 以上 1 未満に収める

`('x' || 16進文字列)::bit(n)` は、16 進数の文字列をビット列として解釈する書き方です。
7 桁にしているのは 28 ビットに収めるためで、32 ビットにすると符号ビットを踏んで負の値が出ます。

第二引数の `tag` が効きます。

```sql
SELECT det_rand(1, 'blood'), det_rand(1, 'zodiac');
```

同じ `id` でも `tag` が違えば別の値が返るので、血液型を決める乱数と星座を決める乱数を独立させられます。
`tag` を使い回すと二つの値が連動してしまいます。

`IMMUTABLE` を付けているのは、同じ引数なら必ず同じ結果になるとプランナに伝えるためです。
これを宣言しておくと、式インデックスに使えるようになり、プランナが計算を省略できる場面も増えます。

## 割合どおりに振り分ける

血液型のような固定の割合は、0 から 1 の数直線を割合の長さに区切るだけで書けます。

```
0.00        0.38        0.69      0.91   1.00
 |─── A ─────|──── O ────|── B ───|─AB─|
     38%          31%       22%     9%
```

```sql
CASE
    WHEN det_rand(i, 'blood') < 0.38 THEN 'A'
    WHEN det_rand(i, 'blood') < 0.69 THEN 'O'   -- 0.38 + 0.31
    WHEN det_rand(i, 'blood') < 0.91 THEN 'B'   -- 0.69 + 0.22
    ELSE 'AB'
END
```

`CASE` は上から順に評価されるので、区間の右端を書き並べれば済みます。
区間の幅がそのまま確率になります。

100 万行で実際に測ると、こうなりました。

```
 blood_type |  人数  | 割合
------------+--------+-------
 A          | 380042 | 38.00
 O          | 310640 | 31.06
 B          | 219849 | 21.98
 AB         |  89469 |  8.95
```

狙った割合とほぼ一致しています。

## 重みつきで振り分ける

都道府県を人口比で振り分けたいときは、区間を手で書くわけにはいきません。
47 個分の境界を電卓で出すのは面倒で、人口を修正したら全部やり直しになります。

そこで累積和を使って、区間を SQL に計算させます。

```sql
WITH pref_band AS (
    SELECT
        id,
        (SUM(population) OVER (ORDER BY id) - population)::numeric
            / SUM(population) OVER ()  AS lo,   -- 区間の左端
        (SUM(population) OVER (ORDER BY id))::numeric
            / SUM(population) OVER ()  AS hi    -- 区間の右端
    FROM prefectures
)
```

`SUM(population) OVER (ORDER BY id)` は id 順に足し上げた累計、`SUM(population) OVER ()` は総和です。
累計から自分の人口を引けば区間の左端になり、累計そのものが右端になります。
総和で割って 0 から 1 の範囲に正規化します。

| 都道府県 | 人口（万人） | 区間の幅 |
| --- | --- | --- |
| 東京都 | 1400 | 0.111 |
| 神奈川県 | 920 | 0.073 |
| 鳥取県 | 54 | 0.004 |

あとは乱数がどの区間に落ちたかで JOIN します。

```sql
JOIN pref_band AS pb
    ON r_pref >= pb.lo AND r_pref < pb.hi
```

人口が多い県は区間が広いので、そこに落ちる確率が高くなります。
ダーツの的で、東京都の面積を鳥取県の 26 倍にしたようなものです。

実測はこうなりました。

```
 都道府県 |  人数  | 割合
----------+--------+-------
 東京都   | 112849 | 11.28
 神奈川県 |  74005 |  7.40
 大阪府   |  70159 |  7.02
...
 高知県   |   5354 |  0.54
 島根県   |   5255 |  0.53
 鳥取県   |   4207 |  0.42
```

東京都と鳥取県で 26.8 倍の差が付いています。
これで「同じ `prefecture_id` というカラムなのに、指定する値によってヒット件数が 26 倍違う」という状況が作れました。

## カラム間の相関を意図的に作る

ここまでは各カラムを独立に決めてきました。
逆に、わざと相関させたいこともあります。

星座は生年月日から一意に決まります。
そこで星座だけは乱数を使わず、生年月日から計算しました。

```sql
CASE
    WHEN md >= 321  AND md <= 419  THEN '牡羊座'
    WHEN md >= 420  AND md <= 520  THEN '牡牛座'
    WHEN md >= 521  AND md <= 621  THEN '双子座'
    -- ...
    ELSE '山羊座'   -- 12/22 から 1/19 は年をまたぐのでここに落とす
END
```

`md` は `to_char(birthday, 'MMDD')::int` で、5 月 15 日を `515` という整数にしたものです。
日付を 4 桁の整数にすると、大小比較だけで範囲判定できます。
山羊座だけが年をまたぐので、他を全部判定したあとの `ELSE` に落としています。

星座ごとの日数は 28 日から 32 日と少し違うので、割合も少しばらつきます。

```
 zodiac | 人数  | 割合
--------+-------+------
 双子座 | 87760 | 8.78
 ...
 射手座 | 79153 | 7.92
```

## 相関があると、プランナは行数を読み違える

この相関が、そのまま検証の題材になります。

まず生年月日だけで絞ってみます。

```sql
EXPLAIN ANALYZE SELECT * FROM people WHERE birthday = '1990-05-15';
```

```
 Bitmap Heap Scan on people  (cost=4.77..175.71 rows=45 width=38)
                             (actual time=0.026..0.090 rows=46.00 loops=1)
```

見積もりが `rows=45`、実測が `rows=46.00` です。
統計情報がよく効いていて、ほぼ当たっています。

ここに星座の条件を足します。
1990 年 5 月 15 日生まれは全員が牡牛座なので、ヒットする人数は変わらないはずです。

```sql
EXPLAIN ANALYZE
SELECT * FROM people WHERE birthday = '1990-05-15' AND zodiac = '牡牛座';
```

```
 Bitmap Heap Scan on people  (cost=4.76..175.82 rows=4 width=38)
                             (actual time=0.149..0.539 rows=46.00 loops=1)
   Recheck Cond: (birthday = '1990-05-15'::date)
   Filter: (zodiac = '牡牛座'::text)
```

実測は `rows=46.00` のままですが、見積もりが `rows=4` に落ちました。
11.5 倍のズレです。

原因は掛け算です。
プランナはカラムどうしが独立だと仮定するので、それぞれの選択率を掛けます。
生年月日で 45 行に絞れて、星座で 12 分の 1 になるなら、45 ÷ 12 ≒ 4 行だという計算です。

実際には星座は生年月日から決まっているので、絞り込みは二重に効きません。
プランナがこの依存関係を知らないために、見積もりが 11 分の 1 に縮んでしまいます。

## 拡張統計で相関を教える

このズレは `CREATE STATISTICS` で直せます。
複数カラムの間の関係を、プランナに追加で採取させる機能です。

```sql
CREATE STATISTICS stat_people_birthday_zodiac (dependencies, ndistinct)
  ON birthday, zodiac FROM people;
ANALYZE people;
```

同じクエリを投げ直します。

```
 Bitmap Heap Scan on people  (cost=4.77..175.83 rows=45 width=38)
                             (actual time=0.031..0.096 rows=46.00 loops=1)
```

`rows=4` が `rows=45` に戻りました。
実測 46 行に対して、ほぼ一致しています。

`dependencies` は「birthday が決まれば zodiac も決まる」という関数従属性を採取するオプションです。
これがあると、プランナは選択率を掛け算せず、依存している側の条件を無視します。

## まとめ

検証用データを作るときに使った道具は、これだけでした。

- **`md5(id)` 由来の疑似乱数**：行ごとに独立して値が決まるので、実行順に左右されない
- **数直線の区切り**：固定の割合はこれで足りる
- **累積和による区間**：重みつきの振り分けは SQL に計算させる
- **導出カラム**：意図的に相関を作れば、見積もりのズレを再現できる

100 万行の投入は 2 分 40 秒でした（PostgreSQL 18.4、Docker、Apple Silicon）。
`md5()` を 1 行あたり 4 回ほど呼ぶので、`random()` を使う場合よりは遅くなります。
それでも、記事や書籍に載せた数字が読者の手元でそのまま再現できる価値のほうが大きいと感じています。
