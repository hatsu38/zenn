## この章で分かること

Indexにも100万冊分の情報があるのに、なぜ全件を調べずに探せるのでしょうか。番号1〜9の図で、範囲を絞って探す仕組みを確かめます。その後、題名のIndexを作って同じ検索を比べ、探す範囲を広げると選ばれる方法がどう変わるかを観察します。最後に題名の範囲で約1割の本を探し、目録の順とテーブルの順が違うときに選ばれる三つ目の方法を見ます。

:::message
第1章の本100万冊を使い、題名のIndexがない状態から始めます。この章で作った`books_title_idx`は、次章以降も残します。
:::

## 目録も大きいのに、どう探す？

ここまで、100万冊から1冊を探してきました。題名を順番に比べると、多くのレコードを読む必要があります。一方、番号検索はIndexという目録を使えました。

でも、Indexにも100万冊分の情報があるはずです。Indexを先頭から全部読んでいたら、あまり助けにならなそうです。

![本100万冊の棚と同じ長さで、Indexの目録にも100万件が並ぶ](/images/postgresql-query-journey/06-catalog-question.png)
*本の棚と同じ長さで並ぶ、目録の100万件を見てください（説明するための図）。*

## 番号の範囲から、探す先を選ぶ

番号1〜9を、順番に三つの箱へ分けます。左の箱に1、2、3、真ん中に4、5、6、右に7、8、9を入れました。

三つの箱の上に案内板を一枚立て、箱の境目となる4と7を書いておきます。探したい番号が8なら、どの箱を開けばよいでしょうか。

![案内板の境目4と7を見て、8は7以上なので右の箱だけを開き、その中で8を見つける。左と真ん中の箱は開かない](/images/postgresql-query-journey/06-btree-path.png)
*開くのは右の箱だけで、×を付けた二つの箱は開きません（番号1〜9で説明するための図）。*

8は7以上なので、右の箱へ進みます。その中から8を見つければよく、左と真ん中の箱を開く必要はありません。

PostgreSQLの**B-tree Index**は、値の範囲で進む先を選ぶこの構造を使っています。案内板から行き先が枝分かれする形を、木に見立てています。入口の案内板を**根**、末端の箱を**葉**と呼びます。大きなIndexでは、根と葉の間にも案内板が入ります。

実際のIndexでは、案内板も箱も「ページ」というデータのまとまりです。葉のページには、探す値と、テーブルのどこにレコードがあるかという情報が入っています。ページの大きさとレコードの場所は、第4章で調べます。いまは「案内板で範囲を絞り、必要な箱だけを読む」という動きを押さえてください。

## 冊数が増えると、案内板の段数はどう増えるか

仮に一枚の案内板に100個の行き先が書けるなら、案内板が1段で100個、2段で100×100＝1万個の箱へ行き先を分けられます。箱に100冊ずつ入るなら、案内板2段と葉の箱を合わせた3段で100万冊に届きます。100は増え方をつかむために仮に置いた数で、3段はその仮定から計算した結果です。実際のIndexの分岐数を測った値ではありません。

案内板を1段増やすと分けられる範囲が100倍になるので、冊数が100倍に増えるまで段は増えません。件数が掛け算で増えても、段数は1段ずつしか増えません。この増え方を`O(log n)`と表します。実際の題名のIndexが何段だったかは、第4章で確かめます。

図で、各段で1枚ずつ読んだ合計と、全部を読んだときの枚数を比べてください。

![案内板1枚、案内板100枚、箱1万個の3段から、各段1枚ずつ合わせて3枚だけをたどる。全部なら10,101枚で、1億冊でも4段で4枚になる](/images/postgresql-query-journey/06-tree-levels.png)
*各段で1枚ずつ、合わせて3枚だけを読みます。全部を読むと10,101枚です（説明するための図。1枚の案内板に100個の行き先が書けると仮に置いています）。*

`log`を初めて見ても、まずは**100万件でも、たどるのは数枚の案内板と箱一つで済む**と理解できれば十分です。ただし、案内板をたどった後にテーブルから取り出すレコードが多ければ、そのレコードを読む仕事は別にかかります。

## 題名にもIndexを作る

第1章で用意した100万冊をそのまま使います。Indexを作る前に、題名検索を記録してください。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM books WHERE title = '実験用の本 42';
```

2026年9月25日、PostgreSQL 18.6の新規DBで第1章のデータを用意し、第2章に続けて実行した結果です。並列実行とJITは無効です。この節と次の番号の範囲検索は、同じ通し実行から掲載しています。

```sql
Seq Scan on books  (cost=0.00..19853.00 rows=1 width=30) (actual time=0.010..38.387 rows=1.00 loops=1)
  Filter: (title = '実験用の本 42'::text)
  Rows Removed by Filter: 999999
  Buffers: shared hit=4657 read=2696 written=94
Planning Time: 0.051 ms
Execution Time: 38.405 ms
```

第1章と同じく、100万件に条件を当てています。第2章の`LIMIT 1`とは違い、今回は条件に合うレコードをすべて求める検索です。今回は`Buffers`の`shared hit=4657`と`read=2696`を合わせて7,353回です。`written=94`は、このバックエンドが以前に変更されたページを書き戻した数で、読み取りの7,353回へは足しません。この数は次章で使うので覚えておいてください。

続いて題名用のIndexを作り、統計情報を更新します。

```sql
CREATE INDEX books_title_idx ON books (title);
ANALYZE books;
```

実行結果です。

```sql
CREATE INDEX
ANALYZE
```

同じ題名検索を、もう一度実行します。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM books WHERE title = '実験用の本 42';
```

Indexを作った後の実行結果です。

```sql
Index Scan using books_title_idx on books  (cost=0.42..8.44 rows=1 width=30) (actual time=0.053..0.054 rows=1.00 loops=1)
  Index Cond: (title = '実験用の本 42'::text)
  Index Searches: 1
  Buffers: shared hit=1 read=3
Planning:
  Buffers: shared hit=8 read=1
Planning Time: 0.150 ms
Execution Time: 0.067 ms
```

今度は`Index Scan using books_title_idx`になりました。作った題名のIndexを使っています。さっきの`Filter`に代わり、`Index Cond`に題名の条件が出ていることも確認できます。

| 比較するもの | Indexを作る前 | Indexを作った後 |
| --- | --- | --- |
| 探す方法 | Seq Scan | Index Scan |
| 返したレコード | 1件 | 1件 |
| Rows Removed by Filter | 999,999件 | 表示なし |
| 実行時のshared hit | 4,657 | 1 |
| 実行時のshared read | 2,696 | 3 |
| Execution Time | 38.405 ms | 0.067 ms |

### 同じ1件を、別の方法で探している

Indexを作る前は、100万件の題名を順に比べ、999,999件を除外していました。作った後は、`Index Cond`に書かれた題名を使い、Indexからレコードの場所を探しています。返す本は同じでも、そこにたどり着く方法が変わりました。

読む量の違いは、`Buffers`にも表れています。検索の実行中の値を比べると、7,353回から、`hit=1`と`read=3`を合わせた4回へ減っています。これはレコード数ではなく、**ページにアクセスした回数**です。`Planning`の下の値は計画を作るときのアクセスなので、ここには足しません。この1回が何を数えたものかは、次章で確かめます。

実行時間も38.405 msから0.067 msへ短くなりました。今回の出力では、時間だけでなく、探す方法とアクセス回数にも変化があります。何倍速くなるかは実行する環境や状態で変わるため、まずはこの三つを対応させて読んでください。

:::details Index Searchesという表示について
`Index Searches: 1`は、Indexの探索を1回行ったことを示します。その1回の探索で、根から葉まで複数のページを使うことがあります。1ページだけ読んだという意味ではありません。`hit`と`read`の違いは第5章で説明します。
:::

## 一点を探した後に、たくさん読む場合

次は、範囲を指定して4以上8以下を取り出す場合です。

![案内板から4のある真ん中の箱へ進み、4・5・6を取り出してから隣の右の箱で7と8を取り出し、範囲外の9で止まる。テーブルから取り出すレコードは5件](/images/postgresql-query-journey/06-range-scan.png)
*探すのは1回で、開く箱は2個、テーブルから取り出すレコードは5件です。範囲が広がると、取り出すレコードが増えます（番号1〜9で説明するための図）。*

まず4がある場所を探し、4、5、6、7、8と順に取り出します。途中で箱の終わりに来たら、隣の箱へ進みます。1冊の場所を見つけたときとは違い、範囲に入る冊数が増えるほど、その後に取り出すレコードも増えます。

今度は番号の範囲で探します。条件が番号なので、使えるのは主キーの番号用のIndexである`books_pkey`です。題名用の`books_title_idx`は、題名の条件にしか使えません。

まず、400000から400010までの11冊を探します。`BETWEEN`は両端の値を含みます。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM books WHERE id BETWEEN 400000 AND 400010;
```

実行結果です。

```sql
Index Scan using books_pkey on books  (cost=0.42..8.64 rows=11 width=30) (actual time=0.053..0.054 rows=11.00 loops=1)
  Index Cond: ((id >= 400000) AND (id <= 400010))
  Index Searches: 1
  Buffers: shared hit=3 read=4
Planning:
  Buffers: shared hit=6
Planning Time: 0.041 ms
Execution Time: 0.059 ms
```

最初のレコードの`Index Scan using books_pkey`から、番号のIndexを使ったと分かります。`Index Cond`の条件は「400000以上、400010以下」です。図で4から8を取り出したのと同じように、400000の位置を見つけ、400010までを順にたどります。

実際に返した件数は、`actual time`の後の`rows=11.00`です。400000から400010までの11冊と対応します。11冊を取り出しても、実行時の`Buffers`は`shared hit=3 read=4`で、合計7回のアクセスで済んでいます。

では、1から900000までの90万冊ならどうでしょうか。同じ番号のIndexが使える状態で、条件だけを広げます。同じ`books_pkey`が使われるか、実行する前に予想してください。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM books WHERE id BETWEEN 1 AND 900000;
```

実行結果です。

```sql
Seq Scan on books  (cost=0.00..22353.00 rows=901290 width=30) (actual time=0.009..67.702 rows=900000.00 loops=1)
  Filter: ((id >= 1) AND (id <= 900000))
  Rows Removed by Filter: 100000
  Buffers: shared hit=5196 read=2157
Planning:
  Buffers: shared hit=2 read=2
Planning Time: 0.748 ms
Execution Time: 93.910 ms
```

今度は`Seq Scan`です。90万件を返し、条件に合わない10万件を除外しています。テーブルの100万件のうち、9割が必要になる検索です。

| 比較するもの | 11冊を探す | 90万冊を探す |
| --- | --- | --- |
| 選ばれた方法 | Index Scan（books_pkey） | Seq Scan |
| 実際の出力レコード数 | 11 | 900,000 |
| Execution Time | 0.059 ms | 93.910 ms |

### Indexがあっても、毎回使うわけではない

11冊を探すときは`books_pkey`を使い、90万冊を探すときはテーブルを順に読む方法が選ばれました。Indexを消したわけではありません。変えたのは、検索する番号の範囲です。

少数のレコードなら、Indexで場所を絞る方法が役立ちます。一方、テーブルの大部分が必要な場合は、テーブルを先頭から順に読むほうが有利だと見積もられることがあります。見積もりの中身は第10章で確かめます。

今回確かめられたのは、**Indexが残っていても、探す範囲によって選ばれる方法が変わった**ことです。11冊の検索と90万冊の検索は返す件数が違うため、この時間差で二つの方法の速さを直接は比べられません。方法を選ぶ仕組みは、第10章で調べます。

## 目録の順番と、棚の順番が違うとき

11冊と90万冊の間には、どんな探し方があるのでしょうか。今度は題名の範囲で探します。題名が「実験用の本 4」で始まる本、つまり「実験用の本 4」以上「実験用の本 5」未満の題名を持つ本をすべて取り出します。番号でいえば4、40〜49、400〜499、4000〜4999、40000〜49999、400000〜499999の本で、合わせて111,111冊です。100万冊の約1割にあたります。

11冊のときは`Index Scan`、90万冊のときは`Seq Scan`でした。題名のIndexは残っています。1割ならどちらが選ばれるか、実行する前に予想してください。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM books WHERE title >= '実験用の本 4' AND title < '実験用の本 5';
```

実行結果です。

```sql
Bitmap Heap Scan on books  (cost=3311.93..12314.92 rows=110000 width=30) (actual time=11.747..25.821 rows=111111.00 loops=1)
  Recheck Cond: ((title >= '実験用の本 4'::text) AND (title < '実験用の本 5'::text))
  Heap Blocks: exact=821
  Buffers: shared hit=1371
  ->  Bitmap Index Scan on books_title_idx  (cost=0.00..3284.43 rows=110000 width=0) (actual time=11.680..11.680 rows=111111.00 loops=1)
        Index Cond: ((title >= '実験用の本 4'::text) AND (title < '実験用の本 5'::text))
        Index Searches: 1
        Buffers: shared hit=550
Planning Time: 0.092 ms
Execution Time: 29.090 ms
```

どちらでもない、三つ目の方法が選ばれました。計画が2段になっています。下の`Bitmap Index Scan on books_title_idx`は、題名のIndexだけを読み、条件に合うレコードがテーブルのどのページにあるかを集めます。`rows=111111.00`は集めた場所の数で、`width=0`はレコードそのものを返していないことを表します。上の`Bitmap Heap Scan on books`が、集めた場所をもとにテーブルを読み、レコードを取り出します。`Heap Blocks: exact=821`が、テーブルから読んだページの数です。

### 目録の順に取りに行くと、同じページに何度も戻る

Indexで場所が分かるなら、11冊のときのように、そのまま1冊ずつ取りに行けばよさそうです。なぜ場所を集める段階を挟むのでしょうか。題名のIndexが、この範囲の本をどの順に並べているかを見てみます。`ORDER BY title`で題名の順に並べ、先頭の8冊だけを取り出します。

```sql
SELECT id, title FROM books
WHERE title >= '実験用の本 4' AND title < '実験用の本 5'
ORDER BY title LIMIT 8;
```

実行結果です。

```sql
   id   |       title
--------+-------------------
      4 | 実験用の本 4
     40 | 実験用の本 40
    400 | 実験用の本 400
   4000 | 実験用の本 4000
  40000 | 実験用の本 40000
 400000 | 実験用の本 400000
 400001 | 実験用の本 400001
 400002 | 実験用の本 400002
(8 rows)
```

題名は文字として並ぶので、「実験用の本 4」の次は「実験用の本 40」、その次は「実験用の本 400」です。番号でいえば4、40、400、4000、40000、400000と、桁が一つずつ増えていきます。この先も、400009の次に40001が来て、その次は400010に戻ります。

一方、テーブルのレコードは番号の順にページへ並んでいます（レコードがどのページにあるかは、第4章で`ctid`という値を使って確かめます）。番号40001のレコードはページ294に、番号400010のレコードはページ2941にありました。目録の順に1冊ずつ取りに行くと、ページ2941とページ294を行ったり来たりして、同じページを何度も開くことになります。

そこでPostgreSQLは、先に目録からレコードの場所を集め、ページごとにまとめてから、ページ番号の順にテーブルを読みます。今回の`exact`という方式では、ページ番号だけでなく、そのページの中のどのレコードを取り出すかも印で保持します。この、対象のレコード位置をまとめたものを**ビットマップ**と呼びます。

ビットマップを作る段階が`Bitmap Index Scan`、それを使ってテーブルを読む段階が`Bitmap Heap Scan`です。同じページにある対象レコードをまとめて取り出せるので、目録の順にページを行き来せずに済みます。図で、二つの読み方で開く回数がどう変わるかを見てください。

![目録の順に取りに行くとページ2941と294を行き来して5回開くが、ビットマップに集めてからならページ番号の順に2回で済む](/images/postgresql-query-journey/06-bitmap-scan.png)
*目録の5項目を取り出した例です。下のビットマップは、対象レコードの位置を数字で示しています。ページ番号とレコード位置は2026年9月25日に`ctid`で確認しました。ビット自体の配置は描かず、どの位置を覚えるかを説明するための図です。*

### 同じ11万冊を、ほかの方法で取り出すと

比べるために、この実験の間だけビットマップを候補から外し、同じSQLを実行します。設定で候補を減らすだけで、Indexを消すわけではありません。

```sql
SET enable_bitmapscan = off;
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM books WHERE title >= '実験用の本 4' AND title < '実験用の本 5';
```

実行結果です。

```sql
Index Scan using books_title_idx on books  (cost=0.42..14532.64 rows=110000 width=30) (actual time=0.571..16.464 rows=111111.00 loops=1)
  Index Cond: ((title >= '実験用の本 4'::text) AND (title < '実験用の本 5'::text))
  Index Searches: 1
  Buffers: shared hit=22395
Planning Time: 0.131 ms
Execution Time: 19.673 ms
```

`Index Scan`になり、`Buffers`は`shared hit=22395`です。この22,395回には、テーブルとIndexの両方へのアクセスが含まれます。ビットマップを使った計画の合計1,371回より多いことは分かりますが、この出力だけでは、テーブルへのアクセスとIndexへのアクセスを分けられません。テーブルの821ページだけを開き直した回数とは読まないでください。

さらに`Index Scan`も候補から外すと、`Seq Scan`になります。

```sql
SET enable_indexscan = off;
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM books WHERE title >= '実験用の本 4' AND title < '実験用の本 5';
```

実行結果です。

```sql
Seq Scan on books  (cost=0.00..22353.00 rows=110000 width=30) (actual time=0.039..1785.254 rows=111111.00 loops=1)
  Filter: ((title >= '実験用の本 4'::text) AND (title < '実験用の本 5'::text))
  Rows Removed by Filter: 888889
  Buffers: shared hit=2583 read=4770
Planning Time: 0.083 ms
Execution Time: 1788.428 ms
```

設定を元に戻しておきます。

```sql
RESET enable_bitmapscan;
RESET enable_indexscan;
```

実行結果です。

```sql
RESET
RESET
```

| 比較するもの | Seq Scan | Index Scan | Bitmap Index ScanとBitmap Heap Scan |
| --- | --- | --- | --- |
| 返したレコード | 111,111 | 111,111 | 111,111 |
| Rows Removed by Filter | 888,889 | 表示なし | 表示なし |
| 実行時のページへのアクセス回数 | 7,353 | 22,395 | 1,371（テーブル821、Index550） |
| Execution Time | 1788.428 ms | 19.673 ms | 29.090 ms |

同じ111,111件を返すのに、ページへのアクセス回数は三つとも違います。`Seq Scan`は7,353ページを全部読み、9割近いレコードを除外しました。`Index Scan`は除外するレコードこそありませんが、テーブルとIndexを合わせて22,395回ページにアクセスしました。ビットマップを使う方法は、テーブルのページを821回、つまり1ページにつき一度ずつ読み、Indexのページを550回読みました。

文字列の範囲を比べる処理は、題名が等しいかだけを調べる処理と同じ負担ではありません。並び順の比較にはロケールも関わり、[C/POSIX以外の照合順序では比較が高コストになりうる](https://www.postgresql.org/docs/18/locale.html)と公式文書でも説明されています。ここでの約1.8秒を、一点検索のSeq Scanの時間と直接比べてキャッシュの差とは判断できません。今回、比較処理だけの時間は切り分けて測っていません。

実行時間は、今回は`Index Scan`がいちばん短くなりました。ただし、`Index Scan`もビットマップの計画も、アクセスはすべて`hit`です。「メモリにあったから」だけでは、二つの時間差を説明しきれません。ビットマップを組み立てる処理や、実行順による状態の違いなども関わりうるため、この各1回の結果だけで原因を決めないでください。

一方、実行前の`cost`はビットマップの方法が小さくなっています（12314.92と14532.64）。PostgreSQLは、ページを読む処理やレコードを比べる処理などの見積もりに基づいて方法を選びます。その見積もりが、今回の実行時間の順と一致しなかった、と読みます。見積もりの仕組みは第10章で、`hit`と`read`の違いは第5章で確かめます。

:::details Recheck Condという表示について
ビットマップは、処理ごとの作業用メモリに置きます。収まらなくなると、一部のページについてレコードの位置を省き、「このページのどこか」という粗い形に切り替えることがあります。この`lossy`という方式では、ページごとに1ビットの印を持ち、テーブルを読んだ後で条件に合うレコードかを確かめ直します。その確かめ直しに使う条件が`Recheck Cond`です。今回は`Heap Blocks: exact=821`で、すべてレコードの位置まで持てていました。粗い形になったページがあると、`lossy=`の数が並びます。作業用メモリの大きさは第7章で変えて観察します。
:::

## Indexにも保存容量と更新の負担がある

Indexの大きさも測れます。

```sql
SELECT pg_size_pretty(pg_relation_size('books_title_idx'));
```

実行結果です。

```sql
 pg_size_pretty
----------------
 39 MB
(1 row)
```

今回の題名用のIndexは、テーブルとは別に39 MBの保存領域を使っていました。これはIndexの格納領域の大きさで、1回の検索で39 MBすべてを読むという意味ではありません。

保存容量に加えて、更新の負担もあります。本を1冊増やすなら、テーブルだけでなく目録にも書き足す必要があります。題名を変更するなら、題名のIndexも書き換える必要があります。Indexのページがいっぱいなら、分割などの調整も必要になります。毎回分割するわけではありませんが、レコードを追加したり、Indexの列を更新したりすると、Indexのページも書き換えが必要になります。

Indexを作るかどうかは、読み込みが減る利益と、保存容量や、追加や更新の負担を合わせて考えて決めます。仕組みをさらに調べる入口は[PostgreSQLのIndexの説明](https://www.postgresql.org/docs/18/indexes.html)です。

## 確かめる問い

「1件検索が速くなったので、90万件を取り出すSQLも同じ倍率で速くなる」と言ってよいでしょうか。

:::details 考え方
木をたどって場所を絞る段階と、その後に多くのレコードをテーブルから取り出す段階は、読むページの数が別に決まります。対象範囲を変え、計画とアクセス量を測って確かめます。
:::

題名のIndexは後の章でも使うので残します。

アクセス回数はページ単位だと書きましたが、そのページはテーブルのどこに、どんな大きさで保存されているのでしょうか。次章ではテーブルの保存先を調べ、レコードをまとめて扱うページと対応させます。
