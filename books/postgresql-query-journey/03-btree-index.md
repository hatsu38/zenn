## この章で分かること

Indexにも100万冊分の情報があるのに、なぜ全件を調べずに探せるのでしょうか。番号1〜9の図で、範囲を絞って探す仕組みを確かめます。その後、題名のIndexを作って同じ検索を比べ、探す範囲を広げると選ばれる方法がどう変わるかを観察します。

## 目録も大きいのに、どう探す？

ここまで、100万冊から1冊を探してきました。題名を順番に比べると、多くの行を読む必要があります。一方、番号検索はIndexという目録を使えました。

でも、Indexにも100万冊分の情報があるはずです。Indexを先頭から全部読んでいたら、あまり助けにならなそうです。

![目録も大きい。それでも速い？](/images/postgresql-query-journey/06-catalog-question.png)
*学ぶきっかけを描く、説明用の場面。目録そのものも100万冊分あります。*

## 番号の範囲から、探す先を選ぶ

番号1〜9を、順番に三つの箱へ分けます。左の箱に1、2、3、真ん中に4、5、6、右に7、8、9を入れました。

三つの箱の上に案内板を一枚立て、箱の境目となる4と7を書いておきます。探したい番号が8なら、どの箱を開けばよいでしょうか。

![8は7以上なので右の箱へ進み、その箱の中で8を見つける](/images/postgresql-query-journey/06-btree-path.png)
*番号1〜9で説明するための図です。矢印は探索で進む向きです。*

8は7以上なので、右の箱へ進みます。その中から8を見つければよく、左と真ん中の箱を開く必要はありません。

PostgreSQLの**B-tree Index**は、値の範囲で進む先を選ぶこの構造を使っています。案内板から行き先が枝分かれする形を、木に見立てています。入口の案内板を**根**、末端の箱を**葉**と呼びます。大きなIndexでは、根と葉の間にも案内板が入ります。

実際のIndexでは、案内板も箱も「ページ」というデータのまとまりです。葉のページには、探す値と、表のどこに行があるかという情報が入っています。ページの大きさと行の場所は、第4章で調べます。いまは「案内板で範囲を絞り、必要な箱だけを読む」という動きを押さえてください。

## 冊数が増えると、案内板の段数はどう増えるか

仮に一枚の案内板に100個の行き先が書けるなら、案内板が1段で100個、2段で100×100＝1万個の箱へ行き先を分けられます。箱に100冊ずつ入るなら、案内板2段と葉の箱を合わせた3段で100万冊に届きます。100は増え方をつかむために仮に置いた数で、3段はその仮定から計算した結果です。実際のIndexの分岐数を測った値ではありません。

案内板を1段増やすと分けられる範囲が100倍になるので、冊数が100倍に増えるまで段は増えません。件数が掛け算で増えても、段数は1段ずつしか増えません。この増え方を`O(log n)`と表します。実際の題名のIndexが何段だったかは、第4章で確かめます。

`log`を初めて見ても、まずは**100万件でも、読む案内板は根から葉までの数枚で済む**と理解できれば十分です。ただし、案内板をたどった後に表から取り出す行が多ければ、その行を読む仕事は別にかかります。

## 題名にもIndexを作る

第1章で用意した100万冊をそのまま使います。Indexを作る前に、題名検索を記録してください。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM books WHERE title = '実験用の本 42';
```

今回、Indexを作る前の結果は次のとおりでした。

```sql
Seq Scan on books  (cost=0.00..19852.99 rows=1 width=30) (actual time=0.110..81.524 rows=1.00 loops=1)
  Filter: (title = '実験用の本 42'::text)
  Rows Removed by Filter: 999999
  Buffers: shared hit=7353
Planning Time: 0.510 ms
Execution Time: 81.675 ms
```

第1章と同じく、100万行に条件を当てています。第2章の`LIMIT 1`とは違い、今回は条件に合う行をすべて求める検索です。今回は`Buffers`が`shared hit=7353`で、すべて`hit`になっています。この数は次章で使うので覚えておいてください。

続いて題名用のIndexを作り、統計情報を更新します。

```sql
CREATE INDEX books_title_idx ON books (title);
ANALYZE books;
```

実行結果です。

```sql
CREATE INDEX
ANALYZE
```

同じ題名検索を、もう一度実行します。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM books WHERE title = '実験用の本 42';
```

Indexを作った後の実行結果です。

```sql
Index Scan using books_title_idx on books  (cost=0.42..8.44 rows=1 width=30) (actual time=0.145..0.146 rows=1.00 loops=1)
  Index Cond: (title = '実験用の本 42'::text)
  Index Searches: 1
  Buffers: shared hit=1 read=3
Planning:
  Buffers: shared hit=8 read=1
Planning Time: 0.631 ms
Execution Time: 0.191 ms
```

今度は`Index Scan using books_title_idx`になりました。作った題名のIndexを使っています。さっきの`Filter`に代わり、`Index Cond`に題名の条件が出ていることも確認できます。

| 比較するもの | Indexを作る前 | Indexを作った後 |
| --- | --- | --- |
| 探す方法 | Seq Scan | Index Scan |
| 返した行 | 1行 | 1行 |
| Rows Removed by Filter | 999,999行 | 表示なし |
| 実行時のshared hit | 7,353 | 1 |
| 実行時のshared read | 表示なし | 3 |
| Execution Time | 81.675 ms | 0.191 ms |

### 同じ1行を、別の方法で探している

Indexを作る前は、100万行の題名を順に比べ、999,999行を除外していました。作った後は、`Index Cond`に書かれた題名を使い、Indexから行の場所を探しています。返す本は同じでも、そこにたどり着く方法が変わりました。

読む量の違いは、`Buffers`にも表れています。検索の実行中の値を比べると、7,353回から、`hit=1`と`read=3`を合わせた4回へ減っています。これは行数ではなく、**ページにアクセスした回数**です。`Planning`の下の値は計画を作るときのアクセスなので、ここには足しません。この1回が何を数えたものかは、次章で確かめます。

実行時間も81.675 msから0.191 msへ短くなりました。今回の出力では、時間だけでなく、探す方法とアクセス回数にも変化があります。何倍速くなるかは実行する環境や状態で変わるため、まずはこの三つを対応させて読んでください。

:::details Index Searchesという表示について
`Index Searches: 1`は、Indexの探索を1回行ったことを示します。その1回の探索で、根から葉まで複数のページを使うことがあります。1ページだけ読んだという意味ではありません。`hit`と`read`の違いは第5章で説明します。
:::

## 一点を探した後に、たくさん読む場合

次は、範囲を指定して4以上8以下を取り出す場合です。

![4以上8以下なら、隣の葉も読む](/images/postgresql-query-journey/06-range-scan.png)
*Indexの葉をたどる様子を単純にした図です。表への参照は省略しています。*

まず4がある場所を探し、4、5、6、7、8と順に取り出します。途中で箱の終わりに来たら、隣の箱へ進みます。1冊の場所を見つけたときとは違い、範囲に入る冊数が増えるほど、その後に取り出す行も増えます。

今度は番号の範囲で探します。条件が番号なので、使えるのは主キーの番号用のIndexである`books_pkey`です。題名用の`books_title_idx`は、題名の条件にしか使えません。

まず、400000から400010までの11冊を探します。`BETWEEN`は両端の値を含みます。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM books WHERE id BETWEEN 400000 AND 400010;
```

実行結果です。

```sql
Index Scan using books_pkey on books  (cost=0.42..8.64 rows=11 width=30) (actual time=0.062..0.065 rows=11.00 loops=1)
  Index Cond: ((id >= 400000) AND (id <= 400010))
  Index Searches: 1
  Buffers: shared hit=7
Planning:
  Buffers: shared hit=6
Planning Time: 0.272 ms
Execution Time: 0.087 ms
```

最初の行の`Index Scan using books_pkey`から、番号のIndexを使ったと分かります。`Index Cond`の条件は「400000以上、400010以下」です。図で4から8を取り出したのと同じように、400000の位置を見つけ、400010までを順にたどります。

実際に返した件数は、`actual time`の後の`rows=11.00`です。400000から400010までの11冊と対応します。11冊を取り出しても、実行時の`Buffers`は`shared hit=7`で、7回のアクセスで済んでいます。

では、1から900000までの90万冊ならどうでしょうか。同じ番号のIndexが使える状態で、条件だけを広げます。同じ`books_pkey`が使われるか、実行する前に予想してください。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM books WHERE id BETWEEN 1 AND 900000;
```

実行結果です。

```sql
Seq Scan on books  (cost=0.00..22353.00 rows=902218 width=30) (actual time=0.014..65.590 rows=900000.00 loops=1)
  Filter: ((id >= 1) AND (id <= 900000))
  Rows Removed by Filter: 100000
  Buffers: shared hit=7353
Planning:
  Buffers: shared hit=4
Planning Time: 0.093 ms
Execution Time: 93.493 ms
```

今度は`Seq Scan`です。90万行を返し、条件に合わない10万行を除外しています。表の100万行のうち、9割が必要になる検索です。

| 比較するもの | 11冊を探す | 90万冊を探す |
| --- | --- | --- |
| 選ばれた方法 | Index Scan（books_pkey） | Seq Scan |
| 実際の出力行数 | 11 | 900,000 |
| Execution Time | 0.087 ms | 93.493 ms |

### Indexがあっても、毎回使うわけではない

11冊を探すときは`books_pkey`を使い、90万冊を探すときは表を順に読む方法が選ばれました。Indexを消したわけではありません。変えたのは、検索する番号の範囲です。

少数の行なら、Indexで場所を絞る方法が役立ちます。一方、表の大部分が必要な場合は、表を先頭から順に読むほうが有利だと見積もられることがあります。見積もりの中身は第10章で確かめます。

今回確かめられたのは、**Indexが残っていても、探す範囲によって選ばれる方法が変わった**ことです。11冊の検索と90万冊の検索は返す件数が違うため、この時間差で二つの方法の速さを直接は比べられません。方法を選ぶ仕組みは、第10章で調べます。

## Indexにも保存容量と更新の負担がある

Indexの大きさも測れます。

```sql
SELECT pg_size_pretty(pg_relation_size('books_title_idx'));
```

実行結果です。

```sql
 pg_size_pretty
----------------
 39 MB
(1 row)
```

今回の題名用のIndexは、表とは別に39 MBの保存領域を使っていました。これはIndexの格納領域の大きさで、1回の検索で39 MBすべてを読むという意味ではありません。

保存容量に加えて、更新の負担もあります。本を1冊増やすなら、表だけでなく目録にも書き足す必要があります。題名を変更するなら、題名のIndexも書き換える必要があります。Indexのページがいっぱいなら、分割などの調整も必要になります。毎回分割するわけではありませんが、行を追加したり、Indexの列を更新したりすると、Indexのページも書き換えが必要になります。

Indexを作るかどうかは、読み込みが減る利益と、保存容量や、追加や更新の負担を合わせて考えて決めます。仕組みをさらに調べる入口は[PostgreSQLのIndexの説明](https://www.postgresql.org/docs/18/indexes.html)です。

## 確かめる問い

「1件検索が速くなったので、90万件を取り出すSQLも同じ倍率で速くなる」と言ってよいでしょうか。

:::details 考え方
木をたどって場所を絞る段階と、その後に多くの行を表から取り出す段階は、読むページの数が別に決まります。対象範囲を変え、計画とアクセス量を測って確かめます。
:::

題名のIndexは後の章でも使うので残します。

アクセス回数はページ単位だと書きましたが、そのページは表のどこに、どんな大きさで保存されているのでしょうか。次章では表の保存先を調べ、行をまとめて扱うページと対応させます。
