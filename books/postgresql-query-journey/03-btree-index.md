## この章で分かること

Indexにも100万冊分の情報があるのに、なぜ全件を調べずに探せるのでしょうか。番号1〜9の図で、範囲を絞って探す仕組みを確かめます。その後、題名のIndexを作って同じ検索を比べ、探す範囲を広げると選ばれる方法がどう変わるかを観察します。最後に、Indexが使う保存容量と、追加や更新のたびにかかる負担を測ります。

:::

## 目録も大きいのに、どう探す？

ここまで、100万冊から1冊を探してきました。題名を順番に比べると、多くのレコードを読む必要があります。一方、番号検索はIndexという目録を使えました。

でも、Indexにも100万冊分の情報があるはずです。Indexを先頭から全部読んでいたら、あまり助けにならなそうです。

![本100万冊の棚と同じ長さで、Indexの目録にも100万件が並ぶ](/images/postgresql-query-journey/06-catalog-question.png)
*本の棚と同じ長さで並ぶ、目録の100万件を見てください（説明するための図）。*

## 番号の範囲から、探す先を選ぶ

番号1〜9を、順番に三つの箱へ分けます。左の箱に1、2、3、真ん中に4、5、6、右に7、8、9を入れました。

三つの箱の上に案内板を一枚立て、箱の境目となる4と7を書いておきます。探したい番号が8なら、どの箱を開けばよいでしょうか。

![案内板の境目4と7を見て、8は7以上なので右の箱だけを開き、その中で8を見つける。箱の番号にはテーブルの場所の札が付いていて、左と真ん中の箱は開かない](/images/postgresql-query-journey/06-btree-path.png)
*開くのは右の箱だけで、×を付けた二つの箱は開きません。番号の横の「▸ 場所」は、テーブルのレコードの場所です（番号1〜9で説明するための図）。*

8は7以上なので、右の箱へ進みます。その中から8を見つければよく、左と真ん中の箱を開く必要はありません。

PostgreSQLの**B-tree Index**は、値の範囲で進む先を選ぶこの構造を使っています。案内板から行き先が枝分かれする形を、木に見立てています。入口の案内板を**根**、末端の箱を**葉**と呼びます。大きなIndexでは、根と葉の間にも案内板が入ります。

そのときも比べ方は同じです。根の案内板の境目と比べて途中の案内板を一つ選び、その案内板の境目と比べて箱を一つ選びます。段が増えても、1段ごとに1枚の案内板を見て、次に進む先を一つ選ぶことを繰り返します。

番号1〜27を九つの箱に分けた例で、8を探す道すじをたどってください。

![根の案内板で10未満なので左の案内板を選び、その案内板で7以上なので右の箱を選び、箱の中で8と、そのテーブルの場所を見つける。ほかの二つの案内板と八つの箱は読まない](/images/postgresql-query-journey/06-two-level-path.png)
*読むのは太枠の案内板2枚と箱1個だけで、細い枠の案内板と箱は読みません。③の「▸ 場所」は、前の図と同じく、テーブルのレコードの場所です（番号1〜27で説明するための図）。*

実際のIndexでは、案内板も箱も「ページ」というデータのまとまりです。葉のページには、探す値と、テーブルのどこにレコードがあるかという情報が入っています。第1章の図で、Indexの項目42から本42のレコードへ伸びていた矢印は、この情報をたどったものです。ページの大きさとレコードの場所は、第4章で調べます。いまは「案内板で範囲を絞り、必要な箱だけを読む」という動きを押さえてください。

## 冊数が増えると、案内板の段数はどう増えるか

仮に一枚の案内板に100個の行き先が書けるなら、案内板が1段で100個、2段で100×100＝1万個の箱へ行き先を分けられます。箱に100冊ずつ入るなら、案内板2段と葉の箱を合わせた3段で100万冊に届きます。100は増え方をつかむために仮に置いた数で、3段はその仮定から計算した結果です。実際のIndexの分岐数を測った値ではありません。

案内板を1段増やすと分けられる範囲が100倍になるので、冊数が100倍に増えるまで段は増えません。件数が掛け算で増えても、B-treeの段数は1段ずつしか増えません。この増え方を`O(log n)`と表します。実際の題名のIndexが何段だったかは、第4章で確かめます。

図で、各段で1枚ずつ読んだ合計と、全部を読んだときの枚数を比べてください。

![案内板1枚、案内板100枚、箱1万個の3段から、各段1枚ずつ合わせて3枚だけをたどる。全部なら10,101枚で、1億冊でも4段で4枚になる](/images/postgresql-query-journey/06-tree-levels.png)
*各段で1枚ずつ、合わせて3枚だけを読みます。全部を読むと10,101枚です（説明するための図。1枚の案内板に100個の行き先が書けると仮に置いています）。*

`log`を初めて見ても、まずは**100万件でも、たどるのは数枚の案内板と箱一つで済む**と理解できれば十分です。ただし、案内板をたどった後にテーブルから取り出すレコードが多ければ、そのレコードを読む仕事は別にかかります。

## 題名にもIndexを作る

「準備」の章で用意した100万冊をそのまま使います。Indexを作る前に、題名検索を記録してください。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM books WHERE title = '実験用の本 42';
```

2026年9月25日、PostgreSQL 18.6の新規DBで「準備」の章のデータを用意し、第2章に続けて実行した結果です。並列実行とJITは無効です。この節と次の番号の範囲検索は、同じ通し実行から掲載しています。

```sql:実行結果
Seq Scan on books  (cost=0.00..19853.00 rows=1 width=30) (actual time=0.010..38.387 rows=1.00 loops=1)
  Filter: (title = '実験用の本 42'::text)
  Rows Removed by Filter: 999999
  Buffers: shared hit=4657 read=2696 written=94
…
Execution Time: 38.405 ms
```

第1章と同じく、100万件に条件を当てています。第2章の`LIMIT 1`とは違い、今回は条件に合うレコードをすべて求める検索です。今回は`Buffers`の`shared hit=4657`と`read=2696`を合わせて7,353回です[^written]。7,353という数は次章で使うので覚えておいてください。

[^written]: `written=94`は、この検索を実行した接続が、前の処理で変更されたままのページをディスクへ書き出した数です。読み取りの7,353回へは足しません。

続いて題名用のIndexを作り、統計情報を更新します。種類を指定せずに作ったIndexは、B-treeになります。

```sql
CREATE INDEX books_title_idx ON books (title);
ANALYZE books;
```

`ANALYZE`は、テーブルから一部のレコードを抜き出して統計情報を作ります[^analyze-sample]。そのため、このあとの出力の見積もり（`cost`や、`actual`より前の`rows`）は、あなたの結果と少し違うことがあります。統計情報は第10章で扱います。

[^analyze-sample]: 大きなテーブルでは一部を抜き出して調べるため、統計情報は実行のたびに少し変わり、EXPLAINの見積もりも少し変わりえます。[PostgreSQLの公式ドキュメントのANALYZEの説明](https://www.postgresql.org/docs/18/sql-analyze.html)の「Notes」に書かれています。

同じ題名検索を、もう一度実行します。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM books WHERE title = '実験用の本 42';
```

Indexを作った後の実行結果です。

```sql:実行結果
Index Scan using books_title_idx on books  (cost=0.42..8.44 rows=1 width=30) (actual time=0.053..0.054 rows=1.00 loops=1)
  Index Cond: (title = '実験用の本 42'::text)
  Index Searches: 1
  Buffers: shared hit=1 read=3
Planning:
  Buffers: shared hit=8 read=1
…
Execution Time: 0.067 ms
```

今度は`Index Scan using books_title_idx`になりました。作った題名のIndexを使っています。さっきの`Filter`に代わり、`Index Cond`に題名の条件が出ていることも確認できます。

| 比較するもの | Indexを作る前 | Indexを作った後 |
| --- | --- | --- |
| 探す方法 | Seq Scan | Index Scan |
| 返したレコード | 1件 | 1件 |
| Rows Removed by Filter | 999,999件 | 表示なし |
| 実行時のshared hit | 4,657 | 1 |
| 実行時のshared read | 2,696 | 3 |
| Execution Time | 38.405 ms | 0.067 ms |

### 同じ1件を、別の方法で探している

Indexを作る前は、100万件の題名を順に比べ、999,999件を除外していました。作った後は、`Index Cond`に書かれた題名を使い、Indexからレコードの場所を探しています。返す本は同じでも、そこにたどり着く方法が変わりました。

読む量の違いは、`Buffers`にも表れています。検索の実行中の値を比べると、7,353回から、`hit=1`と`read=3`を合わせた4回へ減っています。これはレコード数ではなく、**ページにアクセスした回数**です。`Planning`の下の値は計画を作るときのアクセスなので、ここには足しません。この1回が何を数えたものかは、次章で確かめます。

実行時間も38.405 msから0.067 msへ短くなりました。今回の出力では、時間だけでなく、探す方法とアクセス回数にも変化があります。何倍速くなるかは実行する環境や状態で変わるため、まずはこの三つを対応させて読んでください。

:::details Index Searchesという表示について
`Index Searches: 1`は、Indexの探索を1回行ったことを示します。その1回の探索で、B-treeの根から葉まで複数のページを使うことがあります。1ページだけ読んだという意味ではありません。`hit`と`read`の違いは第5章で説明します。
:::

## 一点を探した後に、たくさん読む場合

次は、範囲を指定して4以上8以下を取り出す場合です。

![案内板から4のある真ん中の箱へ進み、4・5・6の後は案内板へ戻らずに隣の右の箱へ移って7と8を見つけ、範囲外の9で止まる。見つけた番号の場所から、テーブルのレコード5件を取り出す](/images/postgresql-query-journey/06-range-scan.png)
*真ん中の箱から右の箱へは、案内板を通らずに進みます。探すのは1回で、開く箱は2個、テーブルから取り出すレコードは5件です（番号1〜9で説明するための図）。*

まず4がある場所を探し、4、5、6、7、8と順に取り出します。途中で箱の終わりに来たら、隣の箱へ進みます。案内板まで戻らずに隣へ進めるのは、B-treeの葉の箱が、隣の箱の場所を覚えているからです[^leaf-link]。1冊の場所を見つけたときとは違い、範囲に入る冊数が増えるほど、その後に取り出すレコードも増えます。

[^leaf-link]: [B-treeの構造の公式説明](https://www.postgresql.org/docs/18/btree.html)に、木の各段は「a doubly-linked list of pages」（両隣とつながったページの並び）として使えると書かれています。

今度は番号の範囲で探します。条件が番号なので、使えるのは主キーの番号用のIndexである`books_pkey`です。題名用の`books_title_idx`は、題名の条件にしか使えません。

まず、400000から400010までの11冊を探します。`BETWEEN`は両端の値を含みます。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM books WHERE id BETWEEN 400000 AND 400010;
```

実行結果です。

```sql:実行結果
Index Scan using books_pkey on books  (cost=0.42..8.64 rows=11 width=30) (actual time=0.053..0.054 rows=11.00 loops=1)
  Index Cond: ((id >= 400000) AND (id <= 400010))
  …
  Buffers: shared hit=3 read=4
…
Execution Time: 0.059 ms
```

最初のレコードの`Index Scan using books_pkey`から、番号のIndexを使ったと分かります。`Index Cond`の条件は「400000以上、400010以下」です。図で4から8を取り出したのと同じように、400000の位置を見つけ、400010までを順にたどります。

実際に返した件数は、`actual time`の後の`rows=11.00`です。400000から400010までの11冊と対応します。11冊を取り出しても、実行時の`Buffers`は`shared hit=3 read=4`で、合計7回のアクセスで済んでいます[^pkey-first]。

[^pkey-first]: 接続して初めてこのIndexを使うときは、アクセスが数回多くなることがあります。同じ接続で先に`books_pkey`を使っていれば、合計4回になることもあります。

では、1から900000までの90万冊ならどうでしょうか。同じ番号のIndexが使える状態で、条件だけを広げます。同じ`books_pkey`が使われるか、実行する前に予想してください。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM books WHERE id BETWEEN 1 AND 900000;
```

実行結果です。

```sql:実行結果
Seq Scan on books  (cost=0.00..22353.00 rows=901290 width=30) (actual time=0.009..67.702 rows=900000.00 loops=1)
  …
  Rows Removed by Filter: 100000
  …
Execution Time: 93.910 ms
```

今度は`Seq Scan`です。90万件を返し、条件に合わない10万件を除外しています。テーブルの100万件のうち、9割が必要になる検索です。

| 比較するもの | 11冊を探す | 90万冊を探す |
| --- | --- | --- |
| 選ばれた方法 | Index Scan（books_pkey） | Seq Scan |
| 実際の出力レコード数 | 11 | 900,000 |
| Execution Time | 0.059 ms | 93.910 ms |

:::details actual timeとExecution Timeの差
`actual time`の終わりは67.702 msですが、`Execution Time`は93.910 msで、約26 ms長くなっています。`actual time`はこの処理の中でかかった時間で、処理から出てきた90万件を受け取る側の時間は入りません。`Execution Time`にはその時間も入るので、返すレコードが多いと差が開きます。1件を返した第1章の題名検索では、35.994 msと36.037 msで、差はほとんどありませんでした。
:::

### Indexがあっても、毎回使うわけではない

11冊を探すときは`books_pkey`を使い、90万冊を探すときはテーブルを順に読む方法が選ばれました。Indexを消したわけではありません。変えたのは、検索する番号の範囲です。

範囲の図で見たとおり、`Index Scan`は、Indexで見つけた1件ごとに、テーブルからレコードを取り出しに行きます。11冊なら取り出しに行くのは11回ですが、90万冊を同じ方法で取り出すなら90万回になります。少数のレコードなら、Indexで場所を絞る方法が役立ちます。一方、テーブルの大部分が必要な場合は、Indexをたどって1件ずつ取り出しに行くより、テーブルを先頭から順に読むほうが有利だと見積もられることがあります。

今回確かめられたのは、**Indexが残っていても、探す範囲によって選ばれる方法が変わった**ことです。11冊の検索と90万冊の検索は返す件数が違うため、この時間差で二つの方法の速さを直接は比べられません。方法を選ぶ見積もりの中身は、第10章で調べます。

11冊と90万冊の間の件数では、`Index Scan`でも`Seq Scan`でもない読み方が選ばれることがあります。この読み方は、テーブルのページと共有バッファを調べてから、第5章で観察します。

Indexがあっても使われない例は、ほかにもあります。条件の列を関数で包んだ場合と、前方一致の`LIKE`は、付録「自分の遅いSQLを調べる」のよくある遅い書き方で確かめます。

## Indexにも保存容量と更新の負担がある

Indexの大きさも測れます。

```sql
SELECT pg_size_pretty(pg_relation_size('books_title_idx'));
```

実行結果です。

```sql:実行結果
 pg_size_pretty
----------------
 39 MB
(1 row)
```

今回の題名用のIndexは、テーブルとは別に39 MBの保存領域を使っていました。これはIndexの格納領域の大きさで、1回の検索で39 MBすべてを読むという意味ではありません。

保存容量に加えて、更新の負担もあります。本を1冊増やすなら、テーブルだけでなく目録にも書き足す必要があります。題名を変更するなら、題名のIndexも書き換える必要があります。Indexのページがいっぱいなら、分割などの調整も必要になります。毎回分割するわけではありませんが、レコードを追加したり、Indexの列を更新したりすると、Indexのページも書き換えが必要になります。

どれくらい重くなるかを、読了記録と同じ形の空のテーブルに10万件を追加して比べました。2026年9月28日に3回ずつ測った中央値です。追加する10万件は`reading_records`から読んでいるので、その時間も三つに同じだけ含まれます。

| テーブルのIndex | 10万件の追加にかかった時間 | 変更の記録（WAL、第11章）の量 |
| --- | ---: | ---: |
| なし | 62.8 ms | 7.1 MB |
| 1本 | 184.9 ms | 16.4 MB |
| 2本 | 328.3 ms | 25.5 MB |

Indexが1本増えるごとに、追加の時間も、書く量も増えました。読み取りを速くするIndexは、書き込みのたびに払う費用と引き換えです。

Indexを作るかどうかは、読み込みが減る利益と、保存容量や、追加や更新の負担を合わせて考えて決めます。仕組みをさらに調べる入口は[PostgreSQLのIndexの説明](https://www.postgresql.org/docs/18/indexes.html)です。

## 考えてみよう

「1件検索が速くなったので、90万件を取り出すSQLも同じ倍率で速くなる」と言ってよいでしょうか。

:::details 考え方
B-treeをたどって場所を絞る段階と、その後に多くのレコードをテーブルから取り出す段階は、読むページの数が別に決まります。対象範囲を変え、計画とアクセス量を測って確かめます。
:::

題名のIndexは後の章でも使うので残します。

## まとめ

- B-treeは、並んだ値を上から絞り込むので、100万件の中の1件にも数ページで届く。
- 条件に合うレコードが多いと、Indexからテーブルを読みに行く回数が増える。テーブルの大部分が必要なときは、Indexがあっても`Seq Scan`が選ばれる。
- Indexには、保存容量と、追加や更新のたびに書き換える負担がある。

## 第4章へ

アクセス回数はページ単位だと書きましたが、そのページはテーブルのどこに、どんな大きさで保存されているのでしょうか。次章ではテーブルの保存先を調べ、レコードをまとめて扱うページと対応させます。
