## この章で分かること

SQLの表は、物理的にはファイルやページに保存されています。表のサイズや行の位置を観察し、行数、ページ数、バイト数を別々の量として捉えます。索引から表を参照する関係や、長い値を保存する仕組みも紹介します。同じ件数でも読み込み量が違う理由を説明するための土台を作る章です。

## 7,353回は、何を数えた回数？

第3章では、題名の索引を作ると、実行時のバッファアクセスが7,353回から4回に減りました。では、この「1回」は何を1個と数えた回数なのでしょうか。

行の数ではなさそうです。索引を作る前の検索は100万行に条件を当てていましたが、アクセスは7,353回でした。1行につき1回と数えるなら、100万回近くになるはずです。

そこで、PostgreSQLは行より大きなまとまりでデータを扱っている、と考えてみます。そのまとまりを知るために、まず表がどんな形で保存されているかを調べます。たとえば本が1,000冊なら、コンピュータの中には1,000個の小さなファイルがあるのでしょうか。

![本の一覧は、どこに保存される？](/images/postgresql-query-journey/03-storage-question.png)
*学ぶきっかけを描く、説明用の場面。*

何を単位に読んでいるかを調べるため、まず1,000冊の小さな観察用の表を用意します。小さな表で単位を確かめてから、100万冊の表に戻って7,353回と対応させます。

## この章だけの小さな表を用意する

第1章で用意し、第3章で索引を追加した`public.books`（100万冊、題名索引あり）は残します。同じDBの中に、表をまとめる別の区画（スキーマ）を作り、そこに1,000冊で主キーのみの通常の表を作ります[^temp]。

[^temp]: 接続内だけで使う一時テーブルという作り方もありますが、そのページは接続ごとの領域に置かれ、共有バッファには入りません。第5章で`shared hit`を観察するため、ここでは通常の表を使います。

この章では、**トランザクション**を使います。トランザクションは、いくつかの操作をひとまとめにして、最後に確定する（`COMMIT`）か、全部取り消す（`ROLLBACK`）かを選べる仕組みです。`BEGIN`で開始して開いたまま観察を続け、章末の`ROLLBACK`で観察用のスキーマと表を取り消します。元の`public.books`は変更しません。

次の操作は、この章を試すpsqlで行います。`book_observation`はこの実験専用の名前です。同じ名前のスキーマが既にある場合は、それを削除しないでください。SQL中の`book_observation`をすべて別の名前に書き換えてから実行します。

```sql
BEGIN;
CREATE SCHEMA book_observation;
CREATE TABLE book_observation.books
  (LIKE public.books INCLUDING DEFAULTS INCLUDING CONSTRAINTS);
ALTER TABLE book_observation.books ADD PRIMARY KEY (id);
INSERT INTO book_observation.books
SELECT id, title FROM public.books WHERE id BETWEEN 1 AND 1000;
SET LOCAL search_path = book_observation, public;
ANALYZE books;
SELECT count(*) FROM books;
```

準備SQLの実行結果です。2026年9月23日に共有された実行結果から、入力SQLとpsqlのプロンプトを除いて掲載しています。

```sql
BEGIN
CREATE SCHEMA
CREATE TABLE
ALTER TABLE
INSERT 0 1000
SET
ANALYZE
 count
-------
  1000
(1 row)
```

`INSERT 0 1000`は1,000行を追加したことを示し、最後の`count`でも観察用の表に1,000行あると確認できます。`SET LOCAL search_path`によって、このトランザクション内では、`books`という名前で観察用の表を参照します。

:::details プロンプトの`*`について
この時点で、psqlのプロンプトは`reading_map=*#`に変わります。`*`は、トランザクションの途中であることを示す印です。そのまま次の観察へ進んでください。章末で`ROLLBACK`すると、観察用のスキーマと表が取り消され、`SET LOCAL`の設定も元に戻ります。
:::

## 表の保存先と大きさを調べる

この節の三つの出力（保存先、大きさ、`block_size`）は、以前の原稿で本1,000冊の通常テーブルを観察したときの実測例です。自分の環境では、パスや容量が違うことがあります。

### 表の保存先のパス

```sql
SELECT pg_relation_filepath('books');
```

実行結果です。

```sql
 pg_relation_filepath
----------------------
 base/16384/16385
(1 row)
```

`books`という表名に対して、`base/16384/16385`というパスが返ってきました。これはPostgreSQLのデータディレクトリを基準にした相対パスです。今回ならDocker内のDBサーバ側の場所で、手元のパソコンに同じパスがあるという意味ではありません。

パスに含まれる番号は環境によって異なります。ここでは、SQLで扱っている表に、実際の保存先があることを確認してください。

### 表本体と全体の大きさ

```sql
SELECT pg_size_pretty(pg_relation_size('books')) AS table_size,
       pg_size_pretty(pg_total_relation_size('books')) AS total_size;
```

実行結果です。

```sql
 table_size | total_size
------------+------------
 64 kB      | 136 kB
(1 row)
```

同じ`books`を調べていますが、二つの値は違います。

- `table_size`の64 kB：`pg_relation_size`で調べた、表本体の主な格納領域の大きさ。
- `total_size`の136 kB：`pg_total_relation_size`で調べた、索引や補助的な領域、長い値を別に保存する領域（TOAST。後の補足で説明します）も含めた全体の大きさ。

`pg_size_pretty`は、バイト数をkBなどの読みやすい単位にして表示する関数です。差の72 kBがすべて索引というわけではありません。二つの関数では、数えている領域が違います。

### 1ページの大きさ

```sql
SHOW block_size;
```

実行結果です。

```sql
 block_size
------------
 8192
```

`block_size`は1ページの大きさで、単位はバイトです。この環境では8,192バイト、つまり8 kBでした。先ほどの表本体は64 kBなので、**64 ÷ 8 = 8ページ**分の大きさです。ここでのkBは1,024バイトとして計算します。

本は1,000冊ありますが、表本体の大きさは8ページ分です。1冊につき1ページなら1,000ページ必要なので、そういう保存の仕方ではありません。なお、これは保存領域の大きさから求めたページ数で、SQLが実行時にページへアクセスした回数ではありません。

## 行を、ページという箱に入れる

表のデータは、ページという一定の大きさの領域に分けて保存されます。行を読むときも、その行を含むページが読み込みの単位になります。

ここでは説明のため、1ページに3行入る小さな模型を使います。実際に何行入るかは、行の大きさなどで変わります。

![表の中にページ、ページの中に行](/images/postgresql-query-journey/03-pages-and-rows.png)
*説明用の模型。1ページ3行は実際の容量ではありません。*

本5を読みたいなら、その本が入ったページ1が必要です。欲しいのが本5の1行だけでも、読み込むのは本4〜6の入ったページ1全体です。

実際のページには、行そのものに加えて、ページ内のどこに各行があるかを記録する情報と、空き領域があります。この位置の情報を、次に`ctid`で確かめます。

## 行の場所を見てみる

各行の場所の手掛かりとして、`ctid`を表示できます。

```sql
SELECT id, ctid, title
FROM books ORDER BY id LIMIT 8;
```

実行結果です。

```sql
 id | ctid  |    title
----+-------+--------------
  1 | (0,1) | 実験用の本 1
  2 | (0,2) | 実験用の本 2
  3 | (0,3) | 実験用の本 3
  4 | (0,4) | 実験用の本 4
  5 | (0,5) | 実験用の本 5
  6 | (0,6) | 実験用の本 6
  7 | (0,7) | 実験用の本 7
  8 | (0,8) | 実験用の本 8
(8 rows)
```

先頭の行を見てください。`id`は`1`、`ctid`は`(0,1)`です。`id=1`が本の番号を表すのに対し、`ctid=(0,1)`は**その行が表のどこに保存されているか**を表します。

`ctid`の二つの数は、左から「ページ番号」「そのページ内で行を指す項目の番号」です。ページ番号は0から、項目番号は1から始まります。まずページ0を開き、その中の1番の項目から行の場所をたどる、と読みます。

![ctidの左の0でページを選び、右の1でページ内の項目を選ぶ](/images/postgresql-query-journey/03-ctid-location.png)
*掲載出力の対応を示す模型。行の物理的な並びや空き領域の配置は再現していません。*

出力の8行は、`ctid`の左側がすべて0です。本1から本8までは同じページにあり、右側の1〜8で別々の行を指しています。`LIMIT 8`で表示を止めたので、ページ0に入る行がこの8行だけとは限りません。

今回は番号順に行を追加したので、番号と保存場所が同じ順に並んでいます。この順序は保証されたものではありません。題名などを更新すると、同じ`id`でも`ctid`は変わることがあります。

アプリケーションで本を指定するときは、保存場所である`ctid`ではなく、主キーの`id`を使います。[ctidの公式説明](https://www.postgresql.org/docs/18/ddl-system-columns.html)にも、この使い分けが示されています。更新によって場所が変わる仕組みは第11章で扱います。

## 7,353回は、何の数だったのか

ページが読み込みの単位だと分かったので、第3章の数字に戻ります。今度は100万冊の`public.books`の大きさを調べます。いまは`search_path`の設定で観察用の`books`が先に見つかるので、スキーマ名を付けて指定します。

```sql
SELECT pg_size_pretty(pg_relation_size('public.books')) AS table_size,
       pg_relation_size('public.books') / current_setting('block_size')::int AS pages;
```

2026年9月23日、DockerのPostgreSQL 18.6、本100万冊と題名索引がある状態での実行結果です。

```sql
 table_size | pages
------------+-------
 57 MB      |  7353
(1 row)
```

### 表のページ数と、Seq Scanのアクセス回数が一致した

`current_setting('block_size')`は、先ほど`SHOW block_size`で確かめた8,192バイトです。表本体の大きさを1ページの大きさで割ると、7,353ページになりました。

この数は、第3章で索引を作る前の`Seq Scan`に出ていた`shared hit=7353`と同じです。Seq Scanは表のページを一つずつ使い、各ページの中の行に条件を当てていました。100万行を調べた検索のアクセスが7,353回だったのは、数えていた単位が行ではなくページだったからです。

索引を使った後は、`hit=1`と`read=3`で合計4回でした。索引も、表と同じくページでできています。Index Scanは索引のページをたどった後に表のページも読むので、この4回には索引と表の両方へのアクセスが含まれます。

根から葉まで索引のページをたどり、最後に表のページから目的の行を取り出す経路を、図で見てみましょう。

![索引の根、途中の案内、葉をたどり、表のページから行を取り出す](/images/postgresql-query-journey/03-index-reference.png)
*索引3段と表1ページを使う経路の模型。実行ログから各アクセス先を特定した図ではありません。*

この経路なら、索引の3ページと表の1ページを使います。今回の索引が3段だったことは、以下の補足のSQLで確認しています。ただし、`Buffers`には4回の内訳までは出ていません。この図は、少ないアクセスで1行に届く仕組みを示すものです。

:::details 索引の段数を確かめるには
ページの中身を調べる拡張機能`pageinspect`を使うと、B-treeの高さを表示できます。この章のトランザクションの中で作れば、観察用の表を片付けるROLLBACKで一緒に取り消されます。

```sql
CREATE EXTENSION IF NOT EXISTS pageinspect;
SELECT level FROM bt_metap('public.books_title_idx');
```

2026年9月23日の実行結果です。

```sql
 level
-------
     2
(1 row)
```

`level`は、葉を0段目として数えた根の高さです。2なら、根、途中の案内、葉の3段になります。第3章の模型で「100万冊でも3段で届く」と考えた段数と一致しています。
:::

## 1,000行なら、大きさも同じ？

次は、行の長さだけが違う表を二つ作り、大きさを比べます。章の冒頭で開始したトランザクションの中に、`SAVEPOINT`で戻り先を作ります。サイズを比べた後は、その位置まで取り消して観察を続けます。

`repeat('a', 10)`は、aを10回並べた文字です。今回は10文字の行と200文字の行を、それぞれ1,000行作ります。実行する前に、必要なページ数がどちらで多くなるか予想してください。

```sql
SAVEPOINT row_width;
CREATE TABLE size_short AS
SELECT n AS id, repeat('a', 10) AS note
FROM generate_series(1, 1000) AS n;
CREATE TABLE size_long AS
SELECT n AS id, repeat('a', 200) AS note
FROM generate_series(1, 1000) AS n;
SELECT pg_relation_size('size_short') AS short_bytes,
       pg_relation_size('size_long') AS long_bytes;
ROLLBACK TO SAVEPOINT row_width;
```

2026年9月23日に共有された実行結果です。入力SQLとpsqlのプロンプトを除いて掲載しています。

```sql
SAVEPOINT
SELECT 1000
SELECT 1000
 short_bytes | long_bytes
-------------+------------
       65536 |     262144
(1 row)

ROLLBACK
```

二つの`SELECT 1000`は、それぞれの`CREATE TABLE ... AS SELECT`で1,000行の表を作ったことを表すメッセージです。続く表には、作った表本体の大きさがバイト数で表示されています。

最後の`ROLLBACK`という出力は、`ROLLBACK TO SAVEPOINT row_width`が完了したことを示します。この行幅実験で作った`size_short`と`size_long`は取り消されますが、外側のトランザクションは続いています。観察用の`books`も残るので、そのまま次へ進めます。章末の`ROLLBACK;`で、外側のトランザクションも終了します。

先ほど確認した1ページ8,192バイトで割ってみます。

| 表 | 文字列の長さ | 行数 | 表本体の大きさ | ページ数 |
| --- | ---: | ---: | ---: | ---: |
| `size_short` | 10文字 | 1,000行 | 65,536バイト | 8ページ |
| `size_long` | 200文字 | 1,000行 | 262,144バイト | 32ページ |

ページの大きさは、どちらの表でも8,192バイトです。同じ大きさのページに、短い行と長い行を入れる様子を比べてください。

![長い行は同じページに入る数が少なくなり、1,000行を入れるページが増える](/images/postgresql-query-journey/03-row-width.png)
*総ページ数の8と32は今回の実測値。拡大したページ内の行数は説明用です。*

### 行数だけでは、読む量を比べられない

二つとも1,000行ですが、表本体は8ページと32ページです。同じ行数でも、必要なページ数は**4倍**になりました。長い行は1ページに入る数が少なくなるので、より多くのページが必要です。

表全体を読むなら、長い行の表では4倍のページを読むことになります。「どちらも1,000行だから、読むデータ量も同じ」とは言えません。ただし、この実験で測ったのは保存サイズです。読み取り時間が4倍になるかどうかは、まだ測っていません。

行には文字列以外の列や管理情報もあるため、文字数の比率がそのままページ数の比率になるわけでもありません。

なお、`Buffers`はアクセス回数なので、同じページを繰り返し使えばその分も数えます。表のサイズから求める「何ページあるか」と、SQLを実行して観察する「何回アクセスしたか」は、分けて考えてください。

:::details もっと長い文字列を入れたら
さらに長い値は、圧縮したり、別の保存領域へ置いたりすることがあります。この仕組みをTOASTと呼びます。そのため、文字を10倍にしたら表本体のサイズも必ず10倍、とは予想できません。[物理ストレージの公式解説](https://www.postgresql.org/docs/18/storage.html)から詳しくたどれます。
:::

## 観察用の表を片付ける

この章の観察が終わったら、同じpsqlで次を実行します。観察用スキーマの準備からここまでを、一つのトランザクションとして扱ってきました。

```sql
ROLLBACK;
```

観察用スキーマと表が取り消され、`books`という名前が指す表も元の`public.books`に戻ります。100万冊の`public.books`と題名索引は変更していません。

## 確かめる問い

100万行の表が二つあります。一方は番号だけ、もう一方は長い紹介文も持っています。両方の表を全件読むとき、読むデータの量は同じだと考えてよいでしょうか。

:::details 考え方
行数が同じでも、行の大きさや保存方法が違えばページ数が違います。まず実際のサイズを確かめます。件数だけから読み込み量を決めません。
:::

第3章のSeq Scanは、7,353ページを使っていました。検索のたびに、この7,353ページをストレージから取り寄せているのでしょうか。次章では、小さな表で同じ検索を繰り返し、ページをどこから使っているのかを調べます。
