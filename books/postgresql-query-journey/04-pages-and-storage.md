## この章で分かること

SQLのテーブルは、物理的にはファイルやページに保存されています。テーブルのサイズやレコードの位置を観察し、レコード数、ページ数、バイト数を別々の量として捉えます。Indexからテーブルを参照する関係や、長い値を保存する仕組みも紹介します。同じ件数でも読み込み量が違う理由を説明するための土台を作る章です。

:::message
接続し直したら、「準備」の章の共通設定を入力してください。この章から始めるときの準備は、[実験用リポジトリのREADME](https://github.com/hatsu38/postgresql-structures-lab#readme)にあります。
:::

## 7,353回は、何を数えた回数？

第3章では、題名のIndexを作ると、実行時のバッファアクセスが7,353回から4回に減りました。では、この「1回」は何を1個と数えた回数なのでしょうか。

レコードの数ではなさそうです。Indexを作る前の検索は100万件に条件を当てていましたが、アクセスは7,353回でした。1件につき1回と数えるなら、100万回近くになるはずです。

![Indexを作る前の題名検索は100万件を調べたが、アクセスは7,353回だった](/images/postgresql-query-journey/03-storage-question.png)
*調べたレコードの100万と、アクセスの7,353回を見比べてください（どちらも第3章の実測）。*

そこで、PostgreSQLはレコードより大きなまとまりでデータを扱っている、と考えてみます。たとえば本が1,000冊なら、コンピュータの中には1,000個の小さなファイルがあるのでしょうか。

## レコードを、ページという箱に入れる

PostgreSQLは、レコードを1件ずつ別のファイルにはしません。テーブルのデータはファイルに保存され、そのファイルは**ページ**という一定の大きさの領域に区切られています。1ページには何件ものレコードが入ります。レコードを読むときも、そのレコードを含むページが読み込みの単位になります。欲しいのが1件だけでも、読むのはそのレコードが入ったページ全体です。

実際のページには、レコードそのものに加えて、ページ内のどこに各レコードがあるかを記録する情報と、空き領域があります。この位置の情報は、章の後半で`ctid`として確かめます。

この形を、1,000冊の小さな観察用のテーブルで確かめます。保存先のファイル、テーブルの大きさ、1ページの大きさから、1,000件が何ページに入っているかを求めます。小さなテーブルで単位を確かめてから、100万冊のテーブルに戻って7,353回と対応させます。

## 観察用の小さなテーブルを用意する

100万冊の`books`は残し、同じDBに1,000冊の`books_observation`を作ります。番号と題名の列、番号の主キーを持つ通常のテーブルです[^temp]。以降のSQLでは、名前で二つを区別します。

[^temp]: 接続内だけで使う一時テーブルという作り方もありますが、そのページは接続ごとの領域に置かれ、共有バッファには入りません。第5章で`shared hit`を観察するため、ここでは通常のテーブルを使います。

`books_observation`はこの本の観察用の名前です。同じ名前のテーブルが既にある場合、この本で作ったものなら[実験用リポジトリのREADME](https://github.com/hatsu38/postgresql-structures-lab#readme)の手順で削除してから作り直します。別の用途で使っているものなら削除せず、以下のSQLと以降の観察SQLで別の名前を使ってください。

```sql
CREATE TABLE books_observation (
  id bigint PRIMARY KEY,
  title text NOT NULL
);
INSERT INTO books_observation
SELECT id, title FROM books WHERE id BETWEEN 1 AND 1000 ORDER BY id;
ANALYZE books_observation;
SELECT count(*) FROM books_observation;
```

2026年9月25日、DockerのPostgreSQL 18.6での実行結果です。

```sql:実行結果
INSERT 0 1000
 count
-------
  1000
(1 row)
```

`INSERT 0 1000`は1,000件を追加したことを示し、最後の`count`でも1,000件あると確認できます。`ORDER BY id`で番号順に追加しています。

psqlでは、SQLの実行が終わるたびに変更が確定します。接続を閉じても、作ったテーブルは残ります。

## テーブルの保存先と大きさを調べる

この節の三つの出力（保存先、大きさ、`block_size`）は、2026年9月25日に`books_observation`を観察した実測例です。自分の環境では、パスや容量が違うことがあります。

### テーブルの保存先のパス

```sql
SELECT pg_relation_filepath('books_observation');
```

実行結果です。

```sql:実行結果
 pg_relation_filepath
----------------------
 base/17212/17223
(1 row)
```

`books_observation`というテーブル名に対して、`base/17212/17223`というパスが返ってきました。これはPostgreSQLのデータディレクトリを基準にした相対パスです。今回ならDocker内のDBサーバ側の場所で、手元のパソコンに同じパスがあるという意味ではありません。

パスに含まれる番号は環境によって異なります。ここでは、SQLで扱っているテーブルに、実際の保存先があることを確認してください。返ってきたパスは一つです。1,000冊のレコードは、1,000個の小さなファイルに分かれず、テーブル本体のこのファイルに入っています。

### テーブル本体と全体の大きさ

```sql
SELECT pg_size_pretty(pg_relation_size('books_observation')) AS table_size,
       pg_size_pretty(pg_total_relation_size('books_observation')) AS total_size;
```

実行結果です。

```sql:実行結果
 table_size | total_size
------------+------------
 64 kB      | 136 kB
(1 row)
```

同じ`books_observation`を調べていますが、二つの値は違います。

- `table_size`の64 kB：`pg_relation_size`で調べた、テーブル本体の主な格納領域の大きさ。
- `total_size`の136 kB：`pg_total_relation_size`で調べた、Indexや補助的な領域、長い値を別に保存する領域（TOAST。後の補足で説明します）も含めた全体の大きさ。

`pg_size_pretty`は、バイト数をkBなどの読みやすい単位にして表示する関数です。この章で追うのは、テーブル本体の64 kBです。

:::details 差の72 kBの内訳
差の72 kBは、すべてがIndexというわけではありません。2026年9月28日に同じ手順でテーブルを作り直して内訳を調べると、主キーのIndexが40 kB、各ページの空き具合を記録する補助の領域が24 kB、TOASTのための領域が8 kBで、合わせて72 kBでした。
:::

### 1ページの大きさ

```sql
SHOW block_size;
```

実行結果です。

```sql:実行結果
 block_size
------------
 8192
(1 row)
```

`block_size`は1ページの大きさで、単位はバイトです。この環境では8,192バイト、つまり8 kBでした。先ほどのテーブル本体は64 kBなので、**64 ÷ 8 = 8ページ**分の大きさです。ここでのkBは1,024バイトとして計算します。

本は1,000冊ありますが、テーブル本体の大きさは8ページ分です。1冊につき1ページなら1,000ページ必要なので、そういう保存の仕方ではありません。なお、これは保存領域の大きさから求めたページ数で、SQLが実行時にページへアクセスした回数ではありません。

観察用のテーブルの1,000件が、8ページにどう入っているかを見てください。1ページに何件入るかは、レコードの大きさなどで変わります。

![1,000件のテーブルが8ページに分かれ、本5の入ったページ0を丸ごと読み込む](/images/postgresql-query-journey/03-pages-and-rows.png)
*太枠のページ0と、その中の本5を見てください（ページごとのレコード数は2026年9月25日の実測）。*

本5を読みたいなら、その本が入ったページ0が必要です。欲しいのが本5の1件だけでも、読み込むのは本1〜136の入ったページ0全体です。

## レコードの場所を見てみる

各レコードの場所の手掛かりとして、`ctid`を表示できます。

```sql
SELECT id, ctid, title
FROM books_observation ORDER BY id LIMIT 8;
```

実行結果です。

```sql:実行結果
 id | ctid  |    title
----+-------+--------------
  1 | (0,1) | 実験用の本 1
  2 | (0,2) | 実験用の本 2
  3 | (0,3) | 実験用の本 3
  4 | (0,4) | 実験用の本 4
  5 | (0,5) | 実験用の本 5
  6 | (0,6) | 実験用の本 6
  7 | (0,7) | 実験用の本 7
  8 | (0,8) | 実験用の本 8
(8 rows)
```

先頭のレコードを見てください。`id`は`1`、`ctid`は`(0,1)`です。`id=1`が本の番号を表すのに対し、`ctid=(0,1)`は**そのレコードがテーブルのどこに保存されているか**を表します。

`ctid`の二つの数は、左から「ページ番号」「そのページ内でレコードを指す項目の番号」です。ページ番号は0から、項目番号は1から始まります。まずページ0を開き、その中の1番の項目からレコードの場所をたどる、と読みます。

![出力の1行目のctid (0,1)の0でページ0を選び、1の項目をたどって、実験用の本 1のレコードに届く](/images/postgresql-query-journey/03-ctid-location.png)
*(0,1)の0がページを、1がページの中の項目を選ぶことを見てください。掲載した出力に合わせて描いた図です。ページの中でレコードがどう並ぶかは、次の図で見ます。*

項目は、レコードそのものではありません。ページの中でレコードがどこにあるかを書いた、1件4バイトの小さな札です。項目はページの前から順に、レコードはページの後ろから詰めて置かれ、その間が空き領域になります。レコードを直接指さずに札を一段挟むのは、空き領域を詰めるためにページの中でレコードを動かしても、項目の番号、つまり`ctid`を変えずに済むからです（[ページの構造の公式説明](https://www.postgresql.org/docs/18/storage-page-layout.html)）。

ページ0の中の並びを図にすると、次のようになります。

![ページ0の先頭にページの管理情報があり、その後ろに項目1、2、3…136が前から並ぶ。レコードは本1がいちばん後ろで、本2、本3…本136と後ろから並び、間が空き領域になる。各項目は自分のレコードを指す](/images/postgresql-query-journey/03-page-layout.png)
*項目は前から、レコードは後ろから並び、その間が空き領域になることを見てください。項目の番号が、`ctid`の右側の数です（136件は2026年9月28日の実測、各部分の大きさは説明するための図）。*

出力の8件は、`ctid`の左側がすべて0です。本1から本8までは同じページにあり、右側の1〜8で別々のレコードを指しています。`LIMIT 8`で表示を止めたので、ページ0に入るレコードがこの8件だけとは限りません。

:::details ページごとのレコード数を数えるには
`ctid`の左側のページ番号ごとに数えます。`ctid`をいったん文字列にし、二つの数の組として読める型（`point`）に変えて、左側の数だけを取り出しています。

```sql
SELECT (ctid::text::point)[0]::int AS page, count(*) AS records
FROM books_observation GROUP BY page ORDER BY page;
```

2026年9月28日に、同じ手順で作り直したテーブルで数えると、0〜6ページが136件ずつ、7ページが48件でした。

ページ0から6に136件ずつ、ページ7に残りの48件が入っています。このあとの`size_short`と`size_long`も、テーブル名を変えて同じSQLで数えられます。
:::

今回は番号順にレコードを追加したので、番号と保存場所が同じ順に並んでいます。この順序は保証されたものではありません。題名などを更新すると、同じ`id`でも`ctid`は変わることがあります。

アプリケーションで本を指定するときは、保存場所である`ctid`ではなく、主キーの`id`を使います。[ctidの公式説明](https://www.postgresql.org/docs/18/ddl-system-columns.html)にも、この使い分けが示されています。更新によって場所が変わる仕組みは第11章で扱います。

## 7,353回は、何の数だったのか

ページが読み込みの単位だと分かったので、第3章の数字に戻ります。今度は100万冊の`public.books`の大きさを調べます。`books_observation`と区別して、元のテーブルを指定します。`public`は「準備」の章でテーブルを作った場所の名前です。この場所を**スキーマ**と呼びます。

```sql
SELECT pg_size_pretty(pg_relation_size('public.books')) AS table_size,
       pg_relation_size('public.books') / current_setting('block_size')::int AS pages;
```

2026年9月25日、DockerのPostgreSQL 18.6、本100万冊と題名のIndexがある状態での実行結果です。

```sql:実行結果
 table_size | pages
------------+-------
 57 MB      |  7353
(1 row)
```

### テーブルのページ数と、Seq Scanのアクセス回数が一致した

`current_setting('block_size')`は、先ほど`SHOW block_size`で確かめた8,192バイトです。テーブル本体の大きさを1ページの大きさで割ると、7,353ページになりました。

この数は、第3章でIndexを作る前の`Seq Scan`に出ていた`shared hit=4657 read=2696`の合計と同じです。Seq Scanはテーブルのページを一つずつ使い、各ページの中のレコードに条件を当てていました。100万件を調べた検索のアクセスが7,353回だったのは、数えていた単位がレコードではなくページだったからです。

Indexを使った後は、`hit=1`と`read=3`で合計4回でした。Indexも、テーブルと同じくページでできています。`Index Scan`は、Indexのページをたどった後にテーブルのページも読むので、この4回にはIndexとテーブルの両方へのアクセスが含まれます。

テーブルのページをすべて読むSeq Scanと、根から葉までIndexのページをたどり、最後にテーブルのページから目的のレコードを取り出すIndex Scanの経路を、図で比べてみましょう。

![Seq Scanはテーブルの7,353ページをすべて読み、Index Scanは根・途中・葉のIndexの3ページとテーブルの1ページの合わせて4ページを読む](/images/postgresql-query-journey/03-index-reference.png)
*読むページの数（7,353と4）は実測です。下の4ページの内訳（Indexの3ページとテーブルの1ページ）はIndexの段数から考えたもので、実行ログで各アクセス先を確かめたものではありません。*

この経路なら、Indexの3ページとテーブルの1ページを使います。今回のIndexが3段だったことは、以下の補足のSQLで確認しています。ただし、`Buffers`には4回の内訳までは出ていません。この図は、少ないアクセスで1件に届く仕組みを示すものです。4回が`hit=1`と`read=3`に分かれている意味は、次章で共有バッファを調べてから読みます。

:::details Indexの段数を確かめるには
ページの中身を調べる拡張機能`pageinspect`を使うと、B-treeの高さを表示できます。拡張機能は一度追加すると、このDBで引き続き使えます。

```sql
CREATE EXTENSION IF NOT EXISTS pageinspect;
SELECT level FROM bt_metap('public.books_title_idx');
```

2026年9月25日の実行結果です。

```sql:実行結果
 level
-------
     2
(1 row)
```

`level`は、葉を0段目として数えた根の高さです。2なら、根、途中の案内板、葉の3段になります。第3章で仮の数から「100万冊でも3段で届く」と考えた段数と一致しています。
:::

## 同じ1,000レコードなら、大きさも同じ？

次は、1レコードに入れる文字列の長さを変えて、テーブルの大きさを比べます。この実験で作る`size_short`と`size_long`は、比較が終わったら削除します。同じ名前のテーブルが既に別の用途で使われている場合は、名前を変えてください。

`repeat('a', 10)`は、aを10回並べた文字です。今回は`id`と`note`を持つレコードを、各テーブルに1,000件ずつ作ります。`note`に入れる文字列は、一方が10文字、もう一方が200文字です。実行する前に、必要なページ数がどちらで多くなるか予想してください。

```sql
CREATE TABLE size_short AS
SELECT n AS id, repeat('a', 10) AS note
FROM generate_series(1, 1000) AS n;
CREATE TABLE size_long AS
SELECT n AS id, repeat('a', 200) AS note
FROM generate_series(1, 1000) AS n;
SELECT pg_relation_size('size_short') AS short_bytes,
       pg_relation_size('size_long') AS long_bytes;
```

2026年9月25日、DockerのPostgreSQL 18.6での実行結果です。

```sql:実行結果
 short_bytes | long_bytes
-------------+------------
       65536 |     262144
(1 row)
```

表には、作ったテーブル本体の大きさがバイト数で表示されています。

先ほど確認した1ページ8,192バイトで割ってみます。

| テーブル | noteの文字数 | レコード数 | テーブル本体の大きさ | ページ数 |
| --- | ---: | ---: | ---: | ---: |
| `size_short` | 10文字 | 1,000件 | 65,536バイト | 8ページ |
| `size_long` | 200文字 | 1,000件 | 262,144バイト | 32ページ |

ページの大きさは、どちらのテーブルでも8,192バイトです。1レコードあたりのデータ量が増えると、同じページに入るレコード数がどう変わるか、図で比べてください。

![noteが10文字なら1ページに最大185レコード、200文字なら最大34レコードが入る。1,000件を保存するとレコードの入ったページは6枚と30枚で、それぞれ空きページも2枚ある](/images/postgresql-query-journey/03-row-width.png)
*図の「件」はレコード数です。1ページに入る件数（最大185件と34件）の差が、必要なページ数の差になります。破線はレコードが入っていない空きページです（2026年9月25日の実測）。*

### レコード数が同じでも、読むデータ量は違う

**1レコードあたりのデータ量が大きいほど、1ページに入る件数は少なくなります。** 今回は、`note`が10文字なら1ページに最大185件、200文字なら最大34件でした。そのため、同じ1,000件を保存するのに必要なページ数も変わります。

ただし、`note`の文字数は20倍でも、1ページに入る件数は20分の1にはなっていません。1件ごとに、`note`の値のほかにもかかる分があるからです。2026年9月28日に、同じ手順で作った二つのテーブルのページ0を、前の補足で使った`pageinspect`で読むと、次のようになっていました。

| 1件ごとにかかるもの | noteが10文字 | noteが200文字 |
| --- | ---: | ---: |
| レコードの先頭の管理情報 | 24バイト | 24バイト |
| `id`と`note`の値 | 15バイト | 208バイト |
| レコード全体 | 39バイト | 232バイト |
| ページの中の項目（`ctid`で見た札） | 4バイト | 4バイト |

表の値を、バイト数に比例した長さの帯にすると、次のようになります。

![noteが10文字の1件はレコードの管理情報24バイト、値15バイト、項目4バイト。200文字の1件はレコードの管理情報24バイト、値208バイト、項目4バイトで、レコードの管理情報と項目の長さは2本で同じ](/images/postgresql-query-journey/03-record-bytes.png)
*左端のレコードの管理情報と右端の項目が、2本で同じ長さであることを見てください。帯の長さはバイト数に比例させています（バイト数は2026年9月28日の実測）。*

レコードの管理情報と項目の分は、`note`が何文字でも同じだけかかります。10文字のレコードでは、1件に使う場所の半分以上がこの分です。そのため`note`を20倍にしても、1件に使う場所は20倍にはならず、1ページに入る件数も185件から34件へ減るだけでした。

表の数で8,192バイトを割っても、185件ぴったりにはなりません。ページの先頭には、ページの中の並びの図で見た、ページの管理情報もあります。さらに、レコードを置く位置をそろえるために、レコードの後ろに小さな隙間が空くことがあるからです[^page-fit]。

[^page-fit]: 同じ`pageinspect`で読むと、10文字のテーブルのページ0では、レコードを置いた位置（`heap_page_items`の`lp_off`）が8152、8112、8072と、39バイトではなく40バイトずつずれていました。項目の並びの終わりの位置（`page_header`の`lower`）は764で、ページの管理情報の24バイトと、185件分の項目（185×4＝740バイト）を足した数です。200文字のレコードは232バイトで、位置は232バイトずつずれていました。

実際のファイルには、まだレコードが入っていないページも2枚ずつありました。

- `size_short`：レコードが入った6ページ＋空き2ページ＝8ページ
- `size_long`：レコードが入った30ページ＋空き2ページ＝32ページ

空きページもファイルの一部なので、先ほどのSQLで測った保存サイズに含まれます。今回は**32 ÷ 8＝4倍**の差がありました。PostgreSQLはファイルを広げるときに複数ページをまとめて確保することがあり、レコードが入ったページ数と、ファイル全体のページ数が一致するとは限りません。

テーブル全体を読む場合、今回の`size_long`では`size_short`の4倍のページが対象になります。「どちらも1,000レコードだから、読むデータ量も同じ」とは言えません。ただし、測ったのは保存サイズです。読み取り時間が4倍になることまで確認したわけではありません。

なお、`Buffers`はアクセス回数なので、同じページを繰り返し使えばその分も数えます。テーブルのサイズから求める「何ページあるか」と、SQLを実行して観察する「何回アクセスしたか」は、分けて考えてください。

:::details もっと長い文字列を入れたら
さらに長い値は、圧縮したり、別の保存領域へ置いたりすることがあります。この仕組みをTOASTと呼びます。そのため、文字を10倍にしたらテーブル本体のサイズも必ず10倍、とは予想できません。[物理ストレージの公式解説](https://www.postgresql.org/docs/18/storage.html)から詳しくたどれます。
:::

## 比較用のテーブルを片付け、次章へ残すものを確認する

レコードのデータ量を比べた二つのテーブルを削除します。

```sql
DROP TABLE size_short, size_long;
```

`books_observation`は第5章でも使うので残します。100万冊の`books`と題名のIndexも、そのまま使えます。ここでpsqlを閉じても構いません。再接続するときは、「準備」の章の共通設定を入力してから進めてください。

## 考えてみよう

100万件のテーブルが二つあります。一方は番号だけ、もう一方は長い紹介文も持っています。両方のテーブルを全件読むとき、読むデータの量は同じだと考えてよいでしょうか。

:::details 考え方
レコード数が同じでも、レコードの大きさや保存方法が違えばページ数が違います。まず実際のサイズを確かめます。件数だけから読み込み量を決めません。
:::

## まとめ

- 読み込みの単位はページ（8kB）。読む量は、レコード数ではなくページ数で考える。
- レコード数が同じでも、1件の大きさや保存のしかたで、ページ数は変わる。

第3章のSeq Scanは、7,353ページを使っていました。検索のたびに、この7,353ページをストレージから取り寄せているのでしょうか。次章では、小さなテーブルで同じ検索を繰り返し、ページをどこから使っているのかを調べます。
