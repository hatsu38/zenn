## この章で分かること

読了記録を新しい順に並べるために、どんな仕事が必要でしょうか。少数の値の比較から始めて、実行計画のSortと対応させます。件数とwork_memを別々に変え、メモリ内での処理と一時ファイルを使う処理を観察します。作業メモリをプロセスの地図へ戻し、並べ替えが遅いときに何を確認すべきかを整理します。

## はじめに：新しい読了記録を上にしたい

今度は「最近読み終えた記録の一覧」を作ります。記録が入っている順と、日時の新しい順は同じとは限りません。

最近の記録を見たい利用者に、日時順の一覧を返す場面です。まずは3件だけで考えます。

![読み終えた順に、並べたい](/images/postgresql-query-journey/07-recent-records.png)
*学ぶきっかけを描く、説明用の場面。*

絵の日付と本の番号は説明用です。件数が増えたときの比較やメモリ使用を、次の実験で観察します。

新しい順に返す依頼は、こう書きます。

```sql
SELECT book_id, finished_at
FROM reading_records
ORDER BY finished_at DESC, book_id ASC;
```

`DESC`は大きい値から、`ASC`は小さい値からです。日時が同じ場合は本の番号順にします。

## 大きさを比べて順序を作る

説明用に、日時を数字へ置き換えます。数字が大きいほど新しいとします。8、3、6、1を新しい順にしたいなら、8、6、3、1です。

どうやって並べるか、手元で4枚のカードを動かしてみてください。

次は、二つの小さな並びを作って合流する模型です。PostgreSQLのメモリ内ソートをそのまま再現したものではなく、比較して順序を作る仕事の説明です。

![二つの並びを、比べながら合流する](/images/postgresql-query-journey/07-merge-cards.png)
*比較の模型 ／ PostgreSQLの実装そのものではない。*

行を一度ずつ読むだけでなく、値を比べ、置く順序を決める仕事があります。比較ソートの代表的な増え方は`O(n log n)`です。件数が増えると、読む仕事に加えて、順序を整える仕事も増えます。

## 第1章で用意した200万件を使う

本100万冊・読了記録200万件は、第1章で準備してあります。ここでは件数を確認し、同じ記録の並べ替えを観察します。序章の過去実測で使った2,000万件とは区別してください。

```sql
SELECT count(*) FROM reading_records;
```

2026年9月23日に、初期化した実験用DBで確認した結果です。

```sql
  count
---------

(1 row)
```

`count`が2,000,000なら準備できています。記録を削除したり、追加し直したりする必要はありません。後続章でも、この200万件を使います。

## Sortを観察する

全行を画面へ流すと、表示や転送も混ざります。ここでは実行計画を通して処理を観察します。

```sql
SET max_parallel_workers_per_gather = 0;
SET jit = off;
SET work_mem = '64MB';
```

```sql
SET
SET
SET
```

この設定は、いま接続しているpsqlのセッションに適用されます。接続し直した場合は、実験前に再設定してください。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT book_id, finished_at
FROM reading_records
WHERE finished_at >= timestamp '2026-09-14'
  AND finished_at < timestamp '2026-09-21'
ORDER BY finished_at DESC, book_id ASC;
```

**読了記録200万件**のうち、指定した1週間の記録を並べ替えます。次は、この条件で得られた実行結果です。実行計画の見出しと罫線は省いています。

```sql
Sort  (cost=88387.00..89643.06 rows=502425 width=16) (actual time=182.059..207.760 rows=499998.00 loops=1)
  Sort Key: finished_at DESC, book_id
  Sort Method: quicksort  Memory: 27913kB
  Buffers: shared hit=10811
  ->  Seq Scan on reading_records  (cost=0.00..40811.00 rows=502425 width=16) (actual time=0.022..80.506 rows=499998.00 loops=1)
        Filter: ((finished_at >= '2026-09-14 00:00:00'::timestamp without time zone) AND (finished_at < '2026-09-21 00:00:00'::timestamp without time zone))
        Rows Removed by Filter: 1500002
        Buffers: shared hit=10811
Planning Time: 0.083 ms
Execution Time: 223.929 ms
```

`Sort`の近くで、次の項目を探します。

| 項目 | 調べること |
| --- | --- |
| `Sort Key` | 何を基準に並べたか |
| `Sort Method` | どの方法を使ったか |
| `Memory`や`Disk` | 作業で使った量 |
| 子の`actual rows` | 何行を受け取ったか |

親の実行時間には子を動かす時間も含まれます。全ノードの時間を足して合計にしないでください。まずは「どの段で何行を受け取り、どんな方法を使ったか」を読むことに集中します。

### 200万件を調べ、499,998件を並べた

まず、下側の`Seq Scan`を見ます。`actual`の中の`rows=499998.00`が、期間の条件に合って次の処理へ渡した行数です。`Rows Removed by Filter: 1500002`は、条件に合わず除外した行数です。今回は`loops=1`なので、そのまま足せます。

**499,998行 ＋ 1,500,002行 ＝ 2,000,000行。** 表の200万行を調べ、そのうち約4分の1を次の`Sort`へ渡しています。

上側の`Sort`も`actual`の`rows`は499,998です。この段階では期間の絞り込みが済んでいるので、並べ替えるのは200万行すべてではなく、対象週の499,998行です。`Sort Key`は日時の降順、同じ日時なら本の番号の昇順という、SQLの指定に対応しています。

なお、`cost`と同じ括弧にある`rows=502425`は実行前の見積もりです。実際に数えた499,998行と区別して読みます。見積もりの作り方は第10章で扱います。

### 今回の並べ替えは、メモリに収まった

`Sort Method: quicksort  Memory: 27913kB`から、今回はクイックソートを使い、作業に27,913kBのメモリを使ったことが分かります。約27.3MiBで、設定した`work_mem = '64MB'`の範囲に収まっています。64MBを設定したからといって、64MBすべてを使ったわけではありません。

この出力には`Disk`や`temp read/written`がありません。今回のSortは、途中結果を一時ファイルへ出さずに処理できています。次の実験では、同じ行数のまま作業用メモリを減らし、この部分がどう変わるかを確かめます。

### 223.929msは、ソートだけの時間ではない

`Execution Time: 223.929 ms`は、この実行計画全体の実行時間です。表を読んで期間で絞り込む処理も含まれるので、「約224msかけて並べ替えた」とは言えません。また、通常の`SELECT`で約50万行を画面に表示し終わるまでの時間でもありません。

`Sort`と`Seq Scan`には、どちらも`shared hit=10811`があります。親の値には子の処理でのアクセスも含まれるため、足して21,622回とは数えません。この計画では、表を読むときの共有バッファへのアクセスが、親の`Sort`にも含まれて表示されています。

実行時間やバッファの親子関係は、[PostgreSQL 18のEXPLAINの説明](https://www.postgresql.org/docs/18/using-explain.html)でも確認できます。

## 作業用メモリに収まらないとき

100枚のカードを並べたいのに、机には10枚しか置けないとします。

少しずつ並べて別の場所へ置き、最後に合流させれば、大きな並びを作れます。DBでも、作業用メモリに収まらない場合は、途中結果を一時ファイルへ置く方法があります。

![メモリに収まらないときの並べ替え](/images/postgresql-query-journey/07-external-sort.png)
*外部ソートの模型 ／ まとまりの個数・容量は模式的。*

実際のソートでも、使えるメモリを少なくして比べてみます。

```sql
SET work_mem = '64kB';
```

同じ`EXPLAIN (ANALYZE, BUFFERS)`をもう一度実行します。`external merge`や`Disk`、`temp read/written`が現れたか比べてください。結果は環境とデータで確認します。時間が何倍になるかを先に決めません。

ここからの比較表は、本書の原稿検証時に別途採取したログの抜粋です。上で掲載した読者の実行結果とは別の測定ですが、同じ200万件のサンプルを使い、対象週の入力は499,998行でした。

| work_mem | Sort Methodの出力 | 作業量の表示 |
| --- | --- | --- |
| 64MB | `quicksort` | `Memory: 27913kB` |
| 64kB | `external merge` | `Disk: 12784kB` |

2026年9月22日、DockerのPostgreSQL 18.6、並列実行とJITは無効です。MemoryとDiskは別の場所・形式の量なので、この二つを引き算して節約量とはしません。**方法と置き場所が変わった**ことを読み取ります。

`shared`は表や索引のページに関わる値、`temp`は今回のような一時ファイルに関わる値です。第5章の二つの置き場所が、ここで別々の数字になります。

## メモリを増やせば、いつも解決？

一つの処理で一時ファイルを減らせても、多くの人が同時に同じ作業をすると、必要なメモリは増えます。一つのSQLに複数のソートがある場合もあります。

そのため、`work_mem`を「DB全体でここまで」とは読めません。また、並べ替え以外に時間がかかっているなら、ソート用のメモリを増やしても、その処理は減りません。

実験後は、後続章の基準へ戻します。

```sql
SET work_mem = '4MB';
```

課題です。Sortがすでにメモリ内で済んでいる場合、「一時ファイルをなくすためにwork_memを増やす」という説明は成り立つでしょうか。実際の出力を根拠に考えてください。
