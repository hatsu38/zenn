## この章で分かること

読了記録を新しい順に並べるために、どんな処理が必要でしょうか。まず、ランキングの計画に出ていたメモリの値を手掛かりに、ページを置く共有バッファと、並べ替えなどの処理ごとに使う作業用メモリを分けます。次に、4枚のカードを基準の値で分けて並べる手順を追い、実行計画のSortと対応させます。`work_mem`を変えて、メモリ内で終わる並べ替えと、並べたまとまりを一時ファイルに書いて合流させる並べ替えを観察します。最後に、作業用メモリがどこに置かれるかを第6章の補足と対応させ、並べ替えが遅いときに何を確認すべきかを整理します。

## メモリの領域を用途で分ける

前章のランキングの計画には、`Buffers`のほかに、`Sort Method: top-N heapsort  Memory: 27kB`や、`HashAggregate`の`Memory Usage: 8281kB`のような、メモリの量を表す値も並んでいました。

第5章で見た共有バッファは、テーブルやIndexのページを置く場所でした。しかし、検索の途中で生まれる値は、ページの形をしていません。序章のランキングなら、本ごとに数えた読了記録の件数と、それを多い順に並べ替えている途中の並びが、そうした値です。テーブルのページではないので、共有バッファには置きません。

こうした値を置くのが、処理ごとの**作業領域**（作業用メモリ）です。図で、二つの接続がそれぞれ作業領域を持ち、共有バッファだけを共有している配置を見てください。

![接続Aは数える処理と並べ替えの作業領域を二つ、接続Bは並べ替えの一つを持ち、下の共有バッファのページP0〜P3は両方の接続が使う](/images/postgresql-query-journey/04-memory-regions.png)
*接続Aには破線の枠が二つあります。作業領域は処理ごとに用意され、共有バッファだけを両方の接続で使います（説明するための図）。*

接続Aの「数える」枠の「8、3、6、1」は、本1〜本4ごとに数えた読了記録の件数です。その右の「並べ替え」枠には、同じ件数を多い順に並べ替えている途中の値が入ります。並べ替えは**ソート**とも呼びます。このように一つの接続の中でも、数える処理と並べ替える処理が、それぞれ自分の作業領域を持ちます。

接続Bの「並べ替え」枠も同じ数字にしていますが、接続Bが別に持っている値です。接続Aの途中の値を接続Bが使うことはないので、作業領域は接続ごとに別々です。

一方、下側の共有バッファにあるページP0〜P3は、どちらの接続からも使えます。第5章の検索が2回目から`hit`になったのは、この下側の領域にページが残っていたからです。

ランキングの出力に並んでいた値を、二つの領域に分けると次のようになります。

| 出力の例 | 表しているもの |
| --- | --- |
| `Buffers: shared hit=2048 read=8763` | 共有バッファのページを使った数（第5章） |
| `Sort Method: top-N heapsort  Memory: 27kB` | 並べ替えに使った作業用メモリ |
| `Memory Usage: 8281kB`（HashAggregate）、`Memory Usage: 4883kB`（Hash） | 数える処理と照合の準備に使った作業用メモリ |
| `temp read=9046 written=10758`、`Batches: 9` | 作業用メモリに収まらず、一時ファイルを使ったこと |

この二つの領域の大きさは、別々の設定で決まります。

| 設定名 | 決めるもの |
| --- | --- |
| `shared_buffers` | テーブルやIndexのページを保持する共有バッファの大きさ |
| `work_mem` | ソートなど一つの処理が、作業に使えるメモリ量の基準 |

値は`SHOW`で確認できます。今回の実験環境では、次の値になっていました。

```sql
SHOW shared_buffers;
SHOW work_mem;
```

実行結果です。

```sql:実行結果
 shared_buffers
----------------
 128MB
(1 row)

 work_mem
----------
 4MB
(1 row)
```

この出力は設定値であり、いま各処理が実際に使っているメモリ量ではありません。たとえば`work_mem`の`4MB`を見ても、「この検索で4MB使った」とは読めません。実際に使った量は、ランキングの出力の`Memory`や`Memory Usage`のような、計画の中の値で読みます。

自分の環境の設定を記録し、どちらの領域に関わる値なのかを上の設定の表と対応させてみてください。この章では、この後`work_mem`を変えて、並べ替えの途中の値が作業用メモリに収まるときと、収まらないときを比べます。

:::details work_memの4MBを超えて使う場合
ランキングでは、`work_mem`は4MBなのに`HashAggregate`が8,281kBを使っていました。ハッシュを使う処理には、`work_mem`とは別の目安があるためです（第9章）。

また、`work_mem`は一つの接続が使うメモリ全体の上限でもありません。一つのSQLに並べ替えなどの処理が複数あれば、処理ごとに`work_mem`を目安にメモリを使うことがあります。この章の最後で、接続の数と掛け合わせた目安を見ます。[設定の公式説明](https://www.postgresql.org/docs/18/runtime-config-resource.html)にも対象が分けて書かれています。
:::

:::details ほかの用途のメモリ設定と「一時」の意味
一時テーブルは、接続内で一時的に使うために作るテーブルです。そのページには`temp_buffers`が関わります。Indexの作成や、不要な領域を回収するVACUUMの作業には、`maintenance_work_mem`が関わります。今回の環境で`SHOW`を実行すると、`temp_buffers`は8MB、`maintenance_work_mem`は64MBでした。

一時テーブルのページは、BUFFERSの`local`に現れます。一方、並べ替えの途中結果がメモリに収まらずに書き出される**一時ファイル**は、`temp read`や`temp written`に関係します。この章の後半で、この一時ファイルを観察します。第4・5章の観察用のテーブルは`CREATE TABLE`で作った通常のテーブルなので、`local`ではなく`shared`に現れます。
:::

## 新しい読了記録を上にしたい

前章の小さな計画（`ORDER BY title LIMIT 3`）には`Sort`がありませんでした。題名のIndexが、求める順にレコードを渡していたからです。読了記録には、日時順のIndexがまだありません。

今度は、Indexで順序を得られない読了記録の並べ替えを、サービスの画面で考えます。作るのは「最近読み終えた記録の一覧」です。記録が入っている順と、日時の新しい順は同じとは限りません。まずは少ない件数で考えます。

![入っている順の4件を、新しい日時の順に並べ直す。日時が同じ2件は本の番号順になる](/images/postgresql-query-journey/07-recent-records.png)
*日時が同じ2件は、本の番号順に並びます（説明のための場面。実際の200万件に同じ日時の記録はありません）。*

新しい順に返す依頼は、こう書きます。

```sql
SELECT book_id, finished_at
FROM reading_records
ORDER BY finished_at DESC, book_id ASC;
```

`DESC`は大きい値から、`ASC`は小さい値からです。日時が同じ場合は本の番号順にします。

## 大きさを比べて順序を作る

説明用に、日時を数字へ置き換えます。数字が大きいほど新しいとします。8、3、6、1の4枚のカードが届いたとき、どう並べ替えれば8、6、3、1になるでしょうか。手元でカードを動かしてみてください。

一つの方法は、基準にするカードを1枚選び、ほかのカードをそれより大きいか小さいかで分けることです。ここでは、先頭の8、真ん中の6、末尾の1のうち、真ん中の大きさの6を基準にします。8、3、1を6と1回ずつ比べると、大きい側は8、小さい側は3と1です。これで「8」「6」「3と1」の順に三つのグループが並びます。

8は1枚なので、もう動かしません。「3と1」のグループでは、3を基準にして1と比べ、1を小さい側へ置きます。すべてのグループが1枚になったところで左から読むと、8、6、3、1です。

図で、①〜③の手順と、それぞれで比べた回数を追ってください。

![8・3・6・1から基準の6を選び、6と3回比べて「8」「6」「3と1」に分け、「3と1」を3で分けると8・6・3・1に並ぶ](/images/postgresql-query-journey/07-quicksort-cards.png)
*比較の札で、②では基準の6と3回、③では3と1回比べたことを見てください（考え方を見るための4枚の例）。*

最後に、分けたグループ同士を合わせ直す手間はありません。分けた時点で、大きい側のどのカードも基準より大きく、小さい側のどのカードも基準より小さいからです。グループの中だけを並べれば、グループ同士の順序はもう決まっています。このように、基準で分けることを繰り返して並べる方法を**クイックソート**と呼びます。

比べる回数も数えてみます。一度分けるたびに、グループの中のカードを基準と1回ずつ比べるので、分ける段ごとに比べる回数は合わせて件数`n`程度です。基準がグループをほぼ半分ずつに分ければ、段の数は`log n`程度で済みます。そのため、平均的な比較回数の増え方は`O(n log n)`になります。

ただし、基準がいつもグループの端の値だと、片側にカードが寄って段の数が増えます。そこでPostgreSQLは、分ける並びが大きいときは、先頭・真ん中・末尾の三つの値（さらに大きいときは九つの値）のうち真ん中の大きさのものを基準に選びます。6枚以下の小さな並びは、基準で分けずに、隣どうしを比べて入れ替えながら並べます（[ソート処理のソース](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/include/lib/sort_template.h)）。上の4枚の例は、分け方を見るためのものです。

## Sortを観察する

全レコードを画面へ流すと、測った時間に表示や転送の時間も混ざります。そこで、ここでは実行計画を通して処理を観察します。まず、作業用メモリを64MBに増やして、並べ替えがメモリの中で終わるようにします。

```sql
SET work_mem = '64MB';
```

この設定は、いまのpsqlの接続だけに効きます。接続し直した場合は、共通設定の後に再設定してください。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT book_id, finished_at
FROM reading_records
WHERE finished_at >= timestamp '2026-09-14'
  AND finished_at < timestamp '2026-09-21'
ORDER BY finished_at DESC, book_id ASC;
```

読了記録200万件のうち、指定した1週間の記録を並べ替えます。次は、2026年9月22日にPostgreSQL 18.6で得られた実行結果です。実行計画の見出しと罫線は省いています。

```sql:実行結果
Sort  (cost=88387.00..89643.06 rows=502425 width=16) (actual time=182.059..207.760 rows=499998.00 loops=1)
  Sort Key: finished_at DESC, book_id
  Sort Method: quicksort  Memory: 27913kB
  Buffers: shared hit=10811
  ->  Seq Scan on reading_records  (cost=0.00..40811.00 rows=502425 width=16) (actual time=0.022..80.506 rows=499998.00 loops=1)
        …
        Rows Removed by Filter: 1500002
        Buffers: shared hit=10811
…
Execution Time: 223.929 ms
```

`Sort`の近くで、次の項目を探します。

| 項目 | 調べること |
| --- | --- |
| `Sort Key` | 何を基準に並べたか |
| `Sort Method` | どの方法を使ったか |
| `Memory`や`Disk` | 作業で使った量 |
| 子の`actual rows` | 何件を受け取ったか |

まずは「どの段で何件を受け取り、どんな方法を使ったか」を読むことに集中します。

### 200万件を調べ、499,998件を並べた

まず、下側の`Seq Scan`を見ます。`actual`の中の`rows=499998.00`が、期間の条件に合い、`Seq Scan`が次の処理へ渡したレコード数です。`Rows Removed by Filter: 1500002`は、条件に合わず除外したレコード数です。今回は`loops=1`なので、そのまま足せます。

足すと、499,998件＋1,500,002件＝2,000,000件です。テーブルの200万件を調べ、そのうち約4分の1を次の`Sort`へ渡しています。

上側の`Sort`でも、`actual`の`rows`は499,998です。この段階では期間の絞り込みが済んでいるので、並べ替えるのは200万件すべてではなく、対象週の499,998件です。`Sort Key`は日時の降順、同じ日時なら本の番号の昇順という、SQLの指定に対応しています。

なお、`cost`と同じ括弧にある`rows=502425`は実行前の見積もりです。実際に数えた499,998件と区別して読みます。見積もりの作り方は第10章で扱います。

### 今回の並べ替えは、メモリに収まった

`Sort Method: quicksort  Memory: 27913kB`から、今回はクイックソートを使い、作業に27,913kBのメモリを使ったことが分かります。4枚のカードで追ったのと同じく、基準で分けることを繰り返して499,998件を並べています。27,913kBは約27MBなので、設定した`work_mem = '64MB'`の範囲に収まっています。64MBを設定したからといって、64MBすべてを使ったわけではありません。

この出力には`Disk`や`temp read/written`がありません。今回のSortは、途中結果を一時ファイルへ出さずに処理できています。次の実験では、同じレコード数のまま作業用メモリを減らし、この部分がどう変わるかを確かめます。

図で、200万件のうちSortへ渡ったレコードの割合と、Sortが使ったメモリを見てください。

![200万件の帯のうち4分の1の499,998件がSortへ渡り、残りの1,500,002件は除外された。Sortはquicksortで27,913kBを使い、work_memの64MBに収まった](/images/postgresql-query-journey/07-sort-bands.png)
*帯の長さで、テーブルの200万件と、Sortへ渡した499,998件を比べてください（件数とメモリは実測）。*

### 223.929msは、ソートだけの時間ではない

`Execution Time: 223.929 ms`は、この実行計画全体の実行時間です。テーブルを読んで期間で絞り込む処理も含まれるので、「約224msかけて並べ替えた」とは言えません。また、通常の`SELECT`で約50万件を画面に表示し終わるまでの時間でもありません。

親の実行時間には、子を動かす時間も含まれます。`Buffers`も同じで、`Sort`の`shared hit=10811`は、子の`Seq Scan`がテーブルを読んだときのアクセスを含んだ値です。親子の値を足して合計にしないでください。

実行時間やバッファの親子関係は、[PostgreSQL 18のEXPLAINの説明](https://www.postgresql.org/docs/18/using-explain.html)でも確認できます。

## 作業用メモリに収まらないとき

8、3、6、1の4枚を並べたいのに、机には2枚しか置けないとします。2枚ずつ机で並べて別の場所へ置き、最後に合流させれば、4枚の並びを作れます。この方法を**外部ソート**と呼びます。

このたとえでは、机は`work_mem`で決まる作業用メモリ、置ききれないカードの置き場は一時ファイルに当たります。DBも、並べ終えたまとまりを一時ファイルへ書き、最後に読み戻して合流させます。

![作業用メモリに2枚ずつ入れて並べたまとまりを一時ファイルへ書き出し、二つのまとまりを少しずつ読み戻して合流し、8・6・3・1にする](/images/postgresql-query-journey/07-external-sort.png)
*並べたまとまりを一時ファイルへ書き出し、少しずつ読み戻して合流します（外部ソートを説明するための図。まとまりの数と大きさは縮めています）。*

書き出す前に並べておくのは、最後の合流を軽くするためです。並んだまとまり同士なら、次に出す値は、それぞれのまとまりの先頭を比べるだけで決まります。次の図で、この合流を比べる回数まで追ってください。1段目で、机に載る2枚ずつを並べて、まとまり（8、3）と（6、1）を作ります。2段目で、二つのまとまりの先頭同士を比べ、大きいほうを出していきます。

![8・3・6・1を2枚ずつ並べてまとまりを二つ作り、二つのまとまりの先頭同士を3回比べて合流し、8・6・3・1にする。比較は合わせて5回で2段](/images/postgresql-query-journey/07-merge-cards.png)
*1段目は作業用メモリの中で2枚ずつ並べる段、2段目は並べたまとまりの先頭同士を比べて合流する段です。2段目では、比べるたびに1枚が決まって出ていきます（説明するための図）。*

このように、並べたまとまりを合流させて大きな並びを作る方法を**マージソート**と呼びます。外部ソートの最後の合流は、このマージソートの合流です。

実際のソートでも、使えるメモリを少なくして比べてみます。

```sql
SET work_mem = '64kB';
```

同じ`EXPLAIN (ANALYZE, BUFFERS)`をもう一度実行します。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT book_id, finished_at
FROM reading_records
WHERE finished_at >= timestamp '2026-09-14'
  AND finished_at < timestamp '2026-09-21'
ORDER BY finished_at DESC, book_id ASC;
```

2026年9月25日、PostgreSQL 18.6での実行結果です。本100万冊・読了記録200万件、並列実行とJITは無効です。

```sql:実行結果
Sort  (cost=122183.71..123431.54 rows=499134 width=16) (actual time=289.741..325.654 rows=499998.00 loops=1)
  …
  Sort Method: external merge  Disk: 12784kB
  Buffers: shared hit=9451 read=1360, temp read=6367 written=6793
  ->  Seq Scan on reading_records  (cost=0.00..40811.00 rows=499134 width=16) (actual time=0.019..115.397 rows=499998.00 loops=1)
…
```

`Sort Method`が`external merge`になり、`temp read=6367 written=6793`が現れました。子のSeq Scanが渡す499,998件は変わらず、並べ替えの途中で一時ファイルを使っています。`external merge`は、名前のとおり、外部ソートでまとまりを合流させる方法です。時間の増減はキャッシュや実行順にも左右されるので、まず方式と一時ファイルの有無を比べます。

二つの出力の方式と作業量を並べると、次のようになります。

| work_mem | Sort Methodの出力 | 作業量の表示 |
| --- | --- | --- |
| 64MB | `quicksort` | `Memory: 27913kB` |
| 64kB | `external merge` | `Disk: 12784kB` |

### まとまりは428個でき、6個ずつ合流した

図のまとまりは二つでしたが、今回の実行ではいくつできたのでしょうか。開発者向けの設定`trace_sort`で並べ替えの途中経過を出して確かめると（下の補足）、作業用メモリで並べて書き出したまとまりは428個でした。一つひとつのまとまりは、メモリの中でクイックソートを使って並べています。

作業用メモリが64kBと小さいので、今回は一度に合流できるのが6個でした。そこで、428個を6個ずつ合流して72個にし、72個を12個に、12個を2個にまとめ、最後の2個を合流しながら結果を返していました。図のように一度で合流するのではなく、何回かに分けて合流しています。

途中の合流では、合流した結果をまた一時ファイルへ書き、次の合流で読み戻します。`Disk: 12784kB`は、このソートが一時ファイルに使った領域の大きさです。一方、`temp read/written`は、読み書きの累計をブロック数で数えた値です。ここでのブロックはページと同じ8kBの単位で、ブロック数に8kBを掛けると量になります。同じレコードを合流のたびに書き直して読み戻し、空いた領域は使い回すので、書き込みの累計`written=6793`（約53MB）は、使った領域の12,784kBより大きくなります。

`shared`はテーブルやIndexのページに関わる値、`temp`は今回のような一時ファイルに関わる値です。第5章で見た共有バッファ（テーブルやIndexのページ）と、作業用メモリからあふれた一時ファイルが、ここでは`shared`と`temp`という別々の数字で表れます。なお、一時テーブルのページは、どちらでもなく`local`に表れます（この章の最初の節の補足）。

:::details まとまりの数を確かめる
`trace_sort`をオンにし、ログをpsqlの画面に出すように`client_min_messages`を`log`にしてから、同じ`EXPLAIN (ANALYZE, BUFFERS)`を実行します。`work_mem`は64kBのままです。

```sql
SET trace_sort = on;
SET client_min_messages = log;
EXPLAIN (ANALYZE, BUFFERS)
SELECT book_id, finished_at
FROM reading_records
WHERE finished_at >= timestamp '2026-09-14'
  AND finished_at < timestamp '2026-09-21'
ORDER BY finished_at DESC, book_id ASC;
RESET client_min_messages;
RESET trace_sort;
```

2026年9月28日に実験用DBで測ったときの、実行計画より前に出たログの抜粋です。各行の後ろのCPU時間は省いています。`Disk: 12784kB`と`temp read=6367 written=6793`は、上の出力と同じでした。

```sql:実行結果
…
LOG:  worker -1 switching to external sort with 6 tapes
LOG:  worker -1 starting quicksort of run 1
…
LOG:  worker -1 finished writing run 428 to tape 2
…
LOG:  starting merge pass of 428 input runs on 6 tapes, 1 KB of memory for each input tape
LOG:  starting merge pass of 72 input runs on 6 tapes, 1 KB of memory for each input tape
LOG:  starting merge pass of 12 input runs on 6 tapes, 6 KB of memory for each input tape
LOG:  starting merge pass of 2 input runs on 2 tapes, 24 KB of memory for each input tape
LOG:  performsort of worker -1 done (except 2-way final merge)
LOG:  external sort of worker -1 ended, 1598 disk blocks used
```

`run`がまとまり、`merge pass of 428 input runs`が「428個のまとまりを合流する」段です。`tape`は、まとまりを書き込む一時ファイルの中の置き場所で、6本あるので6個ずつ合流します。最後の`1598 disk blocks`に8kBを掛けると12,784kBで、出力の`Disk`と一致します。一度に合流できる数は作業用メモリの大きさから決まり、作業用メモリがどれだけ小さくても6個は合流できます（[外部ソートのソース](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/utils/sort/tuplesort.c)の`tuplesort_merge_order`）。
:::

:::details 二つの出力を見比べるときの注意
1回目の出力と比べると、`Sort`の`cost`と、見積もりの`rows`も違います。`cost`が大きくなったのは、一時ファイルを使う並べ替えになると見込んだためです。見積もりの`rows`（502,425と499,134）が違うのは、測った日が違い、見積もりの元になる統計情報（第10章）が同じではないためです。

quicksortは9月22日、external mergeは9月25日の別の測定なので、時間差の比較には使いません。どちらもPostgreSQL 18.6、読了記録200万件、対象週499,998件で、並列実行とJITは無効です。

`Memory`と`Disk`は、保存場所もデータの形式も違う量なので、引き算して節約量とはしません。
:::

## メモリを増やせば、いつも解決？

`work_mem`を増やすと、メモリ不足で生じた一時ファイルを減らせる場合があります。ただし、`work_mem`は一つのソートなどが使う作業用メモリの基準です。複数の接続でソートが同時に動けば、それぞれが作業用メモリを使います。10接続でソートが一つずつ動けば合計で`work_mem`の10倍程度、一つのSQLで二つずつ同時に動けば20倍程度を使う可能性があります。これはソートの作業領域の目安で、プロセス全体のメモリ使用量の上限ではありません。

このSortは、SQLを受け取った接続のバックエンドプロセスが、自分の作業用メモリの中で行いました。第6章の補足で見たように、各接続のプロセスがそれぞれこの領域を持ち、共有バッファは全プロセスで一つです。そのため、`work_mem`を「DB全体でここまで」とは読めません。

また、並べ替え以外に時間がかかっているなら、ソート用のメモリを増やしても、その処理は減りません。第12章の最後の課題では、ランキングのSQLを`work_mem`だけ変えて測り、一時ファイルが消えても速くならない例を見ます。

実験後は、後続章の基準へ戻します。

```sql
SET work_mem = '4MB';
```

課題です。Sortがすでにメモリ内で済んでいる場合、「一時ファイルをなくすためにwork_memを増やす」という説明は成り立つでしょうか。64MBのときの`Sort Method`の表示を根拠に考えてください。

## まとめ

- `Sort Method`と`Memory`・`Disk`で、作業用メモリの中で並べたか、一時ファイルにあふれたかを読む。
- `work_mem`を増やしても、並べるレコード数は減らない。時間の多くが並べ替えより前の処理にあるなら、扱う件数を減らす方が効く。
