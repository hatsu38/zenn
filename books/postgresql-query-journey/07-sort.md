## この章で分かること

読了記録を新しい順に並べるために、どんな処理が必要でしょうか。少数の値の比較から始めて、実行計画のSortと対応させます。`work_mem`を変えて、メモリ内で終わる並べ替えと、一時ファイルを使う並べ替えを観察します。最後に、作業用メモリを第6章のプロセスの配置に位置付け直し、並べ替えが遅いときに何を確認すべきかを整理します。

## 新しい読了記録を上にしたい

前章の計画には`Sort`がありませんでした。題名のIndexが、求める順に行を渡していたからです。読了記録には、日時順のIndexがまだありません。

今度は、Indexで順序を得られない読了記録の並べ替えを、サービスの画面で考えます。作るのは「最近読み終えた記録の一覧」です。記録が入っている順と、日時の新しい順は同じとは限りません。まずは少ない件数で考えます。

![読み終えた順に、並べたい](/images/postgresql-query-journey/07-recent-records.png)
*学ぶきっかけを描く、説明用の場面。*

新しい順に返す依頼は、こう書きます。

```sql
SELECT book_id, finished_at
FROM reading_records
ORDER BY finished_at DESC, book_id ASC;
```

`DESC`は大きい値から、`ASC`は小さい値からです。日時が同じ場合は本の番号順にします。

## 大きさを比べて順序を作る

説明用に、日時を数字へ置き換えます。数字が大きいほど新しいとします。8、3、6、1の4枚のカードが届いたとき、どう並べ替えれば8、6、3、1になるでしょうか。手元でカードを動かしてみてください。

次は、二つの小さな並びを作って合流する模型です。PostgreSQLがメモリ内で使う方法は、後で実行計画から確かめます。この図は「比較して順序を作る」という点だけを示します。

![二つの並びを、比べながら合流する](/images/postgresql-query-journey/07-merge-cards.png)
*比較の模型で、PostgreSQLの実装そのものではありません。*

並べ替えには、行を一度ずつ読む処理に加えて、値を比べて置く順序を決める処理があります。値を比べて並べる方法（比較ソート）では、比較の回数が件数`n`に対しておおむね`n log n`に比例して増えます。これを`O(n log n)`と書きます。行数が2倍になると、比較は2倍より少し多く必要です。

## Sortを観察する

全行を画面へ流すと、測った時間に表示や転送の時間も混ざります。そこで、ここでは実行計画を通して処理を観察します。

```sql
SET max_parallel_workers_per_gather = 0;
SET jit = off;
SET work_mem = '64MB';
```

```sql
SET
SET
SET
```

この設定は、いま接続しているpsqlのセッションに適用されます。接続し直した場合は、実験前に再設定してください。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT book_id, finished_at
FROM reading_records
WHERE finished_at >= timestamp '2026-09-14'
  AND finished_at < timestamp '2026-09-21'
ORDER BY finished_at DESC, book_id ASC;
```

読了記録200万件のうち、指定した1週間の記録を並べ替えます。次は、この条件で得られた実行結果です。実行計画の見出しと罫線は省いています。

```sql
Sort  (cost=88387.00..89643.06 rows=502425 width=16) (actual time=182.059..207.760 rows=499998.00 loops=1)
  Sort Key: finished_at DESC, book_id
  Sort Method: quicksort  Memory: 27913kB
  Buffers: shared hit=10811
  ->  Seq Scan on reading_records  (cost=0.00..40811.00 rows=502425 width=16) (actual time=0.022..80.506 rows=499998.00 loops=1)
        Filter: ((finished_at >= '2026-09-14 00:00:00'::timestamp without time zone) AND (finished_at < '2026-09-21 00:00:00'::timestamp without time zone))
        Rows Removed by Filter: 1500002
        Buffers: shared hit=10811
Planning Time: 0.083 ms
Execution Time: 223.929 ms
```

`Sort`の近くで、次の項目を探します。

| 項目 | 調べること |
| --- | --- |
| `Sort Key` | 何を基準に並べたか |
| `Sort Method` | どの方法を使ったか |
| `Memory`や`Disk` | 作業で使った量 |
| 子の`actual rows` | 何行を受け取ったか |

まずは「どの段で何行を受け取り、どんな方法を使ったか」を読むことに集中します。

### 200万件を調べ、499,998件を並べた

まず、下側の`Seq Scan`を見ます。`actual`の中の`rows=499998.00`が、期間の条件に合い、`Seq Scan`が次の処理へ渡した行数です。`Rows Removed by Filter: 1500002`は、条件に合わず除外した行数です。今回は`loops=1`なので、そのまま足せます。

足すと、499,998行＋1,500,002行＝2,000,000行です。表の200万行を調べ、そのうち約4分の1を次の`Sort`へ渡しています。

上側の`Sort`でも、`actual`の`rows`は499,998です。この段階では期間の絞り込みが済んでいるので、並べ替えるのは200万行すべてではなく、対象週の499,998行です。`Sort Key`は日時の降順、同じ日時なら本の番号の昇順という、SQLの指定に対応しています。

なお、`cost`と同じ括弧にある`rows=502425`は実行前の見積もりです。実際に数えた499,998行と区別して読みます。見積もりの作り方は第10章で扱います。

### 今回の並べ替えは、メモリに収まった

`Sort Method: quicksort  Memory: 27913kB`から、今回はクイックソートを使い、作業に27,913kBのメモリを使ったことが分かります。約27.3MiBで、設定した`work_mem = '64MB'`の範囲に収まっています。64MBを設定したからといって、64MBすべてを使ったわけではありません。

この出力には`Disk`や`temp read/written`がありません。今回のSortは、途中結果を一時ファイルへ出さずに処理できています。次の実験では、同じ行数のまま作業用メモリを減らし、この部分がどう変わるかを確かめます。

### 223.929msは、ソートだけの時間ではない

`Execution Time: 223.929 ms`は、この実行計画全体の実行時間です。表を読んで期間で絞り込む処理も含まれるので、「約224msかけて並べ替えた」とは言えません。また、通常の`SELECT`で約50万行を画面に表示し終わるまでの時間でもありません。

親の実行時間には、子を動かす時間も含まれます。`Buffers`も同じで、`Sort`の`shared hit=10811`は、子の`Seq Scan`が表を読んだときのアクセスを含んだ値です。親子の値を足して合計にしないでください。

実行時間やバッファの親子関係は、[PostgreSQL 18のEXPLAINの説明](https://www.postgresql.org/docs/18/using-explain.html)でも確認できます。

## 作業用メモリに収まらないとき

100枚のカードを並べたいのに、机には10枚しか置けないとします。少しずつ並べて別の場所へ置き、最後に合流させれば、大きな並びを作れます。この方法を外部ソートと呼びます。

この模型で、机は`work_mem`で決まる作業用メモリ、置ききれないカードの置き場は一時ファイルに当たります。DBも、並べ終えたまとまりを一時ファイルへ書き、最後に読み戻して合流させます。

![メモリに収まらないときの並べ替え](/images/postgresql-query-journey/07-external-sort.png)
*外部ソートの模型。まとまりの個数と容量は模式的です。*

実際のソートでも、使えるメモリを少なくして比べてみます。

```sql
SET work_mem = '64kB';
```

同じ`EXPLAIN (ANALYZE, BUFFERS)`をもう一度実行します。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT book_id, finished_at
FROM reading_records
WHERE finished_at >= timestamp '2026-09-14'
  AND finished_at < timestamp '2026-09-21'
ORDER BY finished_at DESC, book_id ASC;
```

`external merge`や`Disk`、`temp read/written`が現れたか比べてください。結果は環境やデータで変わるので、自分の出力で確かめてください。時間が何倍になるかは、ここでは予告しません。

次の比較表は、本書の原稿検証時に別途採取したログの抜粋です。2026年9月22日、DockerのPostgreSQL 18.6、並列実行とJITは無効です。上に載せた2026年9月23日の実行結果とは別の測定ですが、同じ200万件のサンプルを使い、対象週の入力は499,998行でした。

| work_mem | Sort Methodの出力 | 作業量の表示 |
| --- | --- | --- |
| 64MB | `quicksort` | `Memory: 27913kB` |
| 64kB | `external merge` | `Disk: 12784kB` |

`external merge`は、図の外部ソートと同じく、並べたまとまりを一時ファイルへ書き出し、最後に合流させる方法です。`Disk: 12784kB`は、その一時ファイルに書いた量を示します。MemoryとDiskは別の場所にある、形式の違う量なので、この二つを引き算して節約量とはしません。`temp read/written`の値はこの抜粋に含めていないので、自分の出力で確かめてください。

`shared`は表やIndexのページに関わる値、`temp`は今回のような一時ファイルに関わる値です。第5章で見た共有バッファ（表やIndexのページ）と、作業用メモリからあふれた一時ファイルが、ここでは`shared`と`temp`という別々の数字で表れます。

## メモリを増やせば、いつも解決？

`work_mem`は、一つのソートやハッシュ処理が使える上限です。`work_mem`を増やせば、一つの処理の一時ファイルは減らせます。しかし、接続ごとのプロセスがそれぞれこの上限まで使えるので、同時に10人が並べ替えれば1接続分の上限の10倍、ソートが二つあるSQLなら20倍まで使う可能性があります。

このSortは、SQLを受け取った接続のバックエンドプロセスが、自分の作業用メモリの中で行いました。第6章の配置では、各接続のプロセスがそれぞれこの領域を持ち、共有バッファは全プロセスで一つです。そのため、`work_mem`を「DB全体でここまで」とは読めません。

また、並べ替え以外に時間がかかっているなら、ソート用のメモリを増やしても、その処理は減りません。

実験後は、後続章の基準へ戻します。

```sql
SET work_mem = '4MB';
```

課題です。Sortがすでにメモリ内で済んでいる場合、「一時ファイルをなくすためにwork_memを増やす」という説明は成り立つでしょうか。64MBのときの`Sort Method`の行を根拠に考えてください。

この章のSortは、対象週の499,998行すべてに順位を付けました。ところが、最近の記録の画面に表示するのは新しい20件だけです。残りの約50万行の順位まで決める必要はあるのでしょうか。次章では`LIMIT 20`を付けて、並べ替えの処理がどう変わるかを調べます。
