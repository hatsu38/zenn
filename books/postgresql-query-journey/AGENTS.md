# この本の執筆方針

## 読書体験

- 一つのサービスを育てる物語に、読者が予想とSQLの実験で参加する。
- 技術を紹介する前に、利用者や開発者の具体的な困りごとを置く。「困る → 原因を絞る → まだ分からないことが残る → 観察する道具や仕組みが必要になる」という動機を作る。架空の障害や調査は実測・実体験と混同させない。
- 序章の題材は「今週よく読まれた本ランキング」。読了記録を表示時に本ごとに集計する。計算済みスコアを取り出す旧試作とは区別し、集計・JOIN・並べ替えの学びを通して後続章で回収する。
- 序章では「はじめに」、サービスの紹介、読者への問い、本全体の学び方を伝える。ランキングの答えや詳しい実験結果は後の章で回収する。
- 第1章「SQLの動きを観察する道具を手に入れる」で、環境構築・データ準備・EXPLAINとEXPLAIN ANALYZEの初歩を案内する。
- 初期の原稿は、面白さと流れを早くレビューできる分量にする。

## 本全体の図解方針

- 文章・図解・SQLを組み合わせて、見やすく分かりやすい本にする。全章でこの方針を適用する。
- 技術の仕組みを説明する図は各章2〜3枚程度を目安にする。サービスの場面を描く絵や、章の入口で全体を見渡すグラレコは、読者の理解に役立つ場所へ追加する。枚数の上限で導入の絵を省かない。SVGからの掲載画像とMermaidを合計して数え、実行結果のコード枠や表は別に扱う。枚数合わせの図は追加せず、同じ説明の重複は整理する。
- 各図には全体像・中心となる仕組み・変化や比較などの役割を持たせる。複数コマで一つの問いを説明する図は1枚とするが、一枚に詰め込んで枚数を減らさない。
- テーブルの構造や関連は関係図、処理やデータの流れは矢印、木構造や状態変化は具体的な値を入れた図で示す。編集可能なSVGを原本にしてPNGを掲載する。
- 一つの図は一つの問いに答える。図の直前に見る目的、直後に読み取れることを短く書く。
- 読者に予想してもらう場面では、答えを示す図を予想の後に置く。
- 図に合わせて不要な設定やテーブルを増やさない。実験SQLとER図の列・型・キー・関連を一致させる。
- 実測した結果の図と、理解のために単純化した説明用の図を明確に区別する。件数・メモリ量・I/O回数を混同しない。
- 「模型」という語は、本文・キャプション・図・補助文書で使わない（2026-09-25のユーザー指定）。説明用の図のキャプションには「説明するための図」と書き、図の札は実測の図にだけ付ける。
- フローの矢印が何を意味するかを明示する。実行計画では原則として行の流れを示し、要求の向きとは区別する。
- スマートフォンでも追えるよう、縦方向を基本に、ラベルとノード数を絞る。色だけで意味を伝えない。
- 文章の言い換えだけになる装飾的な図を増やさない。対応関係や数値の比較が中心なら表も使う。
- Mermaidの構文とプレビューでの表示を確認する。表示確認ができない場合は、その範囲を報告する。

## SQLと実行結果の掲載

- SQLの直後に、実際に返った表や実行計画も掲載する。読者が自分の結果と見比べられる構成にする。
- 入力するSQLと出力結果は、それぞれ別のsqlコードブロックにする（2026-09-23のユーザー指定）。出力もsql表記にするが、入力と混同しないよう直前の文章で実行結果と明示する。入力欄へプロンプトや出力を混ぜない。
- 前に出たSQLをもう一度実行させるときも、その場にSQLを載せる（2026-09-25のユーザー指定）。「先ほどのSQL」「同じSQL」だけでは、読者が前へ戻って探すことになるため。psqlの接続コマンドなど、実行させるコマンドも同じ扱いにする。同じ接続で効いたままの`SET`は繰り返さない。
- 出力がどのデータ量・条件によるものかを示す。ユーザー提供の実行結果と新たな実測を混同しない。
- 出力の後に、見る列・行と、そこから分かることを説明する。

- 実行結果の後は、見る値→今回読み取れる事実→処理の仕組みとの対応、の順で説明する。必要に応じて具体的な結論を小見出しにする。
- 「速くなった」で終えず、探し方・行数・アクセス量のどれが変わったかを示す。原因未特定の時間差と、計画や仕事量の変化を分ける。
- 実測していない性能差や因果関係は断定しない。既存の説明と重複する定型のまとめは増やさず、読者が自分の出力から同じ判断をできる文章にする。
