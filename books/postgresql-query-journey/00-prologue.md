この本は、ランキングが遅いという疑問から始まります。小さなSQLで仕組みを確かめ、最後に同じランキングの改善を考えます。まずは、その道のりを一枚の絵で見てください。

![ランキングの疑問から、小さなSQLでの実験、探索、並べ替え、結合の理解を経て、改善の判断へ戻る](/images/postgresql-query-journey/00-book-sketch.png)
*本全体の道のり。各章で、この中の仕組みを一つずつ確かめます。*

## はじめに

SQLで欲しいデータを取り出せても、その処理に時間がかかる理由までは分からないことがあります。索引（インデックス）を追加して速くなったとしても、何が変わったのかを説明するのは難しいものです。

たとえば、100万冊の中から1冊を探すSQLを考えてみます。返ってくるのは1行ですが、その1行を見つけるまでに何行を調べているのでしょうか。索引を使うと、調べ方はどう変わるのでしょうか。

『いつものSQLで学ぶデータ構造とアルゴリズム』は、こうした疑問を、PostgreSQLで小さな実験をしながら確かめていく本です。本を探す、読了記録を数える、上位20冊を並べる。身近な処理の中に、探索、木構造、並べ替えといった仕組みが出てきます。

その仕組みが実際に動くには、データを保存する場所や、計算に使うメモリも必要です。本書では、データ構造とアルゴリズムに加えて、PostgreSQLのプロセス、ファイル、メモリにも目を向けます。SQLの実行手順を表示する`EXPLAIN`を手がかりに、それぞれをつなげて読んでいきます。

読み終えたときには、「このSQLでは、ここで多くの行を調べている」「この変更なら、その処理を減らせそうだ」と、実行結果を示しながら説明できるようになってほしいと考えています。速くする方法を知るだけでなく、その方法が今回の条件に合うかを自分で確かめられる。そこまでを目標にします。

## この本を読んでほしい方

`SELECT`や`WHERE`でデータを取り出したことはあるけれど、データベースの内側はまだよく分からない。そんな方を想定しています。次のような疑問があれば、本書の実験と重なるはずです。

- SQLは書けるけれど、なぜ遅いのかをどう調べればよいか分からない。
- B-treeやハッシュという言葉は知っているけれど、普段の開発でどこに出てくるのかがつかめない。
- `EXPLAIN`を表示してみたものの、数字や処理名をどう読めばよいか分からない。
- ネットやAIから改善案を得ても、採用してよいかを判断する根拠が欲しい。

高度な数学や、PostgreSQLの内部実装を知っている必要はありません。仕組みを説明するときは、少数のカードや行を使った図から始めます。`JOIN`や集計などのSQLも、実験で何を求めているかを説明しながら進めます。

手元で試すときは、ターミナルでコマンドを入力します。Dockerを使った環境の準備と、SQLを入力する場所は第1章で案内します。本に載せた図と実行結果を先に読み、気になった実験だけを後から試す読み方でも構いません。

## 題材は、読書記録サービス

本書では、本を探して読了記録を残せるサービスを題材にします。利用者が読み終えた本と日付を記録し、その記録をもとに「今週よく読まれた本」を表示するサービスです。

ランキングには、対象の週の読了記録が多い本から順に20冊を載せます。

![本の読了を記録し、今週よく読まれた本をランキングで見る読書記録サービス](/images/postgresql-query-journey/00-reading-service.png)
*架空の画面イメージ。図の書名と件数は説明用で、後のSQL実行結果とは異なります。*

それなら、読了記録を本ごとに数えて、多い順に20冊並べればよさそうです。ところが、データを増やして試すと、結果が返るまで数秒待つようになりました。

このランキングを、本書を通して考える題材にします。最初から複雑なSQL全体を読み解くのは難しいので、まずは「1冊を探す」ところまで小さく分けます。探す、並べる、組み合わせるという処理を順に学び、最後にランキングへ戻ってきます。

:::message
サービスの場面は架空です。実際のサイトで起きた障害ではありません。
:::

## ランキングに使う二つのテーブル

たとえば、本の一覧に次の2冊があるとします。

| 本の番号 | 題名 |
| --- | --- |
| 1 | 星の図鑑 |
| 2 | 海の図鑑 |

一方、読了記録には「どの本を、いつ読み終えたか」を書きます。

| 本の番号 | 読み終えた日 |
| --- | --- |
| 1 | 9月14日 |
| 2 | 9月15日 |
| 1 | 9月16日 |

本は2冊ですが、記録は3件です。星の図鑑は2件、海の図鑑は1件あります。この例では、読んだ**人数**ではなく、読了**記録の件数**を数えます。再読を別の記録として残せば、それも1件です。

本と読了記録を別々のカードにして並べてみます。線は「どの本の記録か」という対応です。同じ本に何枚の記録がつながるかを見てください。

![本の冊数と、読了記録の件数](/images/postgresql-query-journey/00-books-and-records.png)
*サンプルの2冊と3件で考える。*

`books`は本の一覧、`reading_records`は読了記録です。`book_id`を使って、本の番号`id`と対応させます。この実験では、記録の本の番号が本の一覧に存在するかをDBに確かめさせる設定（外部キー制約）は付けません。ただし、生成する記録の`book_id`は、どれも本の一覧にある番号になるように作ります（作り方は第1章）。

## 20冊を返すまで、約4.6秒

同じランキングを、小さいデータと大きいデータで調べた記録があります。

| 比較するもの | 小さいデータ | 大きいデータ |
| --- | ---: | ---: |
| 本 | 1,000冊 | 100万冊 |
| 読了記録 | 2万件 | 2,000万件 |
| 返す本 | 20冊 | 20冊 |
| SQLの経過時間・3回の中央値 | 2.140 ms | 4,553.647 ms |

`ms`はミリ秒です。1,000ミリ秒が1秒なので、右の値は約4.6秒です。返す本はどちらも20冊ですが、経過時間は約2,000倍に増えました。

ここで一度、予想してみてください。20冊を決めるためには、何件の記録を調べる必要があるでしょう。最初の20件だけでしょうか。それとも、もっと必要でしょうか。

:::message
約4.6秒は、過去にサンプルデータで測ったSQLの経過時間です。画面全体の表示時間ではなく、前の節の架空の場面とも別の数値です。
:::

:::details この数値を測った条件
2026年9月21日、Apple M1 Pro・32GiBメモリ、HomebrewのPostgreSQL 18.3で計測しました。本と記録は一時テーブルで、索引は本の主キーだけです。`work_mem=64MB`、並列実行とJITは無効にしました。

大きいデータの対象週には4,999,999件の記録がありました。psqlの`\timing`による3回の経過時間は4,630.241、4,553.647、4,531.875ミリ秒です。キャッシュを空にした測定ではありません。

元のSQLとログはリポジトリの`_drafts/sql-data-structures/experiments/weekly-ranking.sql`および`results/weekly-ranking-*-pg18.3-20260921.txt`にあります。

後続章は通常テーブルを使います。この値を、新しい実験の改善前の数値として直接比較しないでください。同じ環境で改めて測ります。
:::

## ランキングのSQLが求めている結果

ランキングのSQLは次のとおりです。いまは一文字ずつ覚えなくて大丈夫です。

```sql
SELECT b.id, b.title, count(*) AS read_count
FROM books AS b
JOIN reading_records AS r ON r.book_id = b.id
WHERE r.finished_at >= timestamp '2026-09-14'
  AND r.finished_at < timestamp '2026-09-21'
GROUP BY b.id, b.title
ORDER BY read_count DESC, b.id ASC
LIMIT 20;
```

このSQLを言葉にすると、次の依頼になります。

1. 9月14日0時以上、9月21日0時未満の記録を対象にする。
2. 同じ本の記録を数え、題名と一緒に返す。
3. 件数の多い順に並べ、同数なら本の番号が小さい順にする。
4. 上位20冊を返す。

対象週を固定したのは、いつ試しても同じデータを調べるためです。これはSQLが要求する結果の説明で、DB内部が必ずこの順番で処理するという意味ではありません。

### このSQLを試すには

環境とデータの準備は[第1章](01-explain-basics)で行います。まだ準備していなければ、ここではSQLを読むだけで進めてください。

準備済みなら、実験用リポジトリ `postgresql-structures-lab` のディレクトリで、**ターミナルに**次のコマンドを入力します。

```bash
docker compose exec db psql -X -U postgres -d reading_map
```

`reading_map=#` と表示されたら、Docker内のPostgreSQLに接続できています。**ここからはpsqlに**、上の`SELECT`から`LIMIT 20;`までを入力してください。最後の`;`まで入力すると実行されます。`reading_map=#`自体は入力しません。

第1章で用意する本100万冊と読了記録200万件のデータで実行した結果です。2026年9月23日、DockerのPostgreSQL 18.6で確認しました。先ほどの約4.6秒を測ったデータ量とは異なります。

### この20行から分かること

- `read_count`は、指定した週の読了記録の件数です。表示された20冊には、それぞれ2件の記録があります。読んだ人数を数えた値ではありません。
- どの本も件数が同じ2件なので、同数のときの指定`b.id ASC`によって、本の番号が小さい順に並んでいます。
- `(20 rows)`は20行返ったという意味です。調べた記録が20件だった、という意味ではありません。

この表から、どの20冊が選ばれたかは分かります。

## 改善する前に、時間のかかる処理を調べる

このランキングを速くする方法として、索引の追加や、あらかじめ読了記録を数えておく方法が考えられます。表示を20冊から10冊に減らす案もあるでしょう。

どの案を試すか決めるには、今のSQLが何に時間を使っているかを知る必要があります。記録を探す処理なのか、本ごとに数える処理なのか、それとも件数順に並べる処理なのか。結果の20行だけを見ても、そこまでは分かりません。

まず、結果が返るまでの処理を調べましょう。そのうえで、改善案によってどの処理を減らせるかを考えます。

次の図では、多くの読了記録から20冊を選ぶまでを一つの流れにしています。

![20冊を返すまでに、何をしている？](/images/postgresql-query-journey/00-ranking-question.png)
*処理量を調べる前の見取り図。行数の縮尺ではありません。*

`EXPLAIN`を使うと、PostgreSQLが選んだ処理手順を確認できます。その出力と実験結果を比べながら、検索、メモリの使い方、並べ替え、集計の仕組みを学びます。

## 本書の構成

本書は序章と12の章で構成しています。章が進むにつれて、一つのSQLを調べるための手がかりを増やしていきます。

| 章 | 扱うこと | 読み終えたときに確かめられること |
| --- | --- | --- |
| 第1章 | 実験環境とEXPLAINの基本 | 返した行数と、探す途中で調べた行数の違い |
| 第2〜3章 | 全件探索、LIMIT、B-treeの索引 | 1冊を返すために調べる量と、探す範囲の減らし方 |
| 第4〜6章 | ページ、メモリ、接続とプロセス | 減ったアクセスが何を読み、どこを共有する処理なのか |
| 第7〜9章 | 並べ替え、上位N件の選択、結合と集計 | ランキングを作る各処理と、メモリの使い方 |
| 第10〜11章 | 実行計画の選択、統計情報、更新と保守 | 計画の見積もりや、更新され続けるデータが実行にどう関わるか |
| 第12章 | ランキングの再調査 | ここまでの観察を使って、改善案を比較する方法 |

検索と索引の実験で疑問になったアクセス量を、ページやメモリの章で読み解きます。その知識を、続く並べ替えと結合にも使います。初めて読むときは、第1章から順に進むと、それぞれの関係を追いやすくなります。

本書では、実行計画を読むために必要な範囲で内部の仕組みを扱います。PostgreSQLのソースコード全体を追うことや、本番環境の運用や設定を網羅することまでは扱いません。小さな実験を重ねて、説明できることを一つずつ増やします。それが、実際の調査で次に何を確かめるかを考えるための土台になります。

## 図とSQLと実行結果を行き来する

各章では、まず具体的な疑問を置き、図で仕組みを考えてからSQLを試します。掲載した実行結果には、どの値を見ると何が分かるかを添えています。自分の結果と見比べるときも、時間だけでなく、処理の名前、行数、データへのアクセス量を追ってみてください。

同じSQLでも、データ量や設定、実行したときの状態によって結果は変わります。本に載っているミリ秒の値と一致させる必要はありません。予想と違ったら、まず条件を見比べます。そのうえで条件を一つ変え、説明が成り立つかを確かめます。

図のカードや矢印は、仕組みを考えるために単純化したものです。一方、実行結果の数値は、記載した条件で得られた観測値です。この二つを行き来しながら、「図ではこう考えたけれど、実際はどうなったか」を実行結果で確かめます。

## 第1章へ

ここでは、ランキングの改善策をまだ決めなくて大丈夫です。「索引を付けたい」「先に集計しておきたい」など、今の自分なら何を試したいか、一つ書き残しておいてください。第12章で戻ってきたときに、その案のどこを確かめればよいかを考え直します。

まずは、SQLの内側を観察する道具を用意しましょう。第1章では実験環境を作り、たった1冊を探すSQLから始めます。
