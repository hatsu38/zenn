## 2. 今の図の診断

五つの評価（2026-09-24、章ごとに全文と全図を確認）と、横断の計測から分かったこと。

| 原因 | 例 | 読者への影響 |

## 3. 図の四つの型

| 型 | 置く場所 | 描くもの | 描かないもの |
| --- | --- | --- | --- |
| 問い（場面の絵） | 章や節の入口 | その章の具体的な数字と、一つの問い | 答え、飾りの人物や表情、注意書き |
| 仕組み（説明するための図） | 説明の段落の直後 | 小さな値で追う動き。1コマに焦点は一つ | 実装の細部、別の問い |
| 観察（実測） | EXPLAINの実行結果の直後 | 行数に比例した帯、出力の項目名と数値、実測の札 | 実測していない内訳 |
| 比較（前後） | 条件を変えた結果の後 | 同じ配置で、違う所だけを強調 | 配置の違い（見比べを邪魔する） |

- 章の道のりや表の関係を示す全体像は、仕組みの型として扱う。
- 観察の型は今の本にほとんどない。第1・2・7・8・12章へ入れる。序章の「？」の図（`00-ranking-question`）と第12章の全体像を同じ枠組みにして、本の問い「結果は20行なのに、途中で何行を扱っているのか」を閉じる。
- 場面の絵13枚（第1〜12章の入口の12枚と、序章の`00-reading-service`）は問いの型にそろえる。人物を描く場合は、棚を指す・画面を待つなど、問いに関わる動作だけにする。

## 4. 共通の約束

### 4.1 部品

| 部品 | 見た目 | 意味 |
| --- | --- | --- |
| 行カード | 白い横長のカード。本は「番号・題名」、読了記録は「本番号・日付」 | 表の1行 |
| ページ枠 | 番号（「ページ0」など）を枠の中の上に書く枠。中に行カードを入れ、行カードより大きく描く。共有バッファの中のように小さく並べるときは、番号をタブに書く（部品見本の「表のページ」と「共有バッファ」） | 読み込みの単位（8kB） |
| Indexの項目 | 小さな正方形のキー＋「▸場所」 | Indexが持つ値と、行の場所 |
| 計画のノード | 角丸の箱。ノード名は出力と同じ字面で書く | EXPLAINの1行 |
| 量の帯 | 横長の帯。長さを行数に比例させ、数値と出典を書く | 扱った行数 |
| 共有バッファ | RAMの枠の中の大きな枠。中にページ枠を並べる | 接続どうしで共有するページの置き場所 |
| 作業用メモリ | 破線の枠（上限の目安）。処理ごとに一つ。中の薄い緑の塗り（値カードと同じ `.val`）は、使った量 | 並べ替えやハッシュの作業場所 |
| ストレージ | 下段の横長の枠（`.storage`：薄い紫の地に紫の線）。枠の中の左上に「ストレージ（SSDなど）」。中に表のファイル・WALのファイル・一時ファイルを、白い地に紫の線の箱（`.file`）で置き、箱の中に名前を書く。紫はこの二つにだけ使う | 電源が切れても残る場所 |
| 引き出し線 | 矢じりのない細い灰紺の線（`.leader`） | この値の枠が、どのノードの出力か |
| 問いの箱 | 最下段に横いっぱいの角丸の箱（x=24・幅592・高さ60）。地 `#fff0d3`、紺 `#243b50` の線2.5、太字の問い1文 | 問いの型の図の問い。地は焦点（`.hot`）と同じ見た目の薄い橙なので、線の色と太さ（紺2.5／橙4）と位置で見分ける。中に `.hot` を置かない。ほかの箱にこの地を使うのは、`00-book-sketch` の序章と第12章のように、始まりと戻り先の対を示すときだけ（2026-09-25、段階Cの全体レビューで決めた） |
| 画面の枠 | 白い地・紺 `#243b50` の線2.5・上に題の帯。問いの箱と同じく、クラスではなく属性で書く（`00-reading-service` と同じ書き方） | psql やサービスの画面。問いの型の場面と、接続を描く図で使う |
| 大きな「？」 | 56pxの太字（`.big`） | 問いの図で、答えの場所を示す「？」（`02-client-scene`） |
| 比較の札 | 線なしの薄い灰の札（`.cmp`）に紺の太字 | 比べた回数や組の名前（「比較1」など）。「実測」の札と見分ける（`07-merge-cards`） |

- 配色は既存の値（紺`#243b50`、青緑`#277b74`、薄い緑`#dcefe8`、橙`#b88020`など）を引き継ぐ。色だけで意味を持たせず、形・記号・ラベルを併用する。
- ノード名と出力の項目名は等幅の書体（`ui-monospace, Menlo, monospace`）で書き、出力と見比べられるようにする。
- 説明用の小さな入力は、章の中でそろえる（例：第9章の三つの結合の図は同じ記録と本を使う）。
- 部品の見本を1枚のSVGにまとめ、描き直す図はそこから部品を写す。見本は書き出し対象の`sources/`の外に置く。

### 4.2 矢印

| 矢印 | 意味 |
| --- | --- |
| 実線（青緑） | 行やデータが渡る向き |
| 破線（茶） | 要求（次の行を求める） |
| 細い灰色 | 参照・対応（Indexの項目から行へ、など） |
| 太い白抜き | 処理の段階・時間の順 |

- 矢印には動詞のラベルを付ける（「行を渡す」「次の行を求める」「場所をたどる」）。
- 計画の木は常に「子が下、親が上、行は下から上へ」。EXPLAINの出力の並び（親が上）と同じにする。
- ラベルの中で「→」を「だから」の意味に使わない。

### 4.3 強調

| 強調 | 意味 |
| --- | --- |
| 橙の太枠 | いま比べている・注目する所 |
| 太枠＋札（「交換」など。`.swap`：紺の線4、札は紺の地に白い文字） | 位置や値が変わった。札なしでは使わない（札のない紺の太枠は `.route`）（`top-three-heap`） |
| 灰色の破線＋× | 読まない・除外した・外れた（×は `#7d93a3` の線2本。2026-09-25、段階Cの `06-btree-path`・`06-range-scan` で開かない箱に使った） |
| ✓と× | 条件に合った・合わない |
| 紺の太枠（`.route`） | たどって読むページ（B-treeの各段で読む1枚など） |

1コマで橙の太枠を付けるのは一か所（比べる2枚を示すときは2枚）に限る。

読まない物の描き方は二つある（2026-09-25、段階Cで整理）。ページを多数並べる図では、読むページだけを紺の太枠（`.route`）にし、読まないページは元の枠のまま描く（`06-tree-levels`・`03-index-reference`）。破線＋×は、開かない物を名指しできる少数の図に使う（`06-btree-path`・`06-range-scan` の開かない箱）。比べて外れた値の×は、✓と同じ行に紺の文字の×で書く（`05-linear-scan`・`11-visibility-map`・`06-range-scan` の9）。

### 4.4 文字と前後の文

- 画像の中の文字は、見出し（15字程度まで）・札（「実測（日付）」など）・部品の名前・焦点のラベル・矢印の動詞・出力の項目名と値に限る。副題・断り書き・他の章への参照・「。」で終わる文は置かず、要るものはキャプションへ回す（2026-09-25、試作で「札だけ」が図の中のラベルと字面上ぶつかったため言い換えた）。
- 「索引」は使わず「Index」と書く（AGENTS.mdの約束）。「模型」の語は本全体で使わない。2026-09-25の#13で第3章を「仮に置いた数」「説明するための図」に言い換え、同日ほかの章にも広げた。説明のための図には札を付けず、キャプションに「説明するための図」と書く。
- `node scripts/book-figures/check-figures.cjs 図の名前`で✓になることを確かめる。描画して、文字のはみ出し・文字どうしの重なり・矢じりと文字の接触・見出しのすぐ下の副題も測る。この検査は要素の座標をそのまま測るので、原本では `transform` を使わない。矢じり以外の線と文字の交わりは測らないので、PNGで目でも確かめる。
- 文字はSVGの`font-size`で22以上（スマホで約12px）。
- キャプションは、見るところを1文で書き、説明するための図か実測かを一言添える。例：「帯の長さで、除外した999,999行と返した1行の差を見てください（件数は実測）。」
- 代替テキストは、画像内の見出しを繰り返さず、図の中の変化を文で書く。
- 図の直前の文で何を見るかを示し、直後の文で読み取れることを書く。予想を求める場面では、答えを描いた図を予想の後に置く。

## 6. 試作：第1〜2章の図

### 6.1 第1章15行目 `01-search-window`（問い・手直し）

- 問い：画面に出るのは1冊。その1冊を返すまでに、何冊を調べたか。
- 描く：左（スマホ幅では上）に検索画面「実験用の本 42」→「検索結果：1冊」。右に破線の枠「データベースの中（画面からは見えない）」と、途中を中略した長い棚「本の一覧 100万冊」。画面から棚へ「題名で探す」、棚から画面へ「1冊」の矢印。下に問いの箱「1冊が返るまでに、何冊を調べた？」。
- 描かない：棚のどの本を調べたか（答え）、宙に浮いた虫眼鏡、注意書き。
- 焦点：画面の「1冊」と、棚の「100万冊」の対比。
- キャプション案：「画面に出るのは1冊。その裏に、100万冊の一覧があります。」

### 6.2 第1章251行目 `01-scan-and-filter`（観察・描き直し）観察の型の基準にする

- 問い：1行を返すまでに、何行を比べたか。
- 描く（縦1コマ）：
  - 上：ノード「Seq Scan on books」と「Filter: (title = '実験用の本 42')」。
  - 中央：横長の帯1本「表の100万行（先頭 → 最後）」。帯の上に、端から端まで届く矢印「1行ずつ題名を比べる」。帯全体を灰色にし、「× 除外 999,999行」「Rows Removed by Filter: 999999」と書く。

  - 右上に「件数は実測」の札。
- 焦点：灰色の長い帯と、そこから出る1枚のカード。
- 前の文案（249行目を置き換える）：「帯の長さで、除外した行と返した1行の差を見てください。」

### 6.4 第1章217行目付近 新規 `01-explain-stages`（仕組み・新規・中）

### 6.5 第2章15行目 `05-growing-library`（問い・描き直し）

## 9. 本文の要確認（図の修正とは別）

ユーザーが判断する。図の直しでは、ここに依存する言い方を避ける。

1. [01-explain-basics.md:259](01-explain-basics.md)「1行見つけても走査が止まらないのは、題名に『同じ題名は二つない』という約束を付けていないからです」：一意制約を付けてもSeq Scanは止まらない。2026-09-24、PostgreSQL 18.6の一時テーブル（10万行、題名に一意制約、Indexの利用を禁止）で`Rows Removed by Filter: 99999`を確認した。制約を付けて変わるのは、一意のIndexができてIndex Scanを選べるようになること。第2章89行目の理由付けも同じ前提に立っている。→ 2026-09-25、ユーザーの判断で直した。259行目は「このSQLが条件に合う行をすべて求めていて、Seq Scanには条件に合う行の場所を前もって知る手がかりがない」という理由にした。300行目には「番号の検索で100万行を調べずに済んだのは、番号を重複させない約束があるからではなく、このIndexを使えたから」の1文と、その根拠の脚注（主キーでもIndexを使わせないとSeq Scanで999,999行を除外）を足した。第2章89行目は、図の前の文を「どこまで題名を比べるかを見てください」の形にした。本と同じ100万冊での確認は[chapter01-unique-vs-index-20260925.log](../../_drafts/postgresql-query-journey/verification/chapter01-unique-vs-index-20260925.log)。
2. [11-mvcc-and-maintenance.md:136](11-mvcc-and-maintenance.md)「WALを先に保存するというこの順序は、耐久性の設定を標準のままにしたときの約束です」：WALをデータページより先に保存する順序は、`synchronous_commit`の設定によらず守られる（`fsync`を無効にした場合を除く）。`synchronous_commit`で変わるのは、COMMITがWALの保存を待つかどうか。→ 2026-09-25、ユーザーの判断で直すことにし、PR #19 で「WALを先に保存する順序は、`synchronous_commit`の設定を変えても守られます。この設定で変わるのは、COMMITがWALの保存を待ってから返るかどうかです。」にした。「設定によらず」とは書かず `synchronous_commit` に絞った（`fsync` を無効にすると、書き込みの順序を守る仕組みそのものが止まるため）。PR #19 は2026-09-25にマージした。
3. [10-planner-and-statistics.md:104](10-planner-and-statistics.md)「`loops`を掛けて合計に直してから推定と比べます」：推定の`rows`も1回あたりの値なので、実際の`rows`はloopsを掛けずに比べる。[PostgreSQLの説明](https://www.postgresql.org/docs/18/using-explain.html)も、実際の値を1回あたりの平均で表示するのは推定と比べやすくするためだとしている。loopsを掛けるのは合計の時間を知りたいとき。→ 2026-09-25、ユーザーの判断で直すことにし、PR #19 で「推定の`rows`も1回当たりの値なので、`loops`を掛けずにそのまま比べます。`loops`を掛けるのは、合計の行数や時間を知りたいときです。」にした。PR #19 は2026-09-25にマージした。

4. 第1章の番号検索（`id = 42`）の`shared hit=7`は、接続して最初の実行だけの値で、Indexと表のページ（4回）のほかにシステムカタログの読み取りが3回含まれる（2026-09-25、PostgreSQL 18.6。同じ接続で2回目を実行すると`hit=4`。`id`はbigint、`42`はinteger）。後の章で「3段のIndexと表1ページで4回」と説明する図と並べると、7との差を読者が説明できない。第1章の出力を載せ直すか、7の内訳に触れない書き方にする。図（`01-index-to-row`）は内訳に触れない書き方に直した。第3章158行目の範囲検索（`WHERE id BETWEEN 400000 AND 400010`）の「7回のアクセス」も同じで、新しい接続の1回目は7、同じ接続の2回目は`hit=4`だった（2026-09-25）。第3〜4章・第9章の図でページ数を説明するときは、2回目の値か、型のそろった条件の値を使う。段階Cの `06-range-scan` と `03-index-reference` はこの7を使わず、番号1〜9の模型の数（探す1回・開く箱2個・取り出す行5行）と、題名の検索の`shared hit=1 read=3`を使った（2026-09-25）。
