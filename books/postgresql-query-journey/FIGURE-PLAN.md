## 2. 今の図の診断

五つの評価（2026-09-24、章ごとに全文と全図を確認）と、横断の計測から分かったこと。

| 原因 | 例 | 読者への影響 |
| --- | --- | --- |
| 焦点がない | `01-scan-and-filter`は一致1行と不一致999,999行を同じ大きさの箱で描く。橙の強調が、図によって「比べている」「選んだ」「新しい版」「結果」と意味を変える | 見るところが決まらない |
| EXPLAINの数値と図がつながっていない | 実行結果の直後の図に`rows`・`loops`・`Rows Removed by Filter`が書かれていない。第6〜8章の10枚は、PIDを除いて実測値を描いた図がない | 本の軸（EXPLAINで観察する）が図で途切れる |
| 量が見た目に出ていない | 第12章は499,998行と20行を、カード6枚と2枚で描く | 減った量の大きさが伝わらない |
| 物を描かずに文字の箱を並べている | 第11章の技術図3枚は、行の版・可視性マップ・WALのファイルを描いていない | 文章の言い換えになり、仕組みを想像できない |
| 同じ物が図ごとに違う見た目 | 緑のカードが読了記録・索引の項目・本の行を行き来する。「箱」がB-treeの範囲・ページ・ハッシュ表の3通り。計画の木は第6章が下から上、第10章が上から下 | 章をまたいで同じ物だと気付けない |
| 予想より先に答えを見せる | `05-limit-search`の②③、`02-client-scene`の「バックエンド」、`08-twenty-window`の並べ済みの記録、`05-growing-library`の「最後まで探す」、`11-snapshots`（予想を促す文の直後）、`12-ranking-after`の結論文 | 予想と実験の意味が薄れる |

計測した事実：

- 文字：SVGの`font-size`は14〜21の指定が多い（14は場面の絵12枚の注意書き）。スマホでは約0.53倍になり、14は約7px、18は約10pxになる。
- 縦の長さ：縦横比1.2を超える図が29枚（1.3を超えるのは19枚）。PCの幅700pxでは縦840px以上になり、ノートPCの画面に収まらない。最長は`top-three-heap`（1280×3580、PCで約1,960px）。
- 文字の層：画像内のタイトル・副題・注意書き、キャプション、代替テキストが同じ内容を繰り返す。キャプションは46件のうち18件が「実測ではありません」「省略しています」などの断り書きを含み、ほかも多くは条件の説明で、見るところを書いたものは少ない。代替テキストの多くは画像内のタイトルと同じ文。
- よい点：配色は技術図のほとんど（31枚）で共通。すべての図にキャプションがあり、模型と実測を書き分ける習慣がある。これらは引き継ぐ。

## 3. 図の四つの型

| 型 | 置く場所 | 描くもの | 描かないもの |
| --- | --- | --- | --- |
| 問い（場面の絵） | 章や節の入口 | その章の具体的な数字と、一つの問い | 答え、飾りの人物や表情、注意書き |
| 仕組み（模型） | 説明の段落の直後 | 小さな値で追う動き。1コマに焦点は一つ | 実装の細部、別の問い |
| 観察（実測） | EXPLAINの実行結果の直後 | 行数に比例した帯、出力の項目名と数値、実測の札 | 実測していない内訳 |
| 比較（前後） | 条件を変えた結果の後 | 同じ配置で、違う所だけを強調 | 配置の違い（見比べを邪魔する） |

- 章の道のりや表の関係を示す全体像は、仕組みの型として扱う。
- 観察の型は今の本にほとんどない。第1・2・7・8・12章へ入れる。序章の「？」の図（`00-ranking-question`）と第12章の全体像を同じ枠組みにして、本の問い「結果は20行なのに、途中で何行を扱っているのか」を閉じる。
- 場面の絵13枚（第1〜12章の入口の12枚と、序章の`00-reading-service`）は問いの型にそろえる。人物を描く場合は、棚を指す・画面を待つなど、問いに関わる動作だけにする。

## 4. 共通の約束

### 4.1 部品

| 部品 | 見た目 | 意味 |
| --- | --- | --- |
| 行カード | 白い横長のカード。本は「番号・題名」、読了記録は「本番号・日付」 | 表の1行 |
| ページ枠 | 番号タブ付きの枠。中に行カードを入れ、行カードより大きく描く | 読み込みの単位（8kB） |
| 索引の項目 | 小さな正方形のキー＋「▸場所」 | 索引が持つ値と、行の場所 |
| 計画のノード | 角丸の箱。ノード名は出力と同じ字面で書く | EXPLAINの1行 |
| 量の帯 | 横長の帯。長さを行数に比例させ、数値と出典を書く | 扱った行数 |
| 共有バッファ | RAMの枠の中の大きな枠。中にページ枠を並べる | 接続どうしで共有するページの置き場所 |
| 作業用メモリ | 破線の枠（上限の目安）。処理ごとに一つ | 並べ替えやハッシュの作業場所 |
| ストレージ | 下段の枠。中に表のファイル・WALのファイル・一時ファイル | 電源が切れても残る場所 |

- 配色は既存の値（紺`#243b50`、青緑`#277b74`、薄い緑`#dcefe8`、橙`#b88020`など）を引き継ぐ。色だけで意味を持たせず、形・記号・ラベルを併用する。
- ノード名と出力の項目名は等幅の書体（`ui-monospace, Menlo, monospace`）で書き、出力と見比べられるようにする。
- 模型の小さな入力は、章の中でそろえる（例：第9章の三つの結合の図は同じ記録と本を使う）。
- 部品の見本を1枚のSVGにまとめ、描き直す図はそこから部品を写す。見本は書き出し対象の`sources/`の外に置く。

### 4.2 矢印

| 矢印 | 意味 |
| --- | --- |
| 実線（青緑） | 行やデータが渡る向き |
| 破線（茶） | 要求（次の行を求める） |
| 細い灰色 | 参照・対応（索引の項目から行へ、など） |
| 太い白抜き | 処理の段階・時間の順 |

- 矢印には動詞のラベルを付ける（「行を渡す」「次の行を求める」「場所をたどる」）。
- 計画の木は常に「子が下、親が上、行は下から上へ」。EXPLAINの出力の並び（親が上）と同じにする。
- ラベルの中で「→」を「だから」の意味に使わない。

### 4.3 強調

| 強調 | 意味 |
| --- | --- |
| 橙の太枠 | いま比べている・注目する所 |
| 太枠＋札（「入れ替え」など） | 位置や値が変わった |
| 灰色の破線＋× | 読まない・除外した・外れた |
| ✓と× | 条件に合った・合わない |

1コマで橙の太枠を付けるのは一か所（比べる2枚を示すときは2枚）に限る。

### 4.4 文字と前後の文

- 画像の中に置くのは、短い見出し（15字程度まで）と「模型」「実測（日付）」の札だけ。副題と注意書きは置かない。
- 文字はSVGの`font-size`で22以上（スマホで約12px）。
- キャプションは、見るところを1文で書き、模型か実測かを一言添える。例：「帯の長さで、除外した999,999行と返した1行の差を見てください（件数は実測）。」
- 代替テキストは、画像内の見出しを繰り返さず、図の中の変化を文で書く。
- 図の直前の文で何を見るかを示し、直後の文で読み取れることを書く。予想を求める場面では、答えを描いた図を予想の後に置く。

### 4.5 大きさ

- 縦横比は1.3以下を目安にする。超える場合は、コマを分けて2枚にするか、Zennの幅指定`![代替テキスト](/images/postgresql-query-journey/xxx.png =520x)`でPCの表示幅を狭める。
- 幅指定した画像がスマホで画面幅に収まるかは、Zennのプレビューで確かめてから全体に使う（要確認）。
- 描き直した図は、幅360pxと700pxの両方で表示を確かめる。

## 6. 試作：第1〜2章の図

### 6.1 第1章15行目 `01-search-window`（問い・手直し）

- 問い：画面に出るのは1冊。その1冊を返すまでに、何冊を調べたか。
- 描く：左（スマホ幅では上）に検索画面「実験用の本 42」→「検索結果：1冊」。右に破線の枠「データベースの中（画面からは見えない）」と、途中を中略した長い棚「本の一覧 100万冊」。画面から棚へ「題名で探す」、棚から画面へ「1冊」の矢印。下に問いの箱「1冊が返るまでに、何冊を調べた？」。
- 描かない：棚のどの本を調べたか（答え）、宙に浮いた虫眼鏡、注意書き。
- 焦点：画面の「1冊」と、棚の「100万冊」の対比。
- キャプション案：「画面に出るのは1冊。その裏に、100万冊の一覧があります。」

### 6.2 第1章251行目 `01-scan-and-filter`（観察・描き直し）観察の型の基準にする

- 問い：1行を返すまでに、何行を比べたか。
- 描く（縦1コマ）：
  - 上：ノード「Seq Scan on books」と「Filter: (title = '実験用の本 42')」。
  - 中央：横長の帯1本「表の100万行（先頭 → 最後）」。帯の上に、端から端まで届く矢印「1行ずつ題名を比べる」。帯全体を灰色にし、「× 除外 999,999行」「Rows Removed by Filter: 999999」と書く。
  - 帯をくくる括弧から、小さなカード「○ 一致 1行」「rows=1」を出し、その先に「結果」。帯の中での位置は描かない（第2章で分かることを先に見せないため）。
  - 右上に「件数は実測」の札。
- 焦点：灰色の長い帯と、そこから出る1枚のカード。
- 前の文案（249行目を置き換える）：「帯の長さで、除外した行と返した1行の差を見てください。」

- 連動：254行目の記述（9章の要確認1）。図には「最後まで比べる」とだけ書き、理由は描かない。

### 6.6 第2章91行目 `05-linear-scan`（仕組み・手直し）

- 問い：LIMITなしで探すと、何回比べるか。
- 描く：

### 6.7 第2章142行目 `05-limit-search`（仕組み・描き直し）

- 問い：LIMIT 1は、どうやって走査を止めるのか。
- 描く：
  - 上にノード「Limit（1行まで）」、下にノード「Seq Scan on books」。
  - Seq Scanの中に`05-linear-scan`と同じ5枚。本1は×、本2は○、本3〜5は灰色の破線で「比べない」。
  - 本2からLimitへ実線「行を渡す」。LimitからSeq Scanへ破線「次の行を求める」を1本。2本目の破線に×を付けて「もう求めない」。
  - 横に「模型：×1＋○1＝2枚で終わり」と、実測の札付きで「Rows Removed by Filter 41＋rows 1＝42行」。
- 削る：②後ろで見つかる、③一致する本がない。実験の前に答えを見せているため。答えは6.8の帯の図で、実験の後に見せる。
- 直す：「未読」を「比べない」に（同じページの行はページごと読み込まれている）。
- 焦点：2本目の要求に付いた×。
- 部品：ノードと矢印の見た目は第6章`02-execution-tree`と共通にし、ここで先に作る。
- キャプション案：「早く見つかる場合の模型。Limitが次の行を求めなくなった時点で、Seq Scanも止まります。」145行目の文はそのまま使える。

### 6.8 第2章200行目付近 新規 `05-limit-bands`（観察・新規・高）

- 位置：結果の表（195〜200行目）の直後。
- 問い：目的の本の位置で、比べる行数はどれだけ変わったか。

  - 右端に比べた行数：1,000,000／42／999,999／1,000,000。
  - 2本目に拡大の丸「42行（帯のほぼ0%）」、3本目の右端に「残り1行は比べない」。
  - 札「実測：2026-09-23、PostgreSQL 18.6」。

## 9. 本文の要確認（図の修正とは別）

ユーザーが判断する。図の直しでは、ここに依存する言い方を避ける。

1. [01-explain-basics.md:254](01-explain-basics.md)「1行見つけても走査が止まらないのは、題名に『同じ題名は二つない』という約束を付けていないからです」：一意制約を付けてもSeq Scanは止まらない。2026-09-24、PostgreSQL 18.6の一時テーブル（10万行、題名に一意制約、索引の利用を禁止）で`Rows Removed by Filter: 99999`を確認した。制約を付けて変わるのは、一意の索引ができてIndex Scanを選べるようになること。第2章89行目の理由付けも同じ前提に立っている。
2. [11-mvcc-and-maintenance.md:136](11-mvcc-and-maintenance.md)「WALを先に保存するというこの順序は、耐久性の設定を標準のままにしたときの約束です」：WALをデータページより先に保存する順序は、`synchronous_commit`の設定によらず守られる（`fsync`を無効にした場合を除く）。`synchronous_commit`で変わるのは、COMMITがWALの保存を待つかどうか。
3. [10-planner-and-statistics.md:102](10-planner-and-statistics.md)「`loops`を掛けて合計に直してから推定と比べます」：推定の`rows`も1回あたりの値なので、実際の`rows`はloopsを掛けずに比べる。[PostgreSQLの説明](https://www.postgresql.org/docs/18/using-explain.html)も、実際の値を1回あたりの平均で表示するのは推定と比べやすくするためだとしている。loopsを掛けるのは合計の時間を知りたいとき。
