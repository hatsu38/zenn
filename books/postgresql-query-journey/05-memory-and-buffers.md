## この章で分かること

同じSQLを繰り返し実行し、時間とBUFFERSの表示を比較します。ページを使う経路を、バックエンド・共有バッファ・OSキャッシュ・ファイルの関係として整理します。共有バッファと作業用メモリ、一時テーブルと一時ファイルも区別します。観測値から言える範囲を押さえ、改善前後を比較するための測定条件を考えられるようになります。

## はじめに：同じ検索を、もう一度

前の章で、表はページというまとまりで扱われると分かりました。では、同じ本をもう一度探したら、同じページを最初から取り寄せるのでしょうか。

繰り返した検索を、観察ノートに並べるつもりで比べてみます。

![同じ検索を、もう一度](/images/postgresql-query-journey/04-repeat-observation.png)
*学ぶきっかけを描く、説明用の場面。*

後の出力では、変わった値と変わらなかった値の両方を拾います。

## この章だけの小さな表を用意する

第1章で用意し、第3章で索引を追加した`public.books`（100万冊・題名索引あり）は残します。同じDBの別スキーマに、1,000冊・主キーのみの通常テーブルを作ります。一時テーブルとは異なるため、後の共有バッファの観察にも使えます。

次の操作は、この章を試すpsqlで行います。`book_observation`はこの実験専用の名前です。既に存在する場合は削除せず、別名にそろえてから実行してください。

```sql
BEGIN;
CREATE SCHEMA book_observation;
CREATE TABLE book_observation.books
  (LIKE public.books INCLUDING DEFAULTS INCLUDING CONSTRAINTS);
ALTER TABLE book_observation.books ADD PRIMARY KEY (id);
INSERT INTO book_observation.books
SELECT id, title FROM public.books WHERE id BETWEEN 1 AND 1000;
SET LOCAL search_path = book_observation, public;
ANALYZE books;
SELECT count(*) FROM books;
```

準備SQLの実行結果です。2026年9月24日に共有された出力から、入力SQLとpsqlのプロンプトを除いて掲載しています。

```sql

CREATE SCHEMA
CREATE TABLE
ALTER TABLE
INSERT 0 1000
SET
ANALYZE
 count
-------
  1000
(1 row)
```

`INSERT 0 1000`と最後の`count`から、観察用の表に1,000行あると確認できます。このトランザクションは開いたまま観察を続け、観察が終わったところで`ROLLBACK`して片付けます。

次のSQLを3回実行してください。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM books WHERE title = '実験用の本 42';
```

2026年9月24日に共有された、本1,000冊での3回分の実行結果です。「1回目」はこの比較の最初であり、DBを起動してから最初の検索という意味ではありません。表の作成・データの挿入・件数確認を行った後の観察です。

### 1回目

```sql
Seq Scan on books  (cost=0.00..20.50 rows=1 width=27) (actual time=0.018..0.079 rows=1.00 loops=1)
  Filter: (title = '実験用の本 42'::text)
  Rows Removed by Filter: 999
  Buffers: shared hit=8
Planning:
  Buffers: shared hit=3
Planning Time: 0.123 ms
Execution Time: 0.104 ms
```

### 2回目

```sql
Seq Scan on books  (cost=0.00..20.50 rows=1 width=27) (actual time=0.051..0.154 rows=1.00 loops=1)
  Filter: (title = '実験用の本 42'::text)
  Rows Removed by Filter: 999
  Buffers: shared hit=8
Planning Time: 0.167 ms
Execution Time: 0.190 ms
```

### 3回目

```sql
Seq Scan on books  (cost=0.00..20.50 rows=1 width=27) (actual time=0.036..0.093 rows=1.00 loops=1)
  Filter: (title = '実験用の本 42'::text)
  Rows Removed by Filter: 999
  Buffers: shared hit=8
Planning Time: 0.105 ms
Execution Time: 0.117 ms
```

### 変わったのは、どの値？

記録するのは、時間だけではありません。3回の出力を並べてみます。表の`shared hit`は、計画作成時ではなく検索の実行時の値です。

| 実行 | 計画 | 返した行 | 除外した行 | shared hit | Planning Time | Execution Time |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 1回目 | Seq Scan | 1 | 999 | 8 | 0.123 ms | 0.104 ms |
| 2回目 | Seq Scan | 1 | 999 | 8 | 0.167 ms | 0.190 ms |
| 3回目 | Seq Scan | 1 | 999 | 8 | 0.105 ms | 0.117 ms |

この表では、変わった値と変わらなかった値を分けて読みます。

- **変わった：** `Execution Time`は0.104 ms、0.190 ms、0.117 msでした。2回目は遅くなり、3回目は再び速くなっています。
- **変わらなかった：** 3回とも`Seq Scan`で、返した行は1行、除外した行は999行です。`loops=1`なので、毎回1,000行を調べています。
- **同じだった：** 実行時のバッファアクセスは、3回とも`shared hit=8`です。

つまり、**探す方法・調べた行数・実行時のバッファアクセスが同じでも、実行時間は上下しています。** 時間の違いだけを根拠に、調べる量が減ったとは言えません。

`Planning Time`は計画を作る時間で、`Execution Time`とは分けて読みます。1回目の`Planning`の下にある`shared hit=3`も計画作成時のアクセスなので、実行時の8回には足しません。

もう一つ見てほしいのが、**1回目からずっと`shared hit=8`**という点です。3回とも`shared read`は表示されていません。この走査では、最初から共有バッファにあるページを使っています。

そのため、今回の結果を「1回目はストレージから読み、2回目からメモリに載った」と説明することはできません。CPUの状態やほかの処理の負荷など、時間に影響しうる要因はありますが、この出力だけでは変動の原因を特定できません。

自分の結果でも、時間と一緒に計画・行数・BUFFERSを比べてみてください。まず、この`hit`が何を表しているのか、ページの置き場所から見ていきましょう。

## 読み込んだページを共有バッファに保持する

メモリは、プログラムが実行中にデータを保持する領域です。PostgreSQLは読み込んだページをメモリに保持し、同じページを再び使えるようにします。複数のバックエンドから利用できる、このページの保持領域を**共有バッファ**と呼びます。

共有バッファの外では、OSもファイルの内容をメモリに保存することがあります。これを**OSキャッシュ**と呼びます。そこにもなければ、SSDなどのストレージから読み込みます。

ここからの図は、先ほどの3回の実測を再現したものではありません。ページがまだ共有バッファにないところから始める模型です。バックエンドAが読んだページを、後からバックエンドBが必要とする場面を見てみましょう。3コマを通して、ページ7の置き場所と、読み込みが必要かどうかに注目してください。

![Aが必要としたページ7を共有バッファへ読み込み、後からBが同じページを再利用する3コマの図](/images/postgresql-query-journey/shared-buffer-reuse.png)
*説明用の模型。読み込んだページ7が、Bの利用時にも共有バッファに残っている場合です。ページ内の線は行を表し、実際の行数や容量は再現していません。*

1コマ目では、ページ7はまだ共有バッファにありません。2コマ目でファイルから読み込みます。この読み込みが`shared read`に対応します。OSキャッシュに内容があればそれを使い、なければストレージから読みます。

3コマ目では、別の接続のバックエンドBが同じページを必要としています。ページ7が共有バッファに残っているため、ファイルから読み込み直さずに使えます。これが`shared hit`です。

共有バッファに保持するのは、表や索引のページです。SQLの検索結果をそのまま保存する仕組みではないため、ページがメモリにあっても条件の比較や集計は必要です。

## readがあれば、SSDを読んだ？

図の2コマ目には、OSキャッシュから使う経路と、ストレージから読む経路がありました。どちらでも、PostgreSQLの共有バッファにはページを読み込む必要があります。

そのため、`shared read`を見ただけで「その回数だけSSDへ読みに行った」とは言えません。どの層で観察した値かを意識してください。

バッファの値はページへのアクセスを数えるので、同じページに何度も触れればその分が含まれます。「hitが100だから、100種類のページがある」とも限りません。また、親の値に子の処理が含まれることがあるため、計画の全行を単純に足さないようにします。

## メモリの領域を用途で分ける

ここまでの共有バッファは、ページを使うための場所です。一方、行を並べ替えたり、途中の集計値を保持したりする作業領域も必要です。

ページを共有する領域と、それぞれの処理が使う作業領域を見比べてください。

![ページの保存場所と、計算の作業場所](/images/postgresql-query-journey/04-memory-regions.png)
*基本の配置の模型 ／ 並列処理などは省略。*

ソートの途中の値は個別の作業領域へ、再利用する表や索引のページは共有バッファへ置きます。設定名も役割で分けてみましょう。

| 名前 | 主な役割 | 身近な模型 |
| --- | --- | --- |
| `shared_buffers` | 表や索引のページを共有する | 共通の資料置き場 |
| `work_mem` | ソートやハッシュなどの処理の作業量の基準 | 計算用の机 |
| `temp_buffers` | 接続内の一時テーブルのページを扱う | 一時的な資料の置き場 |
| `maintenance_work_mem` | 索引作成やVACUUMなどの作業 | 資料を整備するときの机 |

値は`SHOW`で確認できます。今回の実験環境では、次の値になっていました。

```sql
SHOW shared_buffers;
```

```sql
 shared_buffers
----------------
 128MB
(1 row)
```

```sql
SHOW work_mem;
```

```sql
 work_mem
----------
 4MB
(1 row)
```

```sql
SHOW temp_buffers;
```

```sql
 temp_buffers
--------------
 8MB
(1 row)
```

```sql
SHOW maintenance_work_mem;
```

```sql
 maintenance_work_mem
----------------------
 64MB
(1 row)
```

この出力は設定値であり、いま各処理が実際に使っているメモリ量ではありません。たとえば`work_mem`の`4MB`を見ても、「この検索で4MB使った」とは読めません。

いまは値を変更しません。自分の環境の設定を記録し、どの用途に関わる値なのかを上の表と対応させてみてください。

特に`work_mem`は、接続一つのメモリ全体の上限ではありません。複数の処理がそれぞれ作業する場合があり、ハッシュ処理では別の倍率設定も関わります。第7・9章で具体例を見ます。[設定の公式説明](https://www.postgresql.org/docs/18/runtime-config-resource.html)にも対象が分けて書かれています。

## 「一時」の二つの意味

ここは言葉が似ているので、先に整理します。

- **一時テーブル**：一時的に使う表。そのページは`local`のバッファ情報に現れます。
- **一時ファイル**：並べ替えなどで作業をメモリに収めきれず、途中結果を置くファイル。`temp read`や`temp written`に関係します。

どちらも「一時」ですが、同じものではありません。この本の主実験では、`CREATE TABLE`で作った通常の表を使います。

## 観察用の表を片付ける

この章の観察が終わったら、同じpsqlで次を実行します。観察用スキーマの準備からここまでを一つのトランザクションとして扱います。

```sql
ROLLBACK;
```

観察用スキーマと表が取り消され、参照先も元に戻ります。100万冊の`public.books`と題名索引は変更していません。

## 速くなった理由を、一つに決めない

2回目の時間が短くなっただけでは、索引によって速くなったとは判断できません。索引を追加していなければ、ページが再利用された可能性や、ほかの負荷の違いもあります。

改善を比べるときは、同じデータ、同じ索引、同じ設定で、何回目の実行かを残します。サーバを再起動してもOSキャッシュまで空になるとは限りません。

課題です。「同じSQLの2回目が速かった。だからSQLの処理方法が改善された」という説明に、何を確認したいと返しますか。

:::details 考え方
まず計画が同じか見ます。次にhit/readと時間を比べます。キャッシュ状態の違いと処理方式の違いを分け、分からない部分は仮説として残します。
:::

共有バッファは、複数の接続から利用できる場所でした。3コマの図では、ページを使う側を「バックエンドA」「バックエンドB」と描いています。では、このバックエンドとは何で、接続ごとに何が別々に動き、何を共有しているのでしょうか。次章ではpsqlを二つ開き、プロセスと作業領域の関係を確かめます。
