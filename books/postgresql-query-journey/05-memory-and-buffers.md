## この章で分かること

一度使ったページは、次の検索で再利用できるのでしょうか。ページを保存するストレージと、実行中に使うメモリの関係を図で確認し、`BUFFERS`の`hit`と`read`を読みます。

まず、小さなテーブルのページをメモリから追い出してから同じ検索を3回実行し、ページの再利用と、レコードの条件を調べる処理を区別します。

次に100万冊の`books`に戻り、大きなテーブルを続けて読んでも`read`が残る理由を確かめます。第3章の`hit=1 read=3`を、Indexの段数と分けて読む方法も確かめます。

最後に、題名のIndexの順とテーブルのページの順が違うときに、同じページを何度も開かずに済む読み方（`Bitmap Heap Scan`）を観察します。

## 同じ検索を、もう一度

前の章で、テーブルはページというまとまりで扱われると分かりました。では、同じ本をもう一度探したら、同じページを最初から取り寄せるのでしょうか。

繰り返した検索で、変わった値と変わらなかった値を、観察ノートに並べるつもりで比べてみます。

*2回目の「？」と、観察ノートの三つの項目を見てください。値は、この後の実行で確かめます。*

## ページを保存する場所と、検索で使う場所

前章で調べたテーブルのファイルは、SSDなどのストレージに保存されています。検索するときは、必要なページを**メモリ（RAM）**&#8203;へ読み込みます。メモリは、プログラムが動いている間にデータを置いて使う場所です。

PostgreSQLは、読み込んだテーブルやIndexのページをメモリ内に保持します。この領域は、このサーバへの複数の接続から共通に使う場所で、**共有バッファ**と呼びます。次の検索でも必要なページが残っていれば、ファイルから読み込み直さずに使えます。

図の上側がメモリ、下側がストレージです。同じページが、ファイルからメモリへ読み込まれ、その後も使われる様子を見てください。

![検索が共有バッファにないページをOSキャッシュから、そこにもなければストレージのテーブルのファイルから読み、共有バッファに置く（shared read）。次の検索は共有バッファのページを使う（shared hit）](/images/postgresql-query-journey/shared-buffer-reuse.png)
*④で共有バッファに置いたページを、⑤の次の検索がそのまま使います（読み込み経路を説明するための図。P7は説明用のページ番号）。*

`EXPLAIN (ANALYZE, BUFFERS)`は、ページを使ったときの状況を次の二つに分けて表示します。

| 表示 | ページを使うときの状況 |
| --- | --- |
| `shared hit` | 共有バッファに既にあり、そのページを使った |
| `shared read` | 共有バッファになく、ファイルから読み込んだ |

図には**OSキャッシュ**という領域もあります。PostgreSQLとは別に、OSもファイルの内容をメモリに残すことがあるためです。`read`と表示されたページも、実際はOSキャッシュから読まれていることがあります。そのため、`read`の回数をそのままSSDを読んだ回数とは考えられません。

共有バッファに残るのは、検索結果の1件ではなく、テーブルやIndexのページです。では、ページを再利用できたら、その中から条件に合うレコードを探す処理も省けるでしょうか。次の実験で確かめます。

## 前章の観察用テーブルを確認する

第4章で作った`books_observation`を引き続き使います。まだ作っていない場合や削除済みの場合は、先に下の補足の準備SQLを実行してください。1,000冊あることを確認します。

```sql
SELECT count(*) FROM books_observation;
```

実行結果です。

```sql:実行結果
 count
-------
  1000
(1 row)
```

:::details 第5章から始める場合、または観察用テーブルを削除済みの場合
`books_observation`がない場合だけ、次のSQLで準備します。既に1,000冊ある場合は作り直す必要はありません。別の用途の同名テーブルがある場合は、削除せずに名前を変えてください。

```sql
INSERT INTO books_observation

```

## 同じ検索を3回実行する

前章の観察や、先ほどの件数確認で、観察用テーブルのページは共有バッファに読み込まれています。このまま検索すると1回目から`shared hit`になり、ファイルから読み込む場面を観察できません。

そこで、観察の前に、このテーブルのページを共有バッファから追い出します。PostgreSQL 18では、共有バッファの中身を調べる拡張機能`pg_buffercache`の`pg_buffercache_evict_relation`で、指定したテーブルのページをまとめて追い出せます[^evict]。次の二つを実行してください。

```sql
CREATE EXTENSION IF NOT EXISTS pg_buffercache;
SELECT * FROM pg_buffercache_evict_relation('books_observation');
```

[^evict]: PostgreSQL 18で加わった関数で、17以前にはありません。17以前で試す場合は、DBを再起動すると共有バッファが空になります。スーパーユーザー（すべての権限を持つユーザー）だけが実行できる、開発者の検証用の関数です。実験用リポジトリのREADMEの手順では、スーパーユーザーの`postgres`ユーザーで接続するので実行できます。[pg_buffercacheの公式ドキュメント](https://www.postgresql.org/docs/18/pgbuffercache.html)には、追い出したページが別の処理によってすぐ読み戻されることもあると書かれています。本番のDBで使う道具ではありません。拡張機能はこのDBに残るため、次回以降も使えます。

:::details 追い出した結果の読み方
2026年9月25日、DockerのPostgreSQL 18.6で、第4章の観察を終えた後、接続し直して実行した結果です。

```sql:実行結果
 buffers_evicted | buffers_flushed | buffers_skipped
-----------------+-----------------+-----------------
              11 |               8 |               0
(1 row)
```

`buffers_evicted`の11が、共有バッファから追い出したページの数です。第4章で数えた本体の8ページより3ページ多いのは、テーブルに付いている別のファイルのページも追い出したからです。同じ手順で内訳を数えると、本体の8ページと、各ページの空き具合を記録する**空き領域マップ**の3ページでした。内訳は、`pg_buffercache`の`relforknumber`列でページを数えて確かめました（0が本体、1が空き領域マップ）。空き領域マップは、レコードを追加するときに、空きのあるページを探すために使われます。

`buffers_flushed`の8は、追い出すときにファイルへ書き出されたページの数です。第4章で1,000件を入れたときの変更などが、まだファイルへ書き戻されずにメモリ上に残っていました。そうした変更済みのページは、書き出してから追い出します。`buffers_skipped`は追い出せなかったページの数で、今回は0でした。作成からの経過時間や途中の操作によって、追い出す数や書き出す数は変わります。変更済みのページが既にファイルへ書き戻されていれば、`buffers_flushed`は0になります。

書き出した内容はOSキャッシュにも残りやすいので、この後の1回目の`read`は、OSキャッシュから読んだ可能性が高くなります。`buffers_flushed`が0で書き出さなかった場合も、それまでに読んだページがOSキャッシュに残っていることがあります。
:::

続けて、次のSQLを3回実行します。実行する前に予想してください。1回目と2回目で、`shared hit`と`shared read`はどう変わるでしょうか。そして、`Rows Removed by Filter`は変わるでしょうか。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM books_observation WHERE title = '実験用の本 42';
```

追い出した直後の、1回目の実行結果です。

```sql:実行結果
  Buffers: shared hit=12
…

```

2回目の実行結果です。

```sql:実行結果

  …

…

```

3回目の実行結果です。

```sql:実行結果
Seq Scan on books_observation  (cost=0.00..20.50 rows=1 width=27) (actual time=0.005..0.037 rows=1.00 loops=1)

…

```

3回分を表にまとめます。

| 実行 | 探す方法 | 調べたレコード | shared hit | shared read | Execution Time |
| --- | --- | ---: | ---: | ---: | ---: |
| 1回目 | Seq Scan | 1,000 | 表示なし | 8 | 0.329 ms |
| 2回目 | Seq Scan | 1,000 | 8 | 表示なし | 0.041 ms |
| 3回目 | Seq Scan | 1,000 | 8 | 表示なし | 0.040 ms |

### ページは2回目から再利用され、レコードは毎回調べている

1回目は`shared read=8`でした。追い出した直後で共有バッファに1ページもなかったので、8ページをすべてファイルから読み込んでいます。2回目と3回目は`shared hit=8`に変わり、`read`は消えました。1回目に読み込んだページが共有バッファに残っていて、それを使ったと読めます。この章の問いに戻ると、ページが共有バッファに残っていれば、ストレージから読み直さずにそのページを使います。

一方、`Rows Removed by Filter`は3回とも999です。返した1件と合わせて、**3回とも1,000件の題名を比べています**。ページを読み込み直す手間は省けても、そのページの中から条件に合うレコードを探す仕事は省けていません。

図で、3回分のページの使い方と、比べたレコードの数を見比べてください。

![1回目は8ページをすべてファイルから読み（shared read=8）、2回目と3回目は共有バッファの8ページを使った（shared hit=8）。比べたレコードは3回とも1,000件で、999件を除外した](/images/postgresql-query-journey/04-two-levels.png)
*ページは2回目から共有バッファのものを使い、比べたレコードは3回とも1,000件です（2026年9月25日の実測）。*

SQLも、返る1件も、3回とも同じです。それなら前回の答えをそのまま返してもよさそうですが、PostgreSQLには、通常のSELECTの結果全体を保存し、次の実行でそのまま返す組み込みの結果キャッシュはありません。共有バッファに置くのはページです。

たとえば、1回目と2回目の間に別の接続が同じ題名の本を追加したり、この本の題名を書き換えたりしているかもしれません。前回の1件を取っておいて返すと、その変更を見落とします。そのため、実行するたびにページの中のレコードを確認します。レコードの変更が他の接続からどう見えるかは、第11章で扱います。

この出力から確かに言えるのは、探す方法と調べたレコード数が同じまま、`read`が`hit`へ変わったことです。時間も0.329 msから0.041 msへ短くなっていますが、それぞれ1回だけの測定です。前の節の図のとおり、`read`にはOSキャッシュから読んだページも含まれるので、1回目の時間がSSDを読む時間だとも言えません。

:::details Planningの値は別に読む
`Planning Time`は計画を作る時間、`Execution Time`は実行の時間です。1回目の`Planning`の下の`shared hit=12`も計画作成時のアクセスなので、検索の実行時の8回には足しません。テーブルの定義などを読んだ回数で、追い出した11ページとは別のものです。
:::

## 観察用のテーブルを片付ける

観察用テーブルを使う実験は、ここまでです。第4章で作った観察用テーブルを削除します。

```sql
DROP TABLE books_observation;
```

100万冊の`books`と題名のIndexは残ります。`pg_buffercache`など追加した拡張機能も、このDBで引き続き使えます。

## 大きなテーブルを、続けて読むとき

8ページの観察用テーブルでは、2回目からすべてのページが`hit`になりました。では、100万冊の`books`（7,353ページ）を続けて2回読んだら、2回目はすべて`hit`になるでしょうか。第1〜3章の全件検索の出力では、同じSQLを実行しても`hit`と`read`が毎回混ざっていました。

共有バッファの大きさには限りがあります。この環境の`shared_buffers`は128MBで、8kBのページなら16,384ページ分です。いっぱいになると、PostgreSQLは最近あまり使われていないページを選んで外し、空いた場所に新しいページを読み込みます。

図で、外すページと、空いた場所に入るページを見てください。

![9枠がすべて埋まった共有バッファから、しばらく使われていないP2を外して空きを作り、その空きへテーブルのファイルのP10を読み込む](/images/postgresql-query-journey/04-buffer-full.png)
*P2を外した場所が空きになり、新しいP10がそこへ入ります（9枠とページ番号は説明するための図。この環境の共有バッファは16,384ページ分）。*

大きなテーブルを全件読む検索が、読んだページをそのまま共有バッファに置いていくと、一度しか使わないページで共有バッファが埋まります。ほかの接続がよく使うページまで外されてしまいます。そこで大きなテーブルのSeq Scanでは、共有バッファの中に小さな区画を取り、その区画だけを輪のように使い回して読むことがあります。この区画を**リングバッファ**と呼びます。

輪の中では、新しく読み込んだページが、少し前に同じ輪へ読み込んだページの場所を使います。テーブルを最後まで読み終えたとき、輪に残っているのは最後のほうに読んだページだけです。そのため2回目に読むと、共有バッファに残っていたページだけが`hit`になり、残りのページは再び輪を通って`read`になります。`hit`と`read`が混ざるのは、このためです。

10ページのテーブルを4枠の輪で2回読む様子を、図で追ってみます。

![10ページのテーブルを4枠の輪で読むと、1回目の後にはP6〜P9だけが残り、2回目はその4ページがhitに、ほかの6ページが輪を通ってreadになる](/images/postgresql-query-journey/04-ring-buffer.png)
*①で輪に残ったP6〜P9だけが、②で`hit`になります。10ページ・4枠は説明するための図で、2回目は別の4枠を輪にして読みます。*

PostgreSQL 18では、通常の共有バッファを使うテーブルが共有バッファ全体の4分の1を超えることなどが、この読み方を選ぶ[条件](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/access/heap/heapam.c)です。`books`は57 MB（7,353ページ）で、128MBの4分の1（32MB）を超えています。

輪の大きさは[設定から計算されます](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/storage/buffer/freelist.c)。2026年9月28日に、この環境で`books`を写した使い捨てのテーブル（7,394ページ）を全件読むと、読み終えた後に共有バッファに残ったそのテーブルのページは94ページ（約750kB）でした[^ring]。共有バッファ全体の16,384ページの1%にも届きません。続けて2回目を読むと`shared hit=94 read=7300`で、`hit`になったのは、1回目の輪に残っていた94ページと同じ数でした。

[^ring]: `CREATE TABLE ... AS SELECT * FROM books`で作ったテーブルを`pg_buffercache_evict_relation`で追い出してから`count(*)`で全件読み、その後に`pg_buffercache`でそのテーブルのページを数えました。測った後、テーブルは削除しています。

Seq Scanが輪を使うのは、共有バッファにないページを読み込むときだけです。共有バッファにすでにあるページは、輪を通らずにそのまま`hit`になります[^ring-hit]。そのため、輪を通らずに共有バッファへ入ったページは、輪とは別に残り、次のSeq Scanでも`hit`に数えられます。たとえば、第3章のIndex Scanで読んだページは、輪を使わずに読み込まれます。

2026年9月29日に、`books`を写した使い捨てのテーブル（7,391ページ）で確かめました。全件を2回読んだ後、共有バッファに残っていたそのテーブルのページは188ページで、1回ごとの輪に残った94ページずつでした。続けてIndex Scanで番号1〜100,000の本を取り出すと、残っているページは924ページに増えました。そのあと全件を読むと`shared hit=924 read=6467`で、Index Scanで入った736ページも`hit`になりました[^ring-other]。

第1〜3章の全件検索でも、`hit`は数千あり、輪に残る94ページよりずっと多い数でした。これも、それより前の操作で輪を通らずに入ったページが残っていたためと考えられます。たとえば、データを作ったときに書き込んだページです。どの操作で入ったページだったかは、この本では確かめていません。

[^ring-hit]: [bufmgr.c](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/storage/buffer/bufmgr.c)の`BufferAlloc`は、読みたいページが共有バッファにあればそれを使い、なければ輪を含む空き場所の選び方（[freelist.c](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/storage/buffer/freelist.c)の`StrategyGetBuffer`）へ進みます。Index Scanがテーブルを読むときと、この章の後半で見るBitmap Heap Scanは、この輪を使いません。
[^ring-other]: 写したテーブルに番号のIndexを作り、`VACUUM`してから`pg_buffercache_evict_relation`で追い出して測りました。続けて、この章の後半で見るBitmap Heap Scanで番号500,001〜600,000の本を読むと、残っているページはさらに736ページ増え、次の全件読みは`shared hit=1754`でした。測った後、テーブルは削除しています。

## 木の段数と、hit・readの内訳を分ける

第3章で題名のIndexを作った後の検索は、`Buffers: shared hit=1 read=3`で、合わせて4回のアクセスでした。第4章では、この4回を、Indexの根・途中・葉の3ページとテーブルの1ページをたどる経路として図にしました。

図の「Indexの3ページ＋テーブルの1ページ」は、**どこへアクセスするか**の分け方です。一方、`hit=1 read=3`は、**必要なページが共有バッファにあったか**の分け方です。

同じページへ1回ずつアクセスする場合でも、共有バッファの状態によって内訳は変わります。この章の3回の実験でも、同じ8ページが、1回目は`read=8`、2回目は`hit=8`でした。次の表は、4回のアクセスで内訳がどう変わりうるかを説明する例で、実測した値ではありません。

| 4回のアクセス時の状態 | 表示の例 |
| --- | --- |
| すべて共有バッファにある | `hit=4` |
| 1回は共有バッファにあり、3回は読み込みが必要 | `hit=1 read=3` |
| すべて読み込みが必要 | `read=4` |

**Indexが3段だから`read=3`になるわけではありません。** 木の段数は、根から葉までにたどるページ数に関わります。hitとreadの内訳は、そのアクセス時のキャッシュの状態に左右されます。第3章の出力だけでは、hitした1回が根・途中・葉・テーブルのどれだったかも分かりません。

ここまでで、観察用テーブルの同じ8ページが1回目は`read=8`、2回目は`hit=8`になり、100万冊の`books`では輪を使い回して読むので、2回目にも`read`が残ることを見ました。どちらも、ページが共有バッファに残っていたかどうかの違いです。

## 目録の順番と、棚の順番が違うとき

ここからは、第3章で作った題名のIndex`books_title_idx`を使って、100万冊の`books`を探します。

第3章では、番号のIndexがあっても、11冊を探すときは`Index Scan`、90万冊を探すときは`Seq Scan`が選ばれました。その間の件数では、どんな探し方になるのでしょうか。今度は題名の範囲で探します。題名が「実験用の本 4」で始まる本をすべて取り出します。このデータでは、「実験用の本 4」以上「実験用の本 5」未満の題名を持つ本と同じになるので、その範囲を条件にします。番号でいえば4、40〜49、400〜499、4000〜4999、40000〜49999、400000〜499999の本で、合わせて111,111冊です。100万冊の約1割にあたります。

### 目録の順に取りに行くと、同じページに何度も戻る

Indexで場所が分かるなら、11冊のときのように、そのまま1冊ずつ取りに行けばよさそうです。そのとき、テーブルのページはどの順に開くことになるでしょうか。題名のIndexが、この範囲の本をどの順に並べているかを見てみます。`ORDER BY title`で題名の順に並べ、先頭の17冊を取り出します。第4章の`ctid`も一緒に表示して、各レコードがどのページにあるかを確かめます。

```sql
SELECT id, title, ctid FROM books
WHERE title >= '実験用の本 4' AND title < '実験用の本 5'
ORDER BY title LIMIT 17;
```

2026年9月28日、PostgreSQL 18.6での実行結果です。9〜14冊目は省いています。

```sql:実行結果
   id   |       title       |   ctid
--------+-------------------+-----------
      4 | 実験用の本 4      | (0,4)
     40 | 実験用の本 40     | (0,40)
    400 | 実験用の本 400    | (2,128)
   4000 | 実験用の本 4000   | (29,56)
  40000 | 実験用の本 40000  | (294,16)
 400000 | 実験用の本 400000 | (2941,24)
 400001 | 実験用の本 400001 | (2941,25)
 400002 | 実験用の本 400002 | (2941,26)
 …
 400009 | 実験用の本 400009 | (2941,33)
  40001 | 実験用の本 40001  | (294,17)
 400010 | 実験用の本 400010 | (2941,34)
(17 rows)
```

題名は文字として並ぶので、「実験用の本 4」の次は「実験用の本 40」、その次は「実験用の本 400」です。番号でいえば4、40、400、4000、40000、400000と、桁が一つずつ増えていきます。その先は、400009の次に40001が来て、その次は400010に戻ります。

一方、テーブルのレコードは番号の順にページへ並んでいます。`ctid`の左側の数がページ番号です。400000から400010までは、どれもページ2941に固まっていますが、その間に来る40001はページ294にあります。目録の順に1冊ずつ取りに行くと、ページ2941とページ294を行ったり来たりして、同じページを何度も開くことになります。第4章で見たとおり、`Buffers`は同じページを繰り返し使えばその分も数えるので、開き直した回数はアクセスの回数に表れます。

そこでPostgreSQLは、先に目録からレコードの場所を集め、ページごとにまとめてから、ページ番号の順にテーブルを読みます。ページ番号だけでなく、そのページの中のどのレコードを取り出すかも印で保持します。この、対象のレコード位置をまとめたものを**ビットマップ**と呼びます。

ビットマップを作る段階が`Bitmap Index Scan`、それを使ってテーブルを読む段階が`Bitmap Heap Scan`です。同じページにある対象レコードをまとめて取り出せるので、目録の順にページを行き来せずに済みます。図で、二つの読み方で開く回数がどう変わるかを見てください。

![目録の順に取りに行くとページ294と2941を行き来して5回開くが、ビットマップに集めてからならページ番号の順に2回で済む](/images/postgresql-query-journey/06-bitmap-scan.png)
*上の出力に出た5冊（40000、400000、400009、40001、400010）を取りに行く例です。下のビットマップは、この5冊のレコードの位置を数字で示しています。ページ番号とレコード位置は、上の出力の`ctid`のとおりです。ビット自体の配置は描かず、どの位置を覚えるかを説明するための図です。*

### 1割の本を、題名の範囲で探す

では、1割の範囲を実際に探すと、どの読み方が選ばれるでしょうか。11冊のときの`Index Scan`、90万冊のときの`Seq Scan`、いま見たビットマップを使う読み方のどれになるか、実行する前に予想してください。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM books WHERE title >= '実験用の本 4' AND title < '実験用の本 5';
```

2026年9月25日、PostgreSQL 18.6で、100万冊の`books`と題名のIndexがある状態で実行した結果です。

```sql:実行結果
Bitmap Heap Scan on books  (cost=3311.93..12314.92 rows=110000 width=30) (actual time=11.747..25.821 rows=111111.00 loops=1)
  Recheck Cond: ((title >= '実験用の本 4'::text) AND (title < '実験用の本 5'::text))
  Heap Blocks: exact=821
  Buffers: shared hit=1371
  ->  Bitmap Index Scan on books_title_idx  (cost=0.00..3284.43 rows=110000 width=0) (actual time=11.680..11.680 rows=111111.00 loops=1)
        …
        Buffers: shared hit=550
…
Execution Time: 29.090 ms
```

`Index Scan`でも`Seq Scan`でもなく、ビットマップを使う読み方が選ばれました。計画が2段になっています。下の`Bitmap Index Scan on books_title_idx`が、題名のIndexだけを読んでビットマップを作り、上の`Bitmap Heap Scan on books`が、それを使ってテーブルを読みます。PostgreSQLはテーブルのレコードを置く場所を**ヒープ**と呼ぶので、計画の`Heap`はテーブルのことです。

数字は下の段から読みます。`Bitmap Index Scan`の`rows=111111.00`は集めた場所の数で、`width=0`はレコードそのものを返していないことを表します。上の段の`Heap Blocks: exact=821`が、テーブルから読んだページの数です。111,111件の対象レコードは821ページに入っていて、その821ページを読みました。`exact`は、どのページについても、ページの中のレコードの位置まで印を持てたことを表します。

### 同じ11万冊を、ほかの方法で取り出すと

比べるために、この実験の間だけビットマップを候補から外し、同じSQLを実行します。設定で候補を減らすだけで、Indexを消すわけではありません。

```sql
SET enable_bitmapscan = off;
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM books WHERE title >= '実験用の本 4' AND title < '実験用の本 5';
```

実行結果です。

```sql:実行結果
Index Scan using books_title_idx on books  (cost=0.42..14532.64 rows=110000 width=30) (actual time=0.571..16.464 rows=111111.00 loops=1)
  …
  Buffers: shared hit=22395
…
Execution Time: 19.673 ms
```

`Index Scan`になり、`Buffers`は`shared hit=22395`です。この22,395回には、テーブルとIndexの両方へのアクセスが含まれます。ビットマップを使った計画の合計1,371回より多いことは分かりますが、この出力だけでは、テーブルへのアクセスとIndexへのアクセスを分けられません。テーブルの821ページだけを開き直した回数とは読まないでください。

さらに`Index Scan`も候補から外すと、`Seq Scan`になります。

```sql
SET enable_indexscan = off;
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM books WHERE title >= '実験用の本 4' AND title < '実験用の本 5';
```

実行結果です。

```sql:実行結果
Seq Scan on books  (cost=0.00..22353.00 rows=110000 width=30) (actual time=0.039..1785.254 rows=111111.00 loops=1)
  …
  Rows Removed by Filter: 888889
  Buffers: shared hit=2583 read=4770
…
Execution Time: 1788.428 ms
```

設定を元に戻しておきます。

```sql
RESET enable_bitmapscan;
RESET enable_indexscan;
```

| 比較するもの | Seq Scan | Index Scan | Bitmap Index ScanとBitmap Heap Scan |
| --- | --- | --- | --- |
| 返したレコード | 111,111 | 111,111 | 111,111 |
| Rows Removed by Filter | 888,889 | 表示なし | 表示なし |
| 実行時のページへのアクセス回数 | 7,353 | 22,395 | 1,371（テーブル821、Index550） |
| Execution Time | 1788.428 ms | 19.673 ms | 29.090 ms |

同じ111,111件を返すのに、ページへのアクセス回数は三つとも違います。`Seq Scan`は7,353ページを全部読み、9割近いレコードを除外しました。`Index Scan`は除外するレコードこそありませんが、テーブルとIndexを合わせて22,395回ページにアクセスしました。ビットマップを使う方法は、テーブルのページを821回、つまり1ページにつき一度ずつ読み、Indexのページを550回読みました。

実行時間は、今回は`Index Scan`がいちばん短くなりました。一方、PostgreSQLが方法を選ぶための実行前の見積もりである`cost`は、ビットマップの方法が小さくなっています（今回は12314.92と14532.64）。PostgreSQLは、ページを読む処理やレコードを比べる処理などの見積もりに基づいて方法を選びます。その見積もりが、今回の実行時間の順と一致しなかった、と読みます。見積もりの仕組みは第10章で確かめます。

:::details 時間の差について
`Index Scan`もビットマップの計画も、アクセスはすべて`hit`です。「メモリにあったから」だけでは、二つの時間差を説明しきれません。ビットマップを組み立てる処理や、実行順による状態の違いなども関わりえます。あなたの結果では、ビットマップの計画に`read`が含まれていたり、二つの時間の順が入れ替わっていたりするかもしれません。この各1回の結果だけで、どちらが速いかや原因を決めないでください。
:::

:::details Recheck Condという表示について
ビットマップは、処理ごとの作業用メモリ（`work_mem`で大きさが決まるメモリ）に置きます。収まらなくなると、一部のページについてレコードの位置を省き、「このページのどこか」という粗い形に切り替えることがあります。この`lossy`という方式では、ページごとに1ビットの印を持ち、テーブルを読んだ後で条件に合うレコードかを確かめ直します。その確かめ直しに使う条件が`Recheck Cond`で、確かめ直しが要るときに備えて、計画にはいつも表示されます。今回は`Heap Blocks: exact=821`で、すべてレコードの位置まで持てていたので、確かめ直しは起きていません。粗い形になったページがあると、`lossy=`の数が並びます。作業用メモリの大きさは第7章で変えて観察します。
:::

:::details Seq Scanが約1.8秒かかった理由
表の`Seq Scan`の約1.8秒は、ほとんどがページを読む時間ではなく、題名の並び順を比べる時間です。文字列の大小を決める並び順の決まりを**照合順序**と呼びます。この本の実験用DBの照合順序は`en_US.utf8`で、言語の決まりに沿って並べるため、文字コードの数値をそのまま比べるより手間がかかります。[C/POSIX以外の照合順序では比較が高コストになりうる](https://www.postgresql.org/docs/18/locale.html)と公式文書でも説明されています。

確かめるために、同じ範囲を、文字コードの順に比べる`COLLATE "C"`を付けてSeq Scanで比べ直しました。2026年9月28日に2回ずつ測ると、`en_US.utf8`のままでは約2,300ミリ秒、`COLLATE "C"`では約65ミリ秒でした。返すレコード数も、除外したレコード数も同じです。表の1,788ミリ秒とは別の日の測定なので時間はそろいませんが、照合順序を変えるだけで30倍以上の差が出ました。照合順序は、付録で`LIKE`の前方一致にIndexが使えない理由としても出てきます。
:::

## ページを再利用しても、調べるレコード数は減らない

調べる範囲を減らす変更（第3章のIndex）と、ページをメモリから再利用することは別の効果です。この二つを、出力で分けて読めるようになりました。ビットマップを使う読み方は、そのどちらとも違い、テーブルのページを読む順番を変えて、同じページを開き直す回数を減らしていました。

改善の前後を比べるときも、時間だけでなく、計画、レコード数、`hit`と`read`を一緒に記録します。同じデータと設定で複数回測り、ページを再利用できていたかも確認してください。

## まとめ

- `hit`は共有バッファにあったページ、`read`は読み込んだページ。内訳はそのときの共有バッファの状態で決まり、Indexの段数とは別に読む。2回目が速くなるのはページを再利用したからで、調べるレコード数は変わらない。
- 大きなテーブルのSeq Scanは、共有バッファの小さな区画（リングバッファ）を使い回して読む。そのため同じSQLを続けても、2回目に`read`が残る。Index Scanで読んだページのように輪を通らずに入ったページは、輪とは別に残って`hit`になる。
- Indexの順とテーブルのページの順が違うと、1件ずつ取りに行くたびに同じページを開き直す。Bitmap Heap Scanは、場所を集めてからページ番号の順に一度ずつ読む。
- 時間を比べるときは、同じデータと設定で何回か測り、計画、レコード数、`hit`と`read`を一緒に記録する。
