## 本の到達点

SQLを動かすプロセスが、計画に従ってデータ構造をたどり、ページをメモリへ読み込み、処理する様子を説明できる。その説明をEXPLAINと実験で確かめ、ネットやAIの改善案を自分の条件で評価できる。

## 解説の深さ

「本文で扱う」は用語の紹介に加え、具体例を追い、観察結果と対応させ、条件を変えて考えるところまでを指す。補足は読み飛ばしても次章の中心課題に進める内容にする。

| 章 | 解説する範囲と境界 |
| --- | --- |
| 序章 | 困りごととSQLの意味、計測条件まで。改善案の答えは第12章で回収する。 |
| 第1章 | EXPLAIN、ANALYZE、rows、costの入口まで。時間の複雑な内訳とloopsは後続章で補う。 |
| 第6章 | 接続ごとのバックエンド、SQLの処理段階、Index ScanとLimitの実行の図まで。保守プロセスは第11章で扱う。 |
| 第4章 | ページの役割と行の場所まで。TOASTは入口、生ページの詳細と全forkの構造は補足。 |
| 第5章 | 共有バッファ・OSキャッシュ・作業用メモリの区別まで。置換アルゴリズムの実装やOSの調整は発展。 |
| 第2章 | 走査を手で追い、仕事量の増え方を説明する。CPU命令やSIMDの実装は扱わない。 |
| 第3章 | 根から葉、葉から表、分割の必要性、維持負担まで。競合制御と分割の厳密な実装は補足。 |
| 第7章 | 比較・分割・合流の図とwork_memまで。ソート実装の網羅や万能な設定値は目標にしない。 |
| 第8章 | ヒープの更新を具体例で追い、Index順で止まれる条件まで。コード実装と厳密な証明は任意課題。 |
| 第9章 | 3方式とハッシュ集約、メモリ不足時の入口まで。高度な結合順序探索は第10章の補足。 |
| 第10章 | 基本統計と見積もりの伝播まで。拡張統計、Memoize、並列計画は用途と限界の紹介。 |
| 第11章 | MVCC、可視性マップ、VACUUM、WALとcheckpointの役割まで。回復手順、分離レベル全種、レプリケーションは発展。 |
| 第12章 | 同じ条件での比較とサービス要件による判断まで。本番監視基盤や集計更新基盤の構築は別テーマ。 |

## 章をまたぐ問いの回収

| 最初に生まれる問い | 理解に必要なつながり | 回収する章 |
| --- | --- | --- |
| 20冊だけなのに遅いのはなぜ？ | 入力の走査 → 結合 → 集約 → 上位選択 | 2・8・9を経て12 |
| 同じSQLでも時間が違うのはなぜ？ | プロセス → ページ → キャッシュ → 比較条件 | 4〜6、12 |
| Indexがあるのに使わないのはなぜ？ | 木で絞る → 表を読む → 対象割合 → コスト | 3・8・10 |
| メモリを増やせば速くなる？ | 共有バッファと作業領域 → spill → 同時実行 | 5・7・9 |
| LIMITがあるのに全件読むのはなぜ？ | 行の要求 → 必要な入力 → ソートと上位候補 | 2・5・7・8 |
| 更新後、Indexだけでは済まなくなるのはなぜ？ | 行のバージョン → 可視性 → 可視性マップ | 3・6を経て11 |
| AIの改善案を採用してよい？ | 減る仕事 → 計測 → 同じ結果 → サービス要件 | 各章の課題を経て12 |

## 読み方と実験の共通設計

- 第2〜4章は、PIDの違い・表のサイズ・BUFFERSの変化という小さな観察から始める。アーキテクチャの講義だけを3章続けない。
- 主実験は通常テーブルを使う。第1章で本100万冊・読了記録200万件を準備し、初期容量とログで進む選択肢を提示する。第2章ではデータ量を変えず、LIMITによる途中終了を比較する。
- 各章の実験開始時に、件数・Index・設定・トランザクション状態を示す。設定や一時的なIndexの復元方法を添える。
- 既存ログの転用時は、PostgreSQLのバージョン・Dockerか直接実行か・通常表か一時表かを区別する。追加実験を未実施のまま実測結果として書かない。
- 予想の後に出力と図を置く。説明用の図と実測値の図を区別する。
- 第11章の後では、ページの読み込みだけでなく、更新・可視性・耐久性も説明できるようにする。復旧操作の手順書までは広げない。
- 各章の到達点は、用語を言えることではなく、初見の条件で予想・観察・説明ができるかで確認する。
- 最終課題は、ランキング改善について「前提・仮説・比較条件・同じ結果の確認・実測・採用理由・残る不確実性」を短くまとめる。
