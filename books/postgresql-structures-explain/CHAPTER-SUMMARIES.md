序章から第12章までの構成レビュー用。本文の完成稿ではなく、各章で何をどの順序で伝えるかを示す。追加実験は未実施。

## [序章：20冊のランキングが、なかなか出てこない](00-prologue.md)

### Summary

SQLの結果は読めても、なぜその処理が速い・遅いのかは説明できない。その疑問を出発点に、本書の目的と想定読者を伝えます。読書記録サービスのランキングを共通の題材として紹介し、20冊を返すまでに約4.6秒かかった既存実験と、小さなデータでのSQL・出力を示します。改善案を選ぶ根拠を得るために、EXPLAIN、データ構造とアルゴリズム、PostgreSQL内部をつなげて学ぶ、という本全体の道筋を案内します。

### 本文の流れ

1. はじめに、SQLの結果から内側の仕組みへ関心を広げ、本書の目的と到達点を伝える。
2. 想定読者、前提となるSQLの経験、実験に必要な操作を案内する。
3. 読書記録サービスを紹介し、本と読了記録のサンプル行・図からランキングの意味を共有する。
4. データ量と対象期間を示し、既存実験の約4.6秒を条件付きで紹介する。画面の待ち時間とSQLの測定値は分ける。
5. ランキングSQLと小規模データでの出力を読む。欲しい結果と、内部の処理手順を区別する。
6. 索引、返す件数、事前集計の案を示し、今ある情報では判断できない点を残す。
7. 全12章の道筋と扱う範囲、図・SQL・実行結果を行き来する読み方を示す。
8. 今の改善案を書き残して第1章の観察へ進み、最終章で考え直すことを案内する。

## [第1章：SQLの動きを観察する道具を手に入れる](01-explain-basics.md)

### Summary

最初の観察は、題名で1冊の本を探す小さなSQLから始めます。実験環境を用意し、EXPLAINで予定を、EXPLAIN ANALYZEで実際の処理を読みます。返した行と条件から除外した行を区別し、番号で探した場合との違いを観察します。結果件数とSQLの仕事量は同じではないと理解し、以降の実験で使う道具を手に入れる章です。

### 本文の流れ

1. ランキング全体の前に、その部品である「本を探す」処理を切り出す理由を伝える。
2. Dockerとpsqlを準備し、小規模データ・件数・主キー・索引の初期状態を確認する。
3. SQLから計画・実行・結果までを短い図で示し、題名検索が何冊調べるか予想する。
4. EXPLAINを実行し、ノード名と推定rowsを読む。costの単位を実時間と分ける。
5. EXPLAIN ANALYZEで、返した行・除外した行・時間を確認し、予想と比較する。
6. 同じ本を番号で探して計画の違いを観察する。存在しない題名を探す課題で理解を確かめる。
7. 環境の中断・再開方法を案内し、この計画を動かすプロセスへの疑問で終える。

## [第2章：SQLは誰が受け取り、どう実行するのか](02-process-and-execution.md)

### Summary

SQLはクライアントから送られ、接続を担当するバックエンドで解析・計画・実行へ進みます。二つの接続とPIDを観察して処理の担当を確かめ、実行計画の木が行を返す様子を小さな模型で追います。プロセスごとの仕事と共有する領域を区別し、メモリやファイルをどこに位置付ければよいかを理解します。

### 本文の流れ

1. 二つの接続を開き、同じSQLを送ったときに誰が処理するかを予想する。
2. pg_backend_pid()とpg_stat_activityで接続とバックエンドを対応させ、クライアント・サーバの図を描く。
3. 一つのSELECTを解析・書き換え・計画・実行の順に追い、各段階の役割を説明する。
4. Scan・Sort・Limitの小さな木で、行を要求する向きと返す向きを追う。
5. バックエンド、共有メモリ、主要な裏方のプロセスを地図へ配置する。並列ワーカーの存在も位置付ける。
6. 別接続と共有できるものを読者に描いてもらい、実際に読むデータの保存先へ進む。

## [第3章：テーブルの行は、どこに保存されているのか](03-pages-and-storage.md)

### Summary

SQLの表は、物理的にはファイルやページに保存されています。表のサイズや行の位置を観察し、行数・ページ数・バイト数を別々の量として捉えます。索引から表を参照する関係や、長い値を保存する仕組みの入口にも触れます。同じ件数でも読み込み量が違う理由を説明するための土台を作る章です。

### 本文の流れ

1. booksの数行を表示し、この行がどこに保存されているかを問いにする。
2. 保存先とサイズを調べ、論理的な表と、表・索引などの物理的な領域を対応させる。
3. ページサイズを確認し、一つのページに管理情報と複数の行がある模型を描く。
4. ctidを手掛かりに行の位置を観察し、永続的な主キーとの違いを説明する。
5. 同じ行数で行幅を変え、サイズがどう変わるか調べる。長い値とTOASTを補足する。
6. 行数だけでは読むページ数を決められないと整理し、ページをどこから読むかへ疑問を移す。

## [第4章：同じSQLでも時間が変わるのはなぜか](04-memory-and-buffers.md)

### Summary

同じSQLを繰り返し実行し、時間とBUFFERSの表示を比較します。ページを使う経路を、バックエンド・共有バッファ・OSキャッシュ・ファイルの関係として整理します。共有バッファと作業用メモリ、一時テーブルと一時ファイルも区別します。観測値から言える範囲を押さえ、改善前後を比較するための測定条件を考えられるようになります。

### 本文の流れ

1. 同じ検索を複数回実行し、計画・行数・時間・BUFFERSに何が変わるか予想して記録する。
2. ページの読み込み経路を図解し、shared hitとshared readを対応させる。
3. OSキャッシュを加え、readだけでは物理ストレージの読み込みを断定できない理由を説明する。
4. アクセス回数とページの種類数、親子ノードの集計範囲、localとtempの違いを整理する。
5. 各メモリ設定を役割別に並べ、共有ページ・処理の作業領域・メンテナンスを区別する。
6. 初回と繰り返し実行の条件を残す比較方法をまとめ、時間差への別の仮説を挙げる課題で締める。

## [第5章：1冊を探すために、何冊調べているのか](05-linear-search.md)

### Summary

本が増えたとき、1冊を探す仕事はどれだけ増えるのでしょうか。検索条件を固定してデータ量を増やし、返した行・除外した行・ページアクセスを比べます。LIMITによる途中終了や、見つからない場合も試します。線形探索の仕事量を具体例から理解し、「少数の結果なら軽い」という判断を自分で確かめられるようになります。

### 本文の流れ

1. 題名検索を固定し、本が増えたときの結果件数・除外行数・時間をそれぞれ予想する。
2. 実験設定をそろえ、1,000冊・10万冊・100万冊へ増やして比較する。
3. カードを順番に調べる模型と観測値をつなぎ、その後で線形探索とO(n)に名前を付ける。
4. LIMIT 1、該当行の位置、該当行なしを比べ、途中で止まれる条件を考える。
5. 第3・4章のページとBUFFERSを使い、行数だけでなくアクセス量からも仕事を比べる。
6. 「LIMIT 1だから安心」という提案を検討し、番号検索が途中を飛ばせる仕組みへ進む。

## [第6章：B-treeは、どうやって探す場所を絞るのか](06-btree-index.md)

### Summary

索引自体も多くのページを持つのに、B-treeは目的の場所を少ない段数で絞り込みます。小さな木を手でたどり、実際の索引の高さやページアクセスと対応させます。一点検索から範囲検索へ条件を広げ、表の行を取り出す仕事と索引を維持する仕事も考えます。索引の効果を、使ったかどうかだけでなく減らした仕事から説明する章です。

### 本文の流れ

1. 表と索引の大きさを確認し、索引も全部読むなら速くならないはず、という疑問を置く。
2. 具体的な番号を持つ小さな木で、根から葉までの探索を予想しながらたどる。
3. 実際の索引の高さや検索時のページアクセスを観察し、模型との対応と違いを整理する。
4. 題名に索引を追加し、同じ検索の前後で計画・アクセス量・時間を比較する。
5. 一点検索から範囲検索へ広げ、木を降りる仕事と、その後に多くの行を読む仕事を分ける。
6. 保存容量、挿入・更新、ページ分割の必要性を扱い、検索の利益と維持の負担を考える。
7. 索引を採用する条件を言葉にし、次の章の「見つけた行を並べる」仕事へつなぐ。

## [第7章：並べ替えの仕事と、メモリの境界を観察する](07-sort.md)

### Summary

読了記録を新しい順に並べるために、どんな仕事が必要でしょうか。少数の値の比較から始めて、実行計画のSortと対応させます。件数とwork_memを別々に変え、メモリ内での処理と一時ファイルを使う処理を観察します。作業メモリをプロセスの地図へ戻し、並べ替えが遅いときに何を確認すべきかを整理します。

### 本文の流れ

1. 日時順の一覧を題材にし、絞り込む行数と並べる行数を確認する。
2. 日時カードを比べる模型で仕事を数え、比較ソートとO(n log n)の見方を導入する。
3. Sortの入力行数・キー・方式・メモリを読み、親ノードの時間に子の処理が含まれることを確認する。
4. データを固定してwork_memを変え、メモリ内の処理と外部ソートを比較する。
5. 一時ファイルへの分割・合流を図示し、表のsharedと作業中のtempを分けて読む。
6. 複数の処理・接続が使う作業領域を図に戻し、単にメモリを増やす案の確認条件をまとめる。
7. 上位20件だけ欲しいときも全体を並べる必要があるか、という問いを次章へ残す。

## [第8章：上位20件だけを選ぶには](08-top-n-heap.md)

### Summary

上位20件だけが必要なとき、すべての順位を確定する必要はあるのでしょうか。少数の候補を保つヒープを具体例で追い、top-N heapsortの出力と対応させます。さらに索引の順序を利用する取得方法と比較します。調べる件数・候補として保持する件数・返す件数を分け、LIMITが減らす仕事を説明できるようになります。

### 本文の流れ

1. 前章の一覧にLIMITを付け、走査量・保持量・結果件数のどれが減るか予想する。
2. LIMITの前後を測り、少数の結果でも入力全体を読む場合があることを観察する。
3. 上位3件のカード模型で候補の入れ替えを追い、ヒープの部分的な順序を理解する。
4. top-N heapsortの表示、候補の保持量、nとkによる仕事の増え方を模型につなぐ。
5. 日時の索引を追加し、順序を利用して必要な件数で止まれる場合を比較する。
6. 取得件数を増やし、同じ索引が必ず有利とは限らないことを観察する。
7. 日時順と読了数順のランキングは同じかを問い、数える・組み合わせる処理へ進む。

## [第9章：本と読了記録を組み合わせ、数える](09-join.md)

### Summary

読了記録に題名を付け、本ごとに読了記録を数える処理を学びます。少数の行を繰り返し探す方法から始め、大量の行をハッシュ表で照合する方法、並んだ入力を合流させる方法へ広げます。集約では入力行数とグループ数を区別し、メモリとの関係も観察します。結合や集計の前に行を減らす案を、意味と仕事量の両面から考える章です。

### 本文の流れ

1. ER図と少数の行で、読了記録へ題名を付ける作業を手で行う。
2. 20件を索引で繰り返し探すNested Loopを観察し、loopsとループ当たりの値を読む。
3. 対象を大量の行へ広げ、Hash Joinの準備と照合を小さなハッシュ表で追う。
4. 並んだ二つの入力を合流させるMerge Joinを追い、入力を並べる準備も比較する。
5. 本ごとのカウンタを更新するHashAggregateを描き、入力行数とグループ数を分ける。
6. ハッシュ表がメモリに収まらない場合を観察し、予算と分割処理を結び付ける。
7. 先に集計してから題名を付けても同じ結果になる条件を考え、処理方式を選ぶプランナへ進む。

## [第10章：PostgreSQLは、なぜその計画を選んだのか](10-planner-and-statistics.md)

### Summary

PostgreSQLは実行前に行数や仕事量を見積もり、処理方法を選びます。条件の広さやデータの偏りを変え、統計情報・推定行数・実際の計画を対応させます。costを実時間と区別し、推定のずれが後続の処理へ及ぼす影響を考えます。期待と違う計画を見たとき、何を確かめてから改善を試すかを組み立てる章です。

### 本文の流れ

1. 条件を狭くした場合と広くした場合を比べ、同じ索引があっても選ぶ方法が変わるか観察する。
2. 頻度や分布の図とpg_statsを対応させ、推定行数の材料を説明する。
3. 各ノードの推定と実測を比べ、ずれが結合やソートの判断へどうつながるかを追う。
4. データ変更とANALYZE前後の比較を通じて、統計の更新と実行時の計測を区別する。
5. ページと行の仕事を見積もる模型でcostを説明し、startup・total・LIMITの関係を見る。
6. 列の相関、拡張統計、並列計画、Memoizeを発展の入口として位置付ける。
7. 計画を強制する前の確認手順をまとめ、統計だけでは説明できない更新・可視性の話へつなぐ。

## [第11章：更新された行と、読み手から見える行](11-mvcc-and-maintenance.md)

### Summary

更新中の表を複数の接続から読むと、同じ行でも見える値が異なることがあります。スナップショットと行のバージョンを観察し、不要な領域の回収、可視性マップ、Index Only Scanを結び付けます。最後にWALとデータページの書き出しを整理します。読み取り性能を、更新・後片付け・耐久性まで含めて考えるための章です。

### 本文の流れ

1. 二つの接続で更新とCOMMITを観察し、分離レベルを固定した時間軸に見える値を書き込む。
2. 更新前後の行バージョンをページの模型で示し、読み手が必要とする古い情報を考える。
3. VACUUMとANALYZEを役割で分け、autovacuumと長いトランザクションの関係を説明する。
4. 索引に必要な列があることと、行が見えることを区別し、可視性マップを導入する。
5. 更新・VACUUM前後でHeap Fetchesを比べ、Index Only Scanと表へのアクセスを対応させる。
6. 共有バッファの変更、WAL、データファイルを図示し、COMMITとページ書き出しの違いを整理する。
7. 読み込みの速さだけでは更新を伴う設計を評価できないとまとめ、ランキングの最終判断へ戻る。

## [第12章：ランキングを読み解き、改善を選ぶ](12-ranking-revisited.md)

### Summary

序章のランキングを、ここまで学んだ観察方法・アルゴリズム・内部構造から読み解きます。索引の追加、集計と結合の順序の変更、事前集計について、減る仕事と残る仕事を予想して比較します。結果が同じか、必要な鮮度を満たすか、更新の負担は何かも確かめます。AIや検索で得た案を、自分の条件と根拠で判断するところまでを本の到達点にします。

### 本文の流れ

1. 序章で選んだ改善案を振り返り、現在のデータ・索引・設定・更新状態で基準を測る。
2. 計画を行の流れへ描き直し、推定と実測、繰り返し、ページアクセスから多くの仕事が残る箇所を探す。
3. 3つの改善案について、どの仕事が減り、何が残り、新しい負担は何かを先に予想する。
4. 索引の追加を比較し、検索経路の変化と結合・集約に残る仕事を確認する。
5. 先に集計・上位選択してから本を結合する案を試し、意味が同じになる前提と結果の一致を確かめる。
6. 事前集計の作成と読み出しを分けて測り、更新・訂正・削除・鮮度の責任を考える。
7. 応答時間と鮮度の要件を明示して採用案を選び、要件が変わった場合も考える。
8. 初見の提案に対する確認手順を整理し、3領域の知識を使った短い調査メモを最終課題として書く。
