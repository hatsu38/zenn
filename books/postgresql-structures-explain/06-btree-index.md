## この章で分かること

索引自体も多くのページを持つのに、B-treeは目的の場所を少ない段数で絞り込みます。小さな木を手でたどり、実際の索引の高さやページアクセスと対応させます。一点検索から範囲検索へ条件を広げ、表の行を取り出す仕事と索引を維持する仕事も考えます。索引の効果を、使ったかどうかだけでなく減らした仕事から説明する章です。

## はじめに：目録も大きいのに、どう探す？

本が100万冊になりました。題名を順番に比べると、多くの行を読む必要があります。一方、番号検索は索引という目録を使えました。

でも、索引にも100万冊分の情報があるはずです。索引を先頭から全部読んでいたら、あまり助けにならなそうです。

本棚の隣に大きな目録があるとします。目録の中でどう探すかが、次の疑問です。

![目録も大きい。それでも速い？](/images/postgresql-structures-explain/06-catalog-question.png)
*学ぶきっかけを描く、説明用の場面。*

目録は索引の役割を表す絵です。本文ではB-treeのページと具体的なキーへ置き換えて追います。

そこで使うのが、**範囲を分けながら進む木構造**です。PostgreSQLの標準的な索引では、B-treeという仕組みが使われます。

## 範囲を分ける案内板

まずは、番号1〜9の小さな模型です。上の箱にある境界の番号を見て、進む先を選びます。実際の索引はもっと多くの項目を一つのページに持ちます。

![境界を比べて、読むページを絞る](/images/postgresql-structures-explain/06-btree-path.png)
*B-treeの小さな模型 ／ 実際の項目数はもっと多い。*

番号8なら、どこへ進みますか。1、2、3、4……と全冊を確かめる必要はありません。最初の案内で「7以上」の枝へ進めます。

一番上を**根**、途中の案内を**内部の節**、行の場所へつながる末端を**葉**と呼びます。根は一つですが、枝分かれするため、少ない段数で多くの情報を分けられます。

## 段数は、冊数と同じ速さでは増えない

仮に一つの案内が100個の行き先を持つなら、2段の案内で100×100、3段なら100×100×100の範囲を分けられます。これは増え方をつかむための模型で、実際の索引の分岐数を測った値ではありません。

本が増えても、毎回案内の段を一つ足す必要はありません。この「掛け算で分けた範囲を逆にたどる」増え方が、`O(log n)`という見方につながります。

`log`を初めて見ても、まずは**100万件だから100万回案内を読むわけではない**と理解できれば十分です。表から取り出す行が大量なら、その分の仕事は別に必要です。

## 題名にも索引を作る

第5章の100万冊をそのまま使います。索引を作る前に、題名検索を記録してください。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM books WHERE title = '実験用の本 42';
```

今回、索引を作る前の結果は次のとおりでした。

```text
Seq Scan on books  (cost=0.00..19852.99 rows=1 width=30) (actual time=0.110..81.524 rows=1.00 loops=1)
  Filter: (title = '実験用の本 42'::text)
  Rows Removed by Filter: 999999
  Buffers: shared hit=7353
Planning Time: 0.510 ms
Execution Time: 81.675 ms
```

返した行は1行、除外した行は999,999行です。`loops=1`なので、合計100万行に条件を当てています。第5章の`LIMIT 1`とは違い、今回は条件に合う行をすべて求める検索です。

続いて題名用の索引を作り、統計情報を更新します。

```sql
CREATE INDEX books_title_idx ON books (title);
ANALYZE books;
```

```text
CREATE INDEX
ANALYZE
```

同じ題名検索を、もう一度実行します。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM books WHERE title = '実験用の本 42';
```

```text
Index Scan using books_title_idx on books  (cost=0.42..8.44 rows=1 width=30) (actual time=0.145..0.146 rows=1.00 loops=1)
  Index Cond: (title = '実験用の本 42'::text)
  Index Searches: 1
  Buffers: shared hit=1 read=3
Planning:
  Buffers: shared hit=8 read=1
Planning Time: 0.631 ms
Execution Time: 0.191 ms
```

今度は`Index Scan using books_title_idx`になりました。作った題名の索引を使っています。さっきの`Filter`に代わり、`Index Cond`に題名の条件が出ていることも確認できます。

| 比較するもの | 索引を作る前 | 索引を作った後 |
| --- | --- | --- |
| 探す方法 | Seq Scan | Index Scan |
| 返した行 | 1行 | 1行 |
| Rows Removed by Filter | 999,999行 | 表示なし |
| 実行時のshared hit | 7,353 | 1 |
| 実行時のshared read | 表示なし | 3 |
| Execution Time | 81.675 ms | 0.191 ms |

### 今回、索引で何が変わった？

1. **探し方が変わった。** `Seq Scan`から`Index Scan using books_title_idx`へ変わり、題名の条件を索引の探索に使うようになりました。
2. **ページへのアクセスが減った。** 実行時のBUFFERSは7,353回から、hit 1回＋read 3回の合計4回になっています。
3. **返す結果は同じ1行だった。** 返す件数を減らして速くしたのではなく、同じ本を取り出すまでの調べ方が変わっています。

第4章では、時間が短くなっても計画とバッファアクセスは同じでした。今回は両方が変わっているため、時間の数字に加えて、**索引によって読む範囲を絞れた根拠**があります。

`Index Searches: 1`は索引の探索を1回行ったという表示で、1ページだけ読んだという意味ではありません。また、`read=3`からSSDを3回読んだとは断定できません。第4章で見たとおり、OSキャッシュから読み込める場合もあります。`Planning`のBUFFERSは計画作成時の情報なので、この4回には足しません。

今回の実行時間は81.675 msから0.191 msへ短くなりました。ただし、それぞれ1回の結果です。この時間差をいつでも出る倍率として覚えるより、**同じ結果を返すために、読む範囲を大きく減らせた**ことを押さえてください。

索引の大きさも測れます。

```sql
SELECT pg_size_pretty(pg_relation_size('books_title_idx'));
```

```text
 pg_size_pretty
----------------
 39 MB
(1 row)
```

今回の題名用の索引は、`pg_size_pretty`の表示で39 MBでした。速く探すための情報も、別の保存領域を使っています。これは索引の格納領域の大きさで、1回の検索で39 MBすべてを読むという意味ではありません。

## 一点を探した後に、たくさん読む場合

「8だけ」ではなく「4以上8以下」を欲しいとします。

![4以上8以下なら、隣の葉も読む](/images/postgresql-structures-explain/06-range-scan.png)
*索引の葉をたどる模型 ／ 表への参照は省略。*

最初の位置を少ないページアクセスで見つけても、範囲内の項目は順に読む必要があります。さらに題名などが必要なら、索引から表の行も参照します。

今度は番号の範囲で探します。ここで使えるのは、先ほど作った題名用の`books_title_idx`ではなく、主キーの番号用の索引`books_pkey`です。

まず、400000から400010までの11冊を探します。`BETWEEN`は両端の値を含みます。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM books WHERE id BETWEEN 400000 AND 400010;
```

```text
Index Scan using books_pkey on books  (cost=0.42..8.64 rows=11 width=30) (actual time=0.062..0.065 rows=11.00 loops=1)
  Index Cond: ((id >= 400000) AND (id <= 400010))
  Index Searches: 1
  Buffers: shared hit=7
Planning:
  Buffers: shared hit=6
Planning Time: 0.272 ms
Execution Time: 0.087 ms
```

`books_pkey`を使う`Index Scan`になり、11行を返しました。実行時のバッファアクセスは`shared hit=7`です。索引で範囲の始まりを探し、必要な行を取り出す方法が選ばれています。

では、1から900000までの90万冊ならどうでしょうか。同じ番号の索引が使える状態で、条件だけを広げます。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM books WHERE id BETWEEN 1 AND 900000;
```

```text
Seq Scan on books  (cost=0.00..22353.00 rows=902218 width=30) (actual time=0.014..65.590 rows=900000.00 loops=1)
  Filter: ((id >= 1) AND (id <= 900000))
  Rows Removed by Filter: 100000
  Buffers: shared hit=7353
Planning:
  Buffers: shared hit=4
Planning Time: 0.093 ms
Execution Time: 93.493 ms
```

今度は`Seq Scan`です。90万行を返し、条件に合わない10万行を除外しています。表の100万行のうち、9割が必要になる検索です。

| 比較するもの | 11冊を探す | 90万冊を探す |
| --- | --- | --- |
| 選ばれた方法 | Index Scan（books_pkey） | Seq Scan |
| 推定の出力行数 | 11 | 902,218 |
| 実際の出力行数 | 11 | 900,000 |
| 実行時のshared hit | 7 | 7,353 |
| Execution Time | 0.087 ms | 93.493 ms |

### 索引があっても、毎回使うわけではない

11冊を探すときは`books_pkey`を使い、90万冊を探すときは表を順に読む方法が選ばれました。索引を消したわけではありません。変えたのは、検索する番号の範囲です。

少数の行なら、索引で場所を絞る方法が役立ちます。一方、表の大部分が必要なら、索引をたどってから大量の表の行を参照するより、表を順に読むほうが有利だと見積もられることがあります。

この結果から持ち帰りたいのは、**「索引を使ったか」だけでなく、「何割の行が必要なのか」も見る**ということです。90万行を返す検索を改善したいなら、必要な件数や列を減らせないかも検討対象になります。

この二つは返す件数が違う検索なので、時間差をそのまま「索引と逐次走査の速度差」とは扱えません。また、この出力だけで90万行の検索では索引が必ず遅いと証明したわけでもありません。**索引があっても、必要な範囲によって選ぶ方法が変わる**ことを確認してください。選ぶ理由は第10章で扱います。

## 行の追加・更新に伴う索引の変更

本を1冊増やすなら、表だけでなく目録にも書き足す必要があります。題名を変更するなら、題名の索引にも対応が必要です。

索引のページがいっぱいなら、分割などの調整も必要になります。毎回分割するわけではありませんが、索引は無料の近道ではないのです。

読み込みの利益、保存容量、追加や更新の負担を一緒に考えます。仕組みをさらに調べる入口は[PostgreSQLの索引の説明](https://www.postgresql.org/docs/18/indexes.html)です。

## 確かめる問い

「1件検索が速くなったので、90万件を取り出すSQLも同じ倍率で速くなる」と言ってよいでしょうか。

:::details 考え方
木で場所を絞る仕事と、その後に多くの行を取り出す仕事は別です。対象範囲を変え、計画とアクセス量を測って確かめます。
:::

題名の索引は後の章でも使うので残します。次は、読了記録を新しい順に並べる仕事へ進みましょう。
